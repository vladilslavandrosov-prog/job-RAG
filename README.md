# job-RAG

Документация и разбор кейсов по корпоративной RAG-системе для брокера/инвестиционного советника.

## Онбординг нового сотрудника

[`docs/onboarding.md`](docs/onboarding.md) (плюс читаемая версия [`docs/onboarding-standalone.html`](docs/onboarding-standalone.html)) — с этого документа лучше всего начинать: кто мы, кто клиенты (Д8 — активный оплачиваемый пилот, mz-arsenal — тёплый лид), сжатая проверенная архитектура, сводный список известных рисков и открытых вопросов, карта репозитория и порядок дальнейшего чтения по ролям.

## Описание системы (итоговый синтез)

[`docs/system-description.md`](docs/system-description.md) — финальная выкладка по всей базе: архитектура (компоненты, полный маршрут данных, ролевая модель, сайзинг), бизнес-портфель (пять практик, пилотная экономика, что реально волнует покупателей), и честный список нерешённого. Собрано тремя ролями (архитектор, аналитик, критик), сверено по иерархии приоритета источников ниже.

## Приоритет источников (при расхождении фактов между материалами)

1. **[`docs/rfi-responses/`](docs/rfi-responses/README.md) — наивысший приоритет.** Документ от разработчика платформы (инженерная/архитектурная команда вендора), а не от продаж или маркетинга. При расхождении с любым другим материалом в этой базе (презентации, лендинг, живые встречи, даже пилотные ТЗ) — **верным считается то, что написано здесь**, пока не появится более новый документ той же категории.
2. [`docs/sources/kamerata/`](docs/sources/kamerata/README.md) — тоже от разработчика, но сам себя помечает как рабочую версию с открытыми `[[...]]`-местами. Приоритет как у источника уровня 1 везде, где он даёт законченный ответ; в спорных/незакрытых местах — уступает `docs/rfi-responses/`.
3. `docs/analysis/case-03-pilot-tz-ai-guard.md` — пилотное ТЗ с юридической силой для конкретного пилота (количественные критерии приёмки).
4. `docs/accounts/` — дословная запись живых встреч; достоверна как факт «что сказали», но сказанное сейлзом/инженером на встрече может быть неточным или упрощённым по сравнению с письменным источником уровня 1.
5. `docs/sales-enablement/` — маркетинговый питч; самый низкий приоритет для фактической точности, полезен только для аргументации и позиционирования.

## Структура

- `docs/sources/` — исходные материалы (ТЗ, логи диалогов с системой); [`docs/sources/synaps-insight/`](docs/sources/synaps-insight/README.md) — 16 операционных гайдов разработчика под прежним рабочим названием платформы; [`docs/sources/kamerata/`](docs/sources/kamerata/README.md) — концептуальный обзор от разработчика под актуальным названием «Камерата» (после ребрендинга 20.08.2026).
- `docs/analysis/` — разбор кейсов: соответствие ТЗ, найденные дефекты, архитектурные предложения.
- `docs/glossary/` — глоссарий: базовые понятия RAG-систем простыми словами, с привязкой к проекту.
- `docs/platform/` — база знаний по интерфейсу платформы: разбор экранов по скриншотам.
- `docs/demo-retail/` — демо-кейсы для ретейла: сценарии использования платформы и (на втором этапе) пакет документов под них.
- `docs/sales-enablement/` — разбор внутреннего материала по методике продаж платформы (лендинг для сейлз-менеджеров): аргументы питча, кейсы клиентов, инструкции по демо, разбор возражений.
- `docs/accounts/` — живые, реальные аккаунты продаж: разбор встреч с конкретными заказчиками по мере их поступления (не гипотетические кейсы), с фокусом на вопросы и заинтересованность заказчика.
- `docs/rfi-responses/` — формальные письменные ответы вендора на технические запросы (RFI/due diligence): самый строгий и самокритичный источник в этой базе, с явным разделением «реализовано / настраивается / дорожная карта / не поддерживается».

Плюс ревизия 2 (35 слайдов) — целенаправленные точечные исправления (RBAC, роль Veai/DLP, каталог моделей) и новый технический дефект (нумерация разделов).
- [`docs/sources/pii-shield-masking-span-registry.docx`](docs/sources/pii-shield-masking-span-registry.docx) — документ разработчика (движок `pii-shield`): полный реестр из 20 встроенных PIIType (детектор/валидатор/токен маски на каждый), механизм кастомных типов (`CustomPIIType`, задаются через конфиг/Admin API в `pii_shield/config.py:151-200` — без ограничения по количеству, с полями id/prefix/patterns/валидатор), отдельный каталог секретов (gitleaks, opt-in), таблица приоритетов источников детекции и переменные окружения, управляющие маскировкой (`MASK_PII_TYPES`, `NER_SKIP_TYPES` и др.). Ключевое для незакрытых пунктов Перечня Д8 (номер договора, код клиента, хостнейм): новый атрибут добавляется без изменения кода платформы — через `CustomPIIType` с regex-паттерном и (опционально) одним из встроенных валидаторов (`luhn`, `inn`, `snils`, `bank_account`, `ogrn`, `iban`, `vin_checksum`, `entropy_min`).
- [`docs/analysis/pokrytie-maskirovaniya-perechen-d8.xlsx`](docs/analysis/pokrytie-maskirovaniya-perechen-d8.xlsx) — построчное сопоставление 30 пунктов заказчиковского [«Перечня информации, составляющей коммерческую тайну АО «Инвестиционная компания Д8», версия 3.0»](docs/sources/commercial-secret-perechen-d8-v3.pdf) (Приложение №2, приказ ГД от 18.05.2026 № 26-18/05-1) со встроенными типами PIIType платформы: статусы «Маскируется» (4) / «Частично» (5) / «Не маскируется» (21) по каждому пункту, нумерация — как в оригинале заказчика. Для всех пунктов, требующих уточнения, — вопрос к заказчику (с примером и, где применимо, технической рекомендацией), плюс разбивка «не маскируется» на потенциальный кастомный PIIType (8 пунктов) vs структурно другой слой контроля/DLP (13 пунктов), со ссылкой на встроенный DLP-механизм платформы (RFI §5.3). Прошло независимое ревью тремя ролями (аналитик/архитектор/критик): сверено с оригиналом скана (исправлена одна пропущенная формулировка), исправлена ошибка по IP-адресам (п. 3.3, уже покрыто типом IP), помечен риск для критерия приёмки пилота (номер договора). Плюс [`instrukciya-pokrytie-maskirovaniya-perechen-d8.docx`](docs/analysis/instrukciya-pokrytie-maskirovaniya-perechen-d8.docx) — сводная инструкция в 4 разделах (источник и контекст, методология, результаты покрытия, открытые вопросы к заказчику) в цветах платформы. Третий лист файла — «Три слоя маскирования»: техническая схема детектирования на каждый случай — Слой 1 (regex-шаблон без контрольной суммы), Слой 2 (вычисляемые значения — ИНН/СНИЛС/карта/ОГРН/IBAN, ровно те 6 типов, что подтверждены RFI), Слой 3 (примеры формулировок для DLP-детектирования организационного текста, например п. 1.1). Все regex и контрольные суммы проверены вычислением (примеры реально проходят описанный алгоритм), прошло отдельное ревью тремя ролями — исправлены битый regex номера договора, неверные веса ИНН, невалидный по Луну номер карты, ошибочная привязка банковского счёта к контрольной сумме (по RFI это формат, не checksum). Внизу листа — раздел 4: конкретные предложенные конфиги `CustomPIIType` (id/prefix/regex/валидатор/min_confidence) для трёх незакрытых пунктов Слоя 1 (номер договора, код клиента, внутренний хостнейм), опирающиеся на документ разработчика [`pii-shield-masking-span-registry.docx`](docs/sources/pii-shield-masking-span-registry.docx) — механизм добавления нового типа без изменения кода платформы, через конфиг/Admin API. Четвёртый лист — «Частичное маскирование»: разбор конкретного вопроса заказчика на реальном примере «Отчёта брокера» — достаточно ли скрыть только ПДн и название компании, если замаскировать документ целиком не удаётся. Вердикт всех трёх ролей единогласный: да, это концептуальная утечка — номер договора/счёта сегодня вообще не маскируется (известный пробел), точный состав портфеля и остатки сами по себе квазиидентификатор, а номер лицензии брокера деанонимизирует компанию в обход замаскированного названия. Пятый лист — «Стратегия без утечки»: конкретное решение — маршрутизация по каналу (внутренняя модель без ограничений vs внешняя только после расширенного маскирования + документ-уровневая DLP-блокировка), расширенный список полей для внешнего канала, честно признанный остаточный риск для портфельных цифр и чек-лист внедрения из 6 шагов.
- [`docs/analysis/pokrytie-maskirovaniya-perechen-d8-dlya-zakazchika.xlsx`](docs/analysis/pokrytie-maskirovaniya-perechen-d8-dlya-zakazchika.xlsx) — клиентская версия основного разбора: те же 30 пунктов и статусы, только 2 листа («Покрытие маскирования», «Три слоя маскирования»), без внутренних ссылок на review-процесс/пути к файлам репозитория. Комментарии и вопросы к заказчику переписаны в деловой формулировке — вместо повторяющегося технического абзаца про DLP-механизм в каждой из 12 строк оставлена короткая пометка и одно общее примечание в конце листа. Второй лист сохранён специально для заказчика — это объяснение самого подхода к маскированию (три слоя детектирования, regex-шаблоны, алгоритмы контрольных сумм — оставлены как есть технически), очищены только формулировки про внутренний review-процесс.
- [`docs/analysis/primer-podhoda-maskirovaniya-otchet-brokera.html`](docs/analysis/primer-podhoda-maskirovaniya-otchet-brokera.html) — клиентская, визуальная версия разбора на примере отчёта брокера (не для инженеров — для показа заказчику): «Лист 1» — исходный документ как есть, «Лист 2» — два варианта маскирования (Вариант 1 — отклонённый, с объяснением почему; Вариант 2 — рабочая схема, 7 из 8 полей, с разбором «как определяется каждое поле») и отдельная таблица применения по каналам («внутренний контур / внешняя модель»). Оформлено в устоявшемся визуальном языке проекта (карточки, статусные цвета — тот же стиль, что в остальных клиентских HTML). Формулировки несколько раз переписывались после обратной связи заказчика («видно, что сделано ИИ») — убраны самоописательные фразы, повторяющиеся ссылки на внутренний процесс ревью, а также блоки «Остаточный риск» и «Следующие шаги» (внутренние по духу, для заказчика не нужны); визуальный стиль при этом сохранён. Плюс [`primer-podhoda-maskirovaniya-otchet-brokera.docx`](docs/analysis/primer-podhoda-maskirovaniya-otchet-brokera.docx) — тот же текст в виде обычного Word-документа (сплошной текст, чёрно-белые таблицы) для печати/официальной переписки.
