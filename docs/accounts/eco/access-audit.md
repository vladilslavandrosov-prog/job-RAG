# Аудит доступа: домен «Эко» и пользователь eco_user@itq-group.com

Разбор по скриншотам живой платформы (Каталог → карточка пользователя и карточка домена), 11.09.2026. Механика проверена по `docs/platform/instrukciya-domeny-i-dostup.md` и `docs/platform/instrukciya-rls-nastroika-prav.md`.

| Блок | Значение |
|---|---|
| Персона | Нет назначенной персоны |
| Персона по умолчанию | Нет стандартной персоны |
| Домены | `Эко` |
| Команды | `Organization` |

## 2. Домен «Эко» → вкладка «Объекты»

4 объекта:

- `eco` (misc) — коллекция `eco`, Qdrant `dim=1024`
- `Fedoseeva` (regulation) — коллекция `Fedoseeva`
- `uploads_user_eco_user__misc` (misc) — по названию похожа на личную папку загрузок самого `eco_user`
- Search Services → `ns_Эко` — служебный Qdrant-namespace домена, управляется `doc-uploader/dlp/secret`

Все объекты — «Владельцы отсутствует» (не заполнено организационное поле, на доступ не влияет).

## 3. Вкладка «Разрешения» (эффективные права в Каталоге)

Показывает права на **редактирование метаданных каталога**, не видимость данных в чате (см. `instrukciya-domeny-i-dostup.md`, §5, «Что НЕ даёт доступа»):

- Разрешённые операции: `EditDescription`, `EditTags`, `EditCertification`, `ViewAll`, `EditTier`, `EditGlossaryTerms`, `EditOwners`, `All`
- `Domain Only Access Policy` → статус `MIXED`, 2 правила — ожидаемо для DOAR (одно правило ALLOW на объекты домена «Эко», одно DENY на всё остальное), не признак ошибки.
- Внизу — явная запись `Access to domain: Эко`, источник `Эко`: подтверждает, что домен-ограничение зарегистрировано на уровне движка прав, а не только текстом в карточке.

## 4. Выводы

### 4.1. RAG/документы — настроено и работает

Домен `Эко` + роль `Domain Only Access Role` вместе дают штатный, подтверждённый механизм (Часть 1 из `instrukciya-domeny-i-dostup.md`, §4): пользователь видит документы ровно из коллекций домена «Эко» (`eco`, `Fedoseeva`) и ничего за его пределами.

### 4.2. Структурные данные (RLS) — не настроено вообще

Персона не назначена → нет ни одного row-фильтра/маски. Практическое следствие зависит от того, входит ли релевантная SQL-схема (если она вообще есть у «Эко») в `governed_schemas`:
- входит → любой запрос по таблицам этой схемы вернёт **0 строк**, без ошибки — выглядит как «данных нет»;
- не входит → таблицы видны **целиком**, без ограничений.

Если у пилота «Эко» вообще планируется чат-по-данным (не только по документам СМК) — этому пользователю нужно завести персону отдельно; сейчас для этого сценария нет никакой настройки.

### 4.3. Открытый вопрос — возможное дублирование документов между коллекциями

В процессе разбора всплыл общий вопрос (не специфичный только для «Эко»): если один и тот же документ загружен в несколько коллекций, это на практике **стирает смысл разделения на домены** — обе аудитории получают доступ к документу независимо от того, кому какой домен назначен, плюс риск версионного расхождения при правках только в одной копии. Не проверено, есть ли у «Эко» такие дубли между `eco` и `Fedoseeva` — стоит сверить при следующей загрузке документов из `source/`.

### 4.4. Личная папка загрузок в общем домене

`uploads_user_eco_user__misc` лежит в том же домене «Эко», что и общие коллекции. Если домен «Эко» когда-нибудь назначат ещё кому-то, кроме `eco_user`, — личные загрузки этого пользователя автоматически станут видны и остальным обладателям домена. Стоит проверить список пользователей с доменом «Эко», прежде чем расширять доступ.
