## 3. Корневая причина №1 (подтверждена, не гипотеза): формат `.doc`

5 из 6 источников, которые удалось идентифицировать (1.2/1.3, 2.2, 2.3, 6.2) — старый бинарный `.doc`. Я лично проверил: **ни LibreOffice, ни pandoc не смогли открыть ни один из 16 `.doc`-файлов** этого корпуса (`Error: source file could not be loaded` / `Unknown input format doc`) — только `catdoc` с явным указанием кодировки (`-s cp1251 -d utf-8`) справился со всеми 16.

Если пайплайн загрузки документов в Камерату использует для разбора `.doc` тот же класс инструментов (LibreOffice-конвертация — стандартная практика для RAG-платформ), результат ожидаемо тот же: документ либо не проиндексировался вообще, либо проиндексировался пустым или битым текстом. Это объясняет 5 из 7 ошибок одной и той же причиной, а не пятью разными.

**Что сделать:** зайти в карточки коллекций `eco`/`Fedoseeva` на платформе и посмотреть количество чанков у этих 5 документов. Ноль или подозрительно мало относительно объёма файла (у И-16-01-11, например, 828 строк текста) — прямое подтверждение. Дальше — пересохранить весь `.doc`-корпус СМК в `.docx` (см. §5 внизу — таких документов большинство) и перезалить.

## 4. Корневая причина №2 (отдельная от формата): случай 5.2

ПР-10(02)-00 — **`.docx`**, я прочитал файл целиком, нужный ответ на месте, текстом, без искажений. Формат тут ни при чём — это **чистый провал поиска/группировки контента (retrieval/chunking)**, не парсинга. Вероятная причина: вопрос сформулирован бытовым языком («какую делать первой», «несколько заявок на срочный ремонт»), а в документе — канцелярским («приоритет отдается тем, которые способны оказать влияние на безопасность») — семантический поиск не сопоставил формулировки. Стоит проверить эту конкретную пару вопрос/документ отдельным тестом в чате под обычным пользователем, посмотреть, какой фрагмент документа модель вообще получает на входе.

**Вывод: у пилота минимум два независимых источника пробелов**, и их нельзя чинить одним и тем же действием — формат (§3) лечится переконвертацией корпуса, retrieval (§4) требует отдельной настройки (переформулировка чанков / калибровка поиска, см. `instrukciya-kalibrovka-politiki-poiska.md` в `docs/platform/`).

1. **Проверить количество чанков** у 5 `.doc`-источников из §3 в карточках коллекций — самый быстрый способ подтвердить причину без догадок.
2. **Пересохранить весь `.doc`-корпус СМК в `.docx`** и перезалить — по текущей выгрузке в `source/` таких большинство.
3. **По случаю 5.2 — отдельно проверить retrieval**, не откладывая на переконвертацию: спросить в чате тем же вопросом под обычным пользователем и посмотреть, какой фрагмент ПР-10(02)-00 модель реально получила.
4. **Донести недостающие источники**: И-12-10-03 (вопрос 3.2), документ про подрядчиков (4.2), документ/раздел про склад «Проверка ОКК» (5.1), сама Форма 17-08 как бланк (4.3).
