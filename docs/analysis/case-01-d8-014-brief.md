# Кейс 01. Приёмочный разбор диалога D8-014 против ТЗ RAG-системы

## Материалы

- `docs/sources/tz-rag-investment.pdf` — ТЗ «Корпоративная RAG-система интеллектуального поиска для брокера / инвестиционного советника», v1.0.
- `docs/sources/d8-014-chat-transcript.pdf` — реальный лог диалога с системой: подготовка к встрече с клиентом D8-014, среда «PII Shield».

## Задача разбора

Логи диалога — это, по сути, незапротоколированный прогон части UAT (раздел 4 ТЗ, тест-кейсы из раздела 5: `TC-AUM`, `TC-CL`, `TC-DOC`, категория «Отчётность и аналитика»). Разбираем его как приёмочную проверку: что система сделала верно по ТЗ, а что нарушает требования, и что это говорит об архитектуре агента.

## Хронология диалога

1. **Карточка клиента** — менеджер, сегмент, риск-профиль, цель по доходности, бенчмарк, стоимость портфеля, флаг внимания.
   Источники: `crm.crm.crm.clients`, `crm.crm.crm.managers`, `trade.trade.trading.mandates_targets`, `trade.trade.trading.portfolios`.
   Стоимость портфеля — не найдена, хотя `trading.portfolios` был среди источников.

2. **Сводка по позициям + проверка лимита концентрации.**
   Позиции: ЛУКОЙЛ 45.4993%, Газпром 31.2048%, Сбербанк 13.3059%, Минфин 8.2639%, Фонд ДР 1.7260%.
   Лимит на одного эмитента для риск-профиля BAL (регламент `rag_docs/01_reglament_limitov.md`) — 25%.
   Вывод агента: «лимит превышен» (со ссылкой на максимальную долю — ЛУКОЙЛ).

3. **P&L по месяцам + просадка.**
   2026-04: 896 090 ₽; 2026-05: -543 500 ₽; 2026-06: 1 499 000 ₽.
   Агент определил «наибольшую просадку» как разницу между апрельским и майским значением P&L: -1 439 590 ₽.

4. **Обращения клиента и незакрытые задачи.**
   Последнее обращение: 2026-06-12, email, исходящее, тема «Встреча по итогам квартала», статус «Закрыто».
   Незакрытых задач в доступных фрагментах не найдено.

5. **Финальный бриф к встрече (сводный запрос).**
   Агент **не смог** собрать итоговый бриф по всем пунктам: сослался на «синтаксический сбой» в последнем SQL по позициям и на то, что по обращениям в доступном фрагменте есть только последнее обращение. Подтвердил лишь портрет клиента, последнее обращение, лимит по регламенту и исключения из лимита. Отказался приводить данные о перевесе в Лукойле/Газпроме и майской просадке — **хотя эти же данные были им ранее корректно получены на шагах 2 и 3 этого же диалога.**

## Соответствие ТЗ: что сделано верно

| Требование ТЗ | Где проявилось | Оценка |
|---|---|---|
| Указание источников в каждом ответе (2.3) | Во всех 5 ответах указаны конкретные таблицы/файлы | Выполняется |
| Отказ при недостатке данных вместо выдумывания (2.3, критерий приёмки №5) | «Стоимость портфеля не найдена» (шаг 1), честный отказ собрать бриф целиком (шаг 5) | Выполняется — агент не галлюцинирует цифры |
| Ссылка на регламент с конкретным фрагментом (2.1.3) | `rag_docs/01_reglament_limitov.md`, фрагмент «Риск-профили клиентов» | Выполняется |

## Найденные дефекты

### Дефект 1 — неполная проверка лимита концентрации (шаг 2)

Проверка сравнила с лимитом только максимальную позицию (ЛУКОЙЛ, 45.4993%). Но Газпром (31.2048%) тоже превышает лимит 25% для BAL. Ответ на финансовый запрос по факту неполный — это напрямую попадает под критерий приёмки №1 «Точность ответов на финансовые запросы» (порог ≥90%): при двух нарушениях лимита сообщено об одном.

**Причина:** правило проверки лимита реализовано как `MAX(доля) > лимит`, а не как поэлементная проверка `для каждого эмитента: доля > лимит`.

### Дефект 2 — подмена понятия «просадка» (шаг 3)

Финансовое определение просадки (drawdown) — падение от локального пика к минимуму **накопленной** стоимости портфеля. Агент вместо этого сравнил соседние значения помесячного P&L (896 090 → -543 500) и назвал их разность просадкой. Это не одно и то же: P&L по месяцам — это поток, а не накопленный баланс, и разница потоков не является просадкой в терминах NAV/эквити.

**Последствие:** цифра -1 439 590 ₽, которую агент назовёт клиенту как «просадку», методологически некорректна и может ввести в заблуждение сотрудника фронт-офиса на встрече с клиентом. Тоже нарушение критерия приёмки №1.

### Дефект 3 (главный) — потеря уже подтверждённых фактов при финальной агрегации (шаг 5)

Это ключевая архитектурная находка. К шагу 5 в диалоге уже были **успешно** получены:
- структура позиций с долями (шаг 2);
- динамика P&L и просадка (шаг 3).

При сводном запросе агент не переиспользовал эти уже полученные и показанные пользователю результаты, а заново сгенерировал SQL для получения тех же данных в более сложном агрегирующем виде — и именно этот новый запрос упал с синтаксической ошибкой. В результате пользователь на финальном, самом важном шаге получил **менее полную сводку**, чем сумма того, что агент уже показал ранее в том же диалоге.

Это не проблема “агент врёт” (что было бы хуже) — агент корректно не стал выдумывать. Проблема в том, что **у агента нет памяти о собственных уже верифицированных результатах внутри сессии**: каждый запрос (включая финальный синтез) транслируется в новый text-to-SQL вызов с нуля, вместо переиспользования/агрегации уже полученных tool-результатов из истории диалога.

Это напрямую бьёт по:
- Основному сценарию использования системы («аналитик/менеджер фронт-офиса готовит бриф к встрече» — п. 1.3, 2.1.4);
- Косвенно — по критерию приёмки №1 (точность), поскольку правильный путь (взять уже подтверждённые числа) был доступен, но не использован.

### Дефект 4 — неполное использование истории при поиске по обращениям (шаг 5)

На шаге 4 агент уже установил: незакрытых задач по клиенту нет. На шаге 5 вместо использования этого факта агент написал расплывчато, что «в доступном фрагменте есть только последнее обращение» — то есть по сути повторно (и хуже) переобследовал источник вместо переиспользования собственного вывода.

## Общий вывод

Система в целом соответствует «мягким» требованиям ТЗ по прозрачности (источники, честный отказ), но проваливает точность на двух независимых уровнях:
1. **Бизнес-логика/финансовая семантика** (Дефекты 1–2) — неверные правила проверки лимита и понятия просадки, независимо от архитектуры RAG.
2. **Управление состоянием сессии** (Дефекты 3–4) — агент не хранит и не переиспользует собственные, уже подтверждённые в диалоге результаты, из-за чего на самом важном (сводном) шаге теряет данные, которые сам же подтвердил минутами ранее.

Оба дефекта относятся к критическим критериям приёмки ТЗ (раздел 4, №1 «Точность ответов на финансовые запросы», ≥90%) — по факту приёмку в текущем виде проходить не должны.

## Рекомендации (для следующего кейса)

1. Проверку лимита концентрации переделать на поэлементную (по каждому эмитенту), а не только по максимальной доле.
2. Разделить понятия «P&L по периодам» и «просадка» (drawdown): считать просадку по накопленной кривой стоимости портфеля (NAV), а не по разности соседних P&L.
3. Добавить агенту память по сессии: результаты уже выполненных под-запросов (SQL и его результат) должны кэшироваться и переиспользоваться при финальном синтезе, а не порождать новый independent-запрос.
4. При падении финального агрегирующего запроса — предусмотреть fallback: собрать бриф из уже имеющихся в контексте диалога подтверждённых результатов вместо полного отказа от соответствующего пункта.
