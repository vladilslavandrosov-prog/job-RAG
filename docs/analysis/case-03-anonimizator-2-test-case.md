# Описание тестового кейса: «Анонимизатор-2» — обезличивание в документе

Приложение №1 к Договору № ИКД-1-PRO от 15.07.2026, блок «Анонимизатор» (AI Guard), сценарий №2.
Тестовые материалы: [`docs/test-data/anonymizer-2-test-documents/`](../test-data/anonymizer-2-test-documents/).

## 1. Что проверяется

Способность AI Guard распознавать и маскировать персональные данные (ПДн) внутри загружаемых
документов — не в тексте запроса, а именно в приложенных файлах — перед тем, как содержимое
документа может уйти во внешнюю облачную LLM, и корректно восстанавливать (демаскировать) эти
данные в ответе.

## 2. Критерий приёмки (дословно из ТЗ)

| Параметр | Значение |
|---|---|
| Форматы | xls/xlsx, doc/docx, pptx, json, xml, txt, pdf (машиночитаемый и сканированный) — 7 форматов |
| Объём выборки | ≥10 документов на формат |
| Порог распознавания/маскирования | ≥98% целевых сущностей распознано и замаскировано |
| Порог утечек | 0 случаев утечки немаскированной сущности во внешний запрос |

## 3. Тестовый набор

Стартовый набор — **2–3 документа на формат** (24 файла), достаточный для быстрой проверки
пайплайна на каждом формате перед тем, как расширять его до полного объёма ≥10/формат. Три
сюжета, каждый воспроизведён во всех 8 форматах (7 из ТЗ + отдельно pdf-текст/pdf-скан):

1. **Анкета клиента** (Смирнов П.А.) — плотный набор персональных данных: ФИО, дата рождения,
   паспорт, ИНН, СНИЛС, адрес, телефон, email, номер договора, номер счёта, номер карты.
2. **Служебная записка** (Кузнецова А.В.) — ПДн внутри связного текста, а не только в полях
   формы — проверяет, что распознавание не зависит от табличной структуры.
3. **Реестр операций** (5 клиентов) — табличный формат с повторяющимися типами сущностей у
   разных лиц — проверяет, что маскирование не путает сущности между записями.

Все ФИО и реквизиты — синтетические, явно помечены как тестовые данные в каждом файле; реальные
клиенты Д8 не задействованы.

`pdf-scan/` — отдельно верифицировано: файлы не содержат текстового слоя (`pdftotext` не
извлекает ни одного символа), то есть это честная имитация скана, требующая OCR-ветки
распознавания AI Guard, а не текстовой.

## 4. Процедура прогона

1. Загрузить документы (по одному или партиями по формату) в контур AI Guard так, как это
   делает пилотная группа в реальном сценарии — через чат/агента, куда прикладывается файл.
2. Зафиксировать, какие сущности AI Guard распознал и заменил метками, и какие — нет.
3. Свериться с `manifest.json` в папке тестовых документов — там перечислены все реально
   встроенные в каждый файл ПДн-сущности (тип + значение).
4. Посчитать факт. % = (верно найденные и замаскированные сущности) / (все сущности в
   `manifest.json` для этого документа) × 100.
5. Отдельно проверить исходящий трафик к облачной LLM (или его лог) на предмет немаскированных
   значений из `manifest.json` — любое совпадение считается утечкой.
6. Прогнать обратный путь (демаскирование в ответе) — сверить, что восстановленные значения в
   ответе AI Guard совпадают с оригиналом, без путаницы между сущностями разных клиентов
   (особенно важно на «Реестре операций», где сущности одного типа повторяются у разных лиц).

## 5. Как трактовать результат

- **≥98% по формату и 0 утечек** — критерий выполнен для этого формата.
- **Ниже порога на конкретном формате** — не автоматический провал пилота: по сценарию 6
  («грязные данные») в ТЗ прямо предусмотрено, что фактический % ниже целевого фиксируется как
  список пробелов покрытия с рекомендациями по донастройке, а не как безусловный дефект. Тот же
  принцип стоит применять и здесь — фиксировать конкретный тип сущности/формат, где просело
  распознавание, а не просто итоговый %.
- **Любая зафиксированная утечка** — блокер, требует разбора до перехода к следующему формату,
  независимо от общего %.

## 6. Ограничение стартового набора

2–3 документа на формат достаточно, чтобы увидеть, работает ли пайплайн на формате в принципе,
но **не** достаточно для формального закрытия критерия приёмки (нужно ≥10/формат для
статистически значимой оценки). Если стартовый набор проходит без структурных проблем (пайплайн
корректно обрабатывает каждый формат), набор стоит расширить до полного объёма по тому же
шаблону данных перед финальной приёмкой сценария.
