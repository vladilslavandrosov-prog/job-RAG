# Вопросы к вендору по дорожной карте (Q4 2026 – H2 2027)

Свод вопросов по документу `docs/sources/kamerata/roadmap-2026q4-2027h2.md` (см. разбор — `case-10-roadmap-analysis.md`), собираемый по мере разбора пунктов, для передачи команде платформы одним пакетом. По каждому вопросу — формулировка для вендора и отдельно наше внутреннее мнение (не для передачи, только для собственной подготовки к разговору).

## Вопрос 1 — Маскирование локальных файлов агента рабочей станции (РМ-1)

**Пункт roadmap:** РМ-1, Q1 2027, уровень C — «Служба чтения локальных файлов на рабочей станции (Windows, macOS) с явной моделью запретов.»

**Вопрос для вендора:**

В пункте РМ-1 указана «явная модель запретов» — правила, определяющие, какие файлы и папки агенту запрещено читать на рабочей станции пользователя. Не указано, что происходит с содержимым файлов, которые агенту читать разрешено. Просьба уточнить:

1. Проходит ли содержимое локальных файлов через тот же механизм маскирования персональных данных и коммерческой тайны (PII Shield / dlp-secret), который сегодня применяется к RAG-корпусу и чату, прежде чем попасть в контекст запроса к LLM — или для рабочей станции предусмотрен отдельный, ещё не описанный контур защиты?
2. Действует ли для агента на рабочей станции то же правило, что и для серверной части: маскирование обязательно только при обращении к внешней (облачной) модели и необязательно при полностью локальной модели в изолированном контуре — или для рабочей станции это правило жёстче (например, маскирование всегда, независимо от того, локальная модель или облачная)?
3. Кто формирует «явную модель запретов» — администратор централизованно (например, через групповые политики, вместе с MSI-установкой по РМ-2), или пользователь может сам расширять список разрешённых на своей машине папок сверх того, что задал администратор?
4. Обращения агента к локальным файлам попадают в тот же журнал аудита (Журнал DLP / audit-БД), что и обращения через серверную часть, или для рабочей станции планируется отдельный журнал?

**Наше мнение (внутреннее):**

Это первый пункт всей дорожной карты, где рядом с новой функцией явно не упомянута уже заявленная модель защиты данных (PII Shield, DLP, маскирование) — вероятно, потому что документ фиксирует только направление (уровень C: «архитектурное решение подтверждено, состав уточняется»), а не готовую архитектуру. Именно поэтому стоит спросить сейчас, до того как эта функция попадёт в договор как обязательство: если маскирование локальных файлов архитектурно не предусмотрено, агент на рабочей станции создаёт новый канал утечки данных, полностью в обход периметра AI Guard, выстроенного для серверной части. Из всех 35 пунктов дорожной карты это единственный с очевидным потенциальным пробелом в безопасности — логично поставить его первым в пакете вопросов вендору.

## Вопрос 2 — Гранулярный доступ внутри одной коллекции документов (предложение для roadmap, не найденный баг)

**Пункт roadmap:** не привязан к конкретному коду — предлагаем рассмотреть как отдельное новое направление, вероятно в линии «Каталог» (КАТ-) или «Надзор» (НАД-).

**Важное уточнение (после независимой проверки предложения, см. `case-20-katalog-tree-critic-verdict.md`):** ниже фактически два разных вопроса, которые легко перепутать. Предложение из этого раздела отвечает только на второй — это стоит явно разделить и при передаче вендору.

- **2a. Гранулярность *внутри* одной коллекции** — доступ на уровне отдельного документа, раздела документа или тега, без дробления коллекции. Это исходный вопрос вендору (см. ниже), и предложенное дерево каталогов **его не решает**: по документированной сегодня архитектуре домен — неизменяемое после создания поле коллекции (`instrukciya-domeny-i-dostup.md`, §3), значит любой узел дерева технически реализуем только как отдельная коллекция — то есть это по-прежнему гранулярность *между* коллекциями. Если единый документ содержит абзац про отпуска и абзац про оклад в одном файле, ни сегодняшняя плоская модель, ни предложенное дерево не разведут их без физического разнесения по разным документам.
- **2b. Организация множества плоских доменов в управляемую структуру** — то, что реально решает дерево каталогов, описанное ниже: вместо десятков не связанных друг с другом плоских доменов/коллекций — иерархия с наследованием видимости между ними.

**Контекст.** При разборе типового сценария «внутри одной тематической области нужен разный уровень допуска» (пример — домен «Кадры»: отпуска и больничные доступны всем сотрудникам, а оклады — только начальнику отдела) выяснилось следующее:

- Для **табличных данных** (DWH) это решается штатно — механизм RLS (`instrukciya-rls-nastroika-prav.md`) позволяет на одной и той же таблице задавать разные row-фильтры и маски колонок для разных персон.
- Для **документов** (RAG-корпус) аналогичного механизма в документации не описано. По концептуальному обзору (`kamerata-overview-review.md`, П3 «Домены», П6 «Коллекции») и рабочей инструкции (`instrukciya-domeny-i-dostup.md`) модель доступа к документам плоская: у коллекции есть один технический домен-ярлык (или домена нет — коллекция общая), и это правило действует на всю коллекцию целиком. *(Точность формулировки: карточка коллекции отдельно поддерживает привязку к нескольким «бизнес-доменам ОМ» — `instrukciya-domeny-i-dostup.md`, §3, «можно выбрать несколько» — но задокументированного правила, работает ли это как «ИЛИ» или «И» для видимости, найти не удалось; стоит уточнить у вендора отдельно.)* Единственный документированный способ развести уровни допуска внутри одной темы — завести отдельную, более узкую коллекцию с отдельным доменом, а не настроить гранулярность внутри существующей.

**Вопрос для вендора:**

1. **(2a, исходный вопрос)** Планируется ли механизм гранулярного доступа внутри одной коллекции документов — аналог RLS, но для неструктурированного контента (например, на уровне отдельного документа, раздела документа или тега, а не только всей коллекции целиком)?
2. Если да — на каком горизонте дорожной карты и в какой линии? Если нет — подтверждаете ли вы, что рекомендуемый паттерн сегодня — дробление одной темы на несколько коллекций с разными доменами? Есть ли для этого практические ограничения (например, по общему числу доменов/коллекций на инстанс)?
3. **(2b, отдельный вопрос от вопроса выше — не путать при обсуждении)** Планируется ли иерархическая организация доменов/коллекций (родитель → потомок, с наследованием видимости вниз)? Сопоставимые платформы это уже реализуют — например, Microsoft Purview (вложенные governance-домены до 5 уровней, с явной функцией «Restrict inherited permissions» на отдельной подколлекции) и Databricks Unity Catalog (`catalog.schema.table` с наследованием прав и дополнительной проверкой прав на каждом уровне пути) — подробнее см. `case-19-precedent-issledovanie-ierarhiya-dostupa.md`.
4. Если такая иерархия появится — как предполагается решать доступ персоны сразу к нескольким несмежным узлам одного домена (например, аудитору или комплаенс-специалисту нужен доступ к двум конкретным отделам ветки «Оклады», но не ко всему дереву «Кадры»)? Во всех проверенных нами аналогах (SharePoint, Google Drive, Databricks, Purview) для этого случая используется отдельный, второстепенный механизм сверх базового наследования (прямой грант / флаг «Limited-Expansive access» / представления-«витрины») — планируется ли что-то подобное, или узел дерева будет единственной единицей выдачи прав?
5. Что происходит с уже выданными привязками персон при реструктуризации дерева (перенос узла из одной ветки в другую, изменение глубины при реорганизации отдела)? В Purview, например, документированной поддержки «переподвесить» опубликованный домен к другому родителю найти не удалось — интересно, будет ли у Камераты то же ограничение, и если да, то что происходит с уже проиндексированными документами узла при переносе.

**Наше предложение (конкретная модель — для вопроса 2b, организация множества доменов; вопрос 2a о внутридокументной гранулярности она не закрывает):**

Вместо плоского списка независимых доменов — сделать домен **деревом каталогов**, где каталоги наследуют друг друга по иерархии видимости: персона, привязанная к узлу дерева, видит документы этого узла **и всех его потомков**, но по умолчанию не видит соседние ветки и не видит выше себя.

```
Домен «Кадры»
├── Общее                          ← видно персоне «Сотрудник» (отпуска, больничные, справочники)
└── Оклады                         ← НЕ наследуется веткой «Общее» — отдельная ветка
    ├── Отдел продаж               ← видно персоне «Начальник отдела продаж»
    ├── Отдел логистики            ← видно персоне «Начальник отдела логистики»
    └── ...
```

Правило по умолчанию: **видимость течёт вниз по дереву от узла привязки, вбок и вверх — не течёт.**

- Персона «Сотрудник» привязана к узлу «Общее» → видит только отпуска/больничные, про «Оклады» не знает вообще, потому что это не потомок «Общее», а отдельная ветка.
- Персона «Директор по персоналу» привязана к **корню домена** «Кадры» → наследует всё дерево целиком: и «Общее», и «Оклады» со всеми отделами внутри. Это не частная удобная деталь примера, а закреплённое во всех проверенных аналогах свойство корня — в Purview права корневого («default») домена в принципе нельзя ограничить (см. `case-19`, §4.3).
- Персона «Начальник отдела продаж» — **составной случай, исправленный после критики** (`case-20`, §2: исходная версия этого примера молча предполагала видимость «Общее», хотя по буквальному правилу «вбок не течёт» узел «Оклады / Отдел продаж» её не даёт). Решение — **явно множественная привязка «персона → узлы»**: начальник отдела продаж привязывается сразу к двум узлам, «Общее» и «Оклады / Отдел продаж», а не только к одному. Это не костыль поверх дерева, а прямое продолжение того, как многодоменность уже работает в платформе сегодня без всякого дерева (`instrukciya-domeny-i-dostup.md`: «выбрать домен(ы) из списка» — множественное число) — дерево не отменяет эту множественность, а добавляет к ней вложенность там, где сама ось «насколько чувствительно» имеет внутреннюю структуру.

Так задача решается не «одним деревом», а двумя составляющими вместе: (1) дерево с наследованием вниз — для оси «насколько чувствительны данные», и (2) множественная привязка персоны к нескольким узлам — для совмещения этой оси с осью «какая у персоны роль/отдел». Обе оси в итоге закрываются без дробления на формально независимые домены, у которых сегодня нет общего «взгляда сверху». Это не изобретение с нуля: отдельное исследование прецедентов (`case-19-precedent-issledovanie-ierarhiya-dostupa.md`) подтверждает, что правило «видимость течёт вниз, вбок и вверх — не течёт» и разрыв наследования на отдельной ветке — задокументированное поведение как минимум в Microsoft Purview (функция «Restrict inherited permissions» + тот же инвариант «корень домена ограничить нельзя»), Google Drive («Limited access» / «Expansive access» на общих дисках), SharePoint («break inheritance») и Databricks Unity Catalog (наследование по `catalog.schema.table` с дополнительной проверкой прав по всему пути). То же исследование указывает на два открытых момента, которые стоит обсуждать с вендором как вопросы, а не считать решёнными самим деревом: ни одна из этих систем не обходится без отдельного механизма для доступа персоны к нескольким несмежным узлам сразу (вопрос 4 выше), и минимум две из них (Purview, SharePoint) документированно не облегчают перенос узла в дереве после того, как на него уже назначены права (вопрос 5 выше).

**Наше мнение (внутреннее):**

Отсутствие гранулярности для документов — не баг и не пробел в тестировании, а осознанное следствие сегодняшней модели «домен = тематическая область» (data mesh-подход, где домен — это грубая, а не гранулярная граница; сама типология доменов Камераты — Source-aligned / Consumer-aligned / Aggregate — прямо заимствована из канонической терминологии data mesh Дехгани, см. `case-19`, §4.1, хотя сама эта теория, что важно, описывает поток данных между доменами, а не иерархию доступа внутри одного — прецедент для вложенности взят не из неё, а из платформ governance поверх неё, Purview и Unity Catalog). Важно не путать это с вопросом 2a — дерево и вся эта модель отвечают только на организационный вопрос 2b, а не на исходный вопрос про гранулярность внутри одной коллекции; выносить их вендору стоит как два отдельных пункта, иначе есть риск, что содержательный ответ по 2a потеряется за обсуждением дерева. Предложенное дерево — не критика плоской модели, а её естественное расширение, и это расширение теперь подкреплено конкретными, проверяемыми прецедентами (`case-19`), а не только интуицией. До появления такого механизма рабочий обходной путь остаётся прежним — дробление на несколько коллекций с разными доменами, что не блокирует пилот Д8, но требует более тщательного проектирования доменной структуры на старте.

Отдельно стоит держать в поле зрения два смежных момента из параллельных разборов: (1) security-стресс-тест (`case-18-security-stress-test-workstation-i-katalogi.md`) отмечает риск «тихого усечения» — RAG-запрос, которому для ответа нужен синтез сразу по двум непересекающимся веткам дерева, может дать уверенный, но неполный ответ без сигнала, что часть данных скрыта, в отличие от честного «не найдено» у сегодняшней плоской модели; (2) дерево каталогов покрывает только документы, заведённые в коллекцию, — оно никак не связано с локальными файлами, которые агент рабочей станции (Вопрос 1, РМ-1) читает напрямую с диска пользователя мимо каталога вообще. То есть даже при полном внедрении этого предложения канал прямого чтения через агент РМ-1 остаётся отдельным, не покрытым деревом (см. Вопрос 1 выше и `case-20`, §7).
