# База данных ТоргЛайн (Postgres) — живой источник для подключения платформы

В отличие от файлового пакета в `docs/demo-retail/dataset/` (документы Word/Excel, загружаемые в платформу как источники), это — структурированная СУБД, к которой платформа подключается напрямую (по стандартному протоколу Postgres), как описано в реальной встрече с заказчиком mz-arsenal («подключение к существующим источникам данных по стандартным протоколам»). Полезно демонстрировать оба типа источников — неструктурированные документы и живую БД — в одном сценарии.

Все компании, лица, счета и цифры полностью вымышлены. Структура и данные согласованы с уже существующим файловым пакетом (те же магазины, тот же поставщик «ФрешПродукт», тот же договор «ЭлектроБытТех» из `docs/accounts/mz-arsenal/next-meeting-prep.md`, тот же клиент Иванов И.И.) — это не отдельно придуманный набор фактов, а структурированный эквивалент того, что уже есть в xlsx/docx.

## Файлы

- `init.sql` — полный DDL + seed-данные, один скрипт «от пустой БД до готового к демо состояния».
- `docker-compose.yml` — локальный Postgres 16 с автозагрузкой `init.sql` при первом старте (`docker compose up`, порт 5432, база `torgline_demo`, пользователь `torgline`/`torgline_demo_password` — сменить перед реальным использованием).
- `torgline-demo-data.xlsx` — тот же набор данных для просмотра/сверки без БД: один лист на таблицу, названия полей в заголовке каждого листа, выгружено напрямую из работающей БД (не из `init.sql` вручную, чтобы точно совпадало с тем, что реально загружается).

Проверено: скрипт запускался и был провалидирован на реальном Postgres 16 (не в docker — в этой среде не было доступа к докер-демону, проверка шла через локальный `psql`); ключевые запросы по каждому сценарию исполнены и сверены с ожидаемыми ответами. При выгрузке в xlsx всплыл отдельный баг: `pandas` по умолчанию распознаёт длинные цифровые строки (номера счетов, БИК) как числа и молча портит их из-за потери точности float64 — банковский счёт `40702810500000098765` превращался в `40702810500000096256`. Исправлено принудительным чтением всех колонок как текста; итоговый xlsx сверен построчно с `init.sql` после исправления.

## Структура данных (первая версия)

| Таблица | Что хранит | К какому сценарию относится |
|---|---|---|
| `regions`, `stores` | Справочник регионов и магазинов сети | 2, 3 |
| `suppliers` | Реквизиты поставщиков (ИНН/КПП/ОГРН, банковские реквизиты, контактное лицо) | 1, 9 |
| `contracts` | Условия договоров: категория, сроки, отсрочка платежа, штрафы, гарантия (мес.) | 1, 9 |
| `products` | Каталог SKU с привязкой к категории и поставщику | 1, 3 |
| `sales_sku_monthly` | Продажи и маржа по SKU за месяц (сеть в целом) | 1 |
| `sales_store_monthly` | Выручка/себестоимость/маржа по магазину за месяц | 2 |
| `inventory_snapshots` | Снимок остатков по магазину/SKU на дату + расчётный «остаток в днях» | 3 |
| `promotions`, `promotion_skus`, `promotion_effectiveness` | Промо-акции, участвующие SKU, фактическая эффективность | 3, 7 |
| `customers`, `loyalty_transactions` | Клиенты программы лояльности и история начислений/списаний баллов | 5 |
| `supplier_claims` | Журнал претензий/штрафов/компенсаций по поставщикам | 1 |
| `employees` | Сотрудники с ролью, привязкой к магазину/региону и логином для входа в платформу — опора для персон «Графа доступа» | 2 |
| `data_sensitivity_catalog` | Каталог чувствительных полей (PII / финансовые / условия договора) по всем таблицам | 9, настройка AI Guard |

**Осознанное упрощение для v1**: `sales_sku_monthly` (сеть в целом по SKU) и `sales_store_monthly` (по магазину без разбивки по SKU) — это две отдельные агрегатные таблицы, а не одна гранулярная таблица «магазин × SKU × период». В уже существующих исходных xlsx-файлах такая полная гранулярность никогда не публиковалась — сшивать её означало бы придумывать цифры, которых нет. Если платформе для демонстрации понадобится вопрос вида «выручка по SKU в конкретном магазине», это повод добавить `sales_store_sku_daily` отдельным, осознанным шагом (см. «Что дальше»), а не подгонять текущие агрегаты.

## Что чему соответствует (быстрая сверка со сценариями)

- Сценарий 1 (бриф перед встречей с поставщиком) → `suppliers` + `contracts` + `sales_sku_monthly` + `supplier_claims`.
- Сценарий 2 (доступ по ролям) → `sales_store_monthly` (колонки `purchase_cost`/`margin_rub` — кандидаты на маскирование для роли «директор магазина», см. `data_sensitivity_catalog`) + `employees` как справочник самих персон (`employees.login` — логин, на который заводится персона в «Графе доступа»; сознательно не в `data_sensitivity_catalog` — маскировать его нельзя, на нём держится сама привязка политик доступа).
- Сценарий 3 (контроль остатков) → `inventory_snapshots` + `promotions`/`promotion_skus`.
- Сценарий 5 (жалоба клиента) → `customers` + `loyalty_transactions`.
- Сценарий 9 (маскирование договора, `docs/demo-retail/scenarios.md`) → `contracts.warranty_months` и реквизиты в `suppliers` — те же самые данные, что и в `dogovor-postavki-tehnika-garantiya.docx`, но теперь ещё и в структурированном виде, для демонстрации маскирования колонок БД, а не только текста документа.

## Бонусная находка при проверке

При тестовом прогоне SQL-запроса для сценария 3 («остаток ниже 3 дней продаж») обнаружилось, что ранее записанный в `dataset/README.md` и `presentation/retail-qa-doc.docx` «ожидаемый ответ» был неполным — реальный расчёт по тем же исходным цифрам даёт заметно более длинные списки SKU по каждому магазину (например, у Магазина №08 и №27 под порог попадают все 6 SKU, а не 3, как было ошибочно записано ранее). Оба файла исправлены на пересчитанный и SQL-проверенный список.

## Как запустить

```bash
# Вариант 1 — Docker
cd docs/demo-retail/database
docker compose up -d
psql "postgresql://torgline:torgline_demo_password@localhost:5432/torgline_demo"

# Вариант 2 — существующий Postgres
psql -h <host> -U <user> -d <db> -f init.sql
```

## Что дальше (не сделано в этой версии, осознанно)

- Гранулярная таблица продаж на уровне «магазин × SKU × день/месяц» — как только появится реальная потребность в таком срезе на демо.
- Роли и права доступа на уровне самой БД (`GRANT`/`ROW LEVEL SECURITY`) — сейчас разграничение ролей демонстрируется через «Граф доступа» платформы, а не через политики самого Postgres; `data_sensitivity_catalog` — это описание того, что нужно замаскировать, а не работающий контроль доступа.
- История изменений (кто и когда обновил гарантийные условия договора, изменил банковские реквизиты и т.д.) — понадобится, если демо перейдёт от «снимка данных» к демонстрации аудита изменений.
