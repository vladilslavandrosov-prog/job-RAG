# Пакет документов для live-демо на платформе (ретейл)

16 файлов, готовых к загрузке в «Синапс.Инсайт» — реальные исходные данные (Word/Excel) для фиктивной сети «ТоргЛайн», под все 9 сценариев из `docs/demo-retail/scenarios.md`. Демонстрация проходит **в самой платформе**: файлы загружаются как источники, а дальше все ответы — реальные ответы агента по этим данным, не заготовленный текст.

Структура пакета (папка-коллекция на сценарий, реальные документы, вопросы для нового чата) соответствует реальной внутренней методике подготовки демо, описанной в видеоинструкциях из `docs/sales-enablement/README.md` (создать коллекцию под кейс → загрузить документы → задавать вопросы в новом чате → одна папка на отрасль). Пакет «ТоргЛайн» — отраслевой аналог примера «Автозавод» из этой методики, только для ретейла.

## Настройка для сценария 9 (маскирование договора)

Тоже настройка платформы, не документ — в правилах маскирования (AI Guard) до демо нужно завести:

| Роль | Режим маскирования | Что скрыто |
|---|---|---|
| Рядовой сотрудник — «жёсткое» маскирование | Данные вырезаются без пометки | Банковские реквизиты (р/с, к/с, БИК), ФИО и контакты сторон, вся статья 4 «Гарантийные обязательства» |
| Рядовой сотрудник — «мягкое» маскирование | Маркер-заглушка вместо данных (например, «текст скрыт политикой») | То же самое, но с явной пометкой о скрытии |
| Сотрудник СБ / авторизованная роль | Без маскирования | Ничего — полный текст договора |

Правило «статья "Гарантийные обязательства" — маскировать всегда» стоит завести отдельным кастомным regex/тематическим правилом (не полагаться только на общее правило по банковским реквизитам), чтобы продемонстрировать именно настраиваемость, о которой шла речь на встрече с заказчиком.

## Полный сценарий демонстрации (вопросы + ожидаемый ответ)

Ожидаемые ответы приведены по данным, реально заложенным в файлы — если платформа отвечает иначе, это тоже показательно (повод обсудить с командой платформы).

### Сценарий 1. Бриф перед встречей с поставщиком

1. «Дай карточку поставщика "ФрешПродукт": условия контракта, категория товаров, срок действия, штрафные условия.»
   → Категория «Fresh», срок 15.01.2025–31.12.2026, отсрочка 21 день, неустойка 0,1%/день за просрочку, право на пересмотр условий при 3+ нарушениях за квартал.
2. «Покажи динамику продаж и маржи по его SKU за 2 квартал 2026, выдели просадку.»
   → Просадка по SKU FR-1001 (томаты грунтовые) в мае: продажи упали с 12 500 до 6 800 шт., маржа просела пропорционально; в июне — восстановление до 11 900 шт.
3. «Были ли претензии или штрафы за последние 6 месяцев?»
   → 4 инцидента за 2 квартал 2026, неустойки на 43 300 руб., компенсации на 83 600 руб., последнее — уведомление о пересмотре условий (03.06.2026).
4. «Собери итоговый бриф к переговорам: условия контракта, динамика продаж/маржи, штрафы, рекомендация по пересмотру условий.»
   → Здесь и проверяется многошаговый синтез: должен ли агент переиспользовать три уже полученных ответа, или заново пересчитывать/терять часть данных.

### Сценарий 2. Разграничение доступа по ролям

Один вопрос **«Покажи выручку и маржу по магазинам»** — от трёх персон:
- Директор Магазина №14 → видит только строку своего магазина, без колонок закупочной стоимости/маржи.
- Региональный директор (Центральный) → видит Магазин №14 и №22, с маржой.
- Финансист HQ → видит все 6 магазинов и все колонки.

### Сценарий 3. Контроль остатков по акции

1. «Какие сейчас идут акции и по каким товарам?» → «Дачный сезон», 15.07–15.08.2026, категория CAT-NEW-BBQ.
2. «Покажи магазины, где остаток по SKU акции ниже 3 дней продаж.» → ожидается список (пересчитан и проверен SQL-запросом по `docs/demo-retail/database/init.sql`, отличается от более короткого списка, который был здесь раньше): Магазин №14 (BBQ-1002, BBQ-1003, BBQ-1006), №22 (BBQ-1001, BBQ-1003, BBQ-1004), №31 (BBQ-1002, BBQ-1003), №08 (все 6 SKU: BBQ-1001, 1002, 1003, 1004, 1006, 1008), №19 (BBQ-1001, BBQ-1002, BBQ-1003, BBQ-1004), №27 (все 6 SKU: BBQ-1001, 1002, 1003, 1004, 1006, 1008).
3. «Сформируй список для догрузки по приоритету — сначала магазины с наибольшим оборотом.» → приоритет: №31, №14, №22, №19, №27, №08 (по выручке из `prodazhi-po-magazinam.xlsx`).

### Сценарий 4. Онбординг продавца-консультанта

1. «Как оформить возврат товара без чека?» → до 5 000 руб. — по документу, удостоверяющему личность, и заявлению; свыше — согласование с директором; при повреждённой заводской упаковке — отдельный регламент.
2. «Что делать, если сработала защитная бирка на выходе?» → пригласить к стойке, проверить чек и бирки, при расхождении — вызвать администратора/охрану, без применения силы.
3. «Какая скидка положена держателю карты лояльности уровня "Золото"?» → начисление 5% + доп. акции и приоритетная поддержка.

### Сценарий 5. Обработка жалобы клиента

1. «Клиент Иванов И.И. жалуется, что не получил баллы за покупку от 12.07. Проверь начисления.» → покупка на 3 200 руб., начислено 160 баллов, зачислено 14.07.2026 (в течение 48 часов согласно правилам программы) — баллы фактически начислены.
2. «Какая политика возврата баллов при возврате товара?» → баллы списываются пропорционально возвращённой сумме.
3. «Составь ответ клиенту с объяснением.» → синтез из истории покупок + политики лояльности.

### Сценарий 6. Пополнение глоссария мерчандайзинга

См. раздел выше — загрузить `planogramma-novaya.docx` отдельно, проверить очередь «Задачи → Предложения».

### Сценарий 7. Шаблонный отчёт по акции

1. Завести шаблон: триггер «эффективность акции [название]», образец ответа с графиком, обычный режим.
2. «Эффективность акции "Дачный сезон"?» → выручка 6 750 000 руб., средний чек 1 890 руб., прирост 38% (цель была 35%), охват лояльности 44% (цель была 40%) — акция превысила целевые показатели.
3. Для сравнения — тот же вопрос со строгим шаблоном, чтобы показать разницу в поведении.

### Сценарий 8. RAG vs Closed-book

Вопрос: «Можно ли принять возврат товара с повреждённой заводской упаковкой, если у покупателя нет чека?»
- RAG-агент → находит `reglament-nestandartnyh-vozvratov.docx`: да, при подтверждении покупки картой лояльности/выпиской, лимит 3 000 руб. без согласования, свыше — с директором.
- Closed-book агент → не располагает внутренним регламентом компании, даёт общий ответ или честно отказывается — наглядная разница.

### Сценарий 9. Маскирование договора и доверие к ответу ИИ

1. «Проверь договор поставки № 118-БТ/2026 с ООО "ЭлектроБытТех": устраивают ли нас условия, можно ли подписывать, есть ли риски для нас как для Покупателя?» (роль — рядовой сотрудник, «жёсткое» маскирование, ст. 4 вырезана без пометки)
   → **риск, который нужно поймать на демо**: если модель отвечает уверенно («условия стандартные, рисков не вижу») и не упоминает, что раздел про гарантию ей не виден — это именно тот сценарий, которого опасался заказчик на живой встрече (см. `docs/accounts/mz-arsenal/meeting-01-analysis.md`, раздел 1). Ожидаемо корректное поведение — модель обязана явно сообщить о неполноте данных, а не тихо давать вывод по неполной картине.
2. Тот же вопрос, «мягкое» маскирование (маркер-заглушка на месте ст. 4) → ожидаемый ответ: «раздел "Гарантийные обязательства" скрыт политикой безопасности, не могу оценить гарантийные риски по этому пункту» — модель явно отказывается от суждения там, где не хватает данных.
3. Тот же вопрос от роли сотрудника СБ / авторизованной роли, без маскирования → полный ответ с конкретными цифрами: гарантия 24 месяца, аннулируется при вскрытии не авторизованным сервисом или нарушении условий хранения, реакция поставщика 3/10 рабочих дней, при 3+ обращениях за 12 месяцев — полная замена партии за счёт поставщика.
4. «Покажи, как этот договор выглядит для рядового сотрудника после маскирования» → банковские реквизиты и ФИО сторон заменены на метки (Number1, Person1 и т.д.), статья 4 — с маркером-заглушкой (в «мягком» режиме) или полностью отсутствует (в «жёстком»).
