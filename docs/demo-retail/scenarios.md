# Демо-кейсы для ретейла: этап 1 — сценарии

Цель — показать возможности платформы «Синапс.Инсайт» на материале, знакомом ретейлеру: SKU, остатки, промо-акции, лояльность, поставщики. Каждый сценарий нацелен на конкретную, уже подтверждённую возможность платформы (см. `docs/platform/`), чтобы демонстрация была не абстрактной, а прямо показывала работающий механизм.

Фиктивная компания для демо: **«ТоргЛайн»** — сеть розничных магазинов (продукты питания + непродовольственные товары), несколько регионов, собственная программа лояльности.

## Обзор сценариев

| № | Сценарий | Персона | Что демонстрирует |
|---|---|---|---|
| 1 | Бриф перед встречей с поставщиком | Категорийный менеджер | Многошаговый синтез, text-to-SQL, шаблоны |
| 2 | Разграничение доступа по ролям | Директор магазина / регион. директор / финансист HQ | Граф доступа: row-фильтры и маски |
| 3 | Контроль остатков по акции | Региональный операционный менеджер | Data-вопросы → SQL, потенциал для проактивных алертов |
| 4 | Онбординг продавца-консультанта | Новый сотрудник магазина | Промпты персон, recall шаблонов, политики ранжирования |
| 5 | Обработка жалобы клиента | Специалист поддержки | Объединение CRM-данных и документов, маскирование ПДн |
| 6 | Пополнение глоссария мерчандайзинга | Категорийный менеджер (модерация) | Конвейер «Задачи → Предложения» |
| 7 | Шаблонный отчёт по акции | Маркетинг-аналитик | «Мои шаблоны» — обычный/строгий режим, график |
| 8 | RAG vs Closed-book | Менеджер по обучению | Ценность retrieval, агенты Closed-book RAG |

## Сценарий 1. Бриф перед встречей с поставщиком

**Персона:** категорийный менеджер (аналог роли «менеджер фронт-офиса» из брокерского кейса).

**Данные для демо:** таблица контрактов с поставщиками (условия, сроки, штрафные санкции), таблица продаж/маржи по SKU за квартал в разрезе поставщика, история претензий/переписки.

**Диалог (черновик):**
1. «Дай карточку поставщика "ФреshПродукт": условия контракта, категория товаров, срок действия, штрафные условия.»
2. «Покажи динамику продаж и маржи по его SKU за последний квартал, выдели просадку.»
3. «Были ли претензии или штрафы за последние 6 месяцев?»
4. «Собери итоговый бриф к переговорам: условия контракта, динамика продаж/маржи, штрафы, рекомендация по пересмотру условий.»

**Что демонстрирует:** тот же класс сценария, что и Кейс 01 (D8-014) — многошаговый синтез в финальном запросе. Это намеренно: сценарий 1 — точка проверки, починен ли в актуальной версии платформы дефект «потери уже подтверждённых данных при синтезе». Если демо проходит гладко — это сильный аргумент в пользу зрелости платформы; если нет — воспроизводимый пример для доработки.

**Формат артефакта:** лог диалога (аналогично `docs/sources/d8-014-chat-transcript.pdf`), возможно с HTML-версией по образцу уже разобранных страниц.

## Сценарий 2. Разграничение доступа по ролям

**Персона:** один и тот же вопрос от трёх ролей — директор магазина, региональный директор, финансист HQ.

**Данные для демо:** таблица продаж/маржи по магазинам с колонками закупочной цены и наценки; персоны с настроенными row-политиками (магазин → свой магазин; регион → свой регион; HQ → всё) и масками (закупочная цена/маржа скрыта для роли «директор магазина»).

**Диалог (три параллельных ветки на один вопрос):**
- Директор магазина: «Покажи продажи и маржу по моему магазину за месяц» → видит только свой магазин, колонка маржи замаскирована или недоступна.
- Региональный директор: тот же вопрос по региону → видит все магазины региона, маржа видна.
- Финансист HQ: тот же вопрос «по всем регионам» → видит всё, включая закупочные цены.

**Что демонстрирует:** «Граф доступа» — row-фильтры и маски по персонам (`docs/platform/upravlenie-dannymi.md`) — то, что в исходном ТЗ было заявлено как «опционально в v2», но фактически уже есть в платформе как механизм.

**Формат артефакта:** три параллельных мини-диалога + один скриншот настройки самой политики доступа (по образцу «Политики доступа» в «Графе доступа»).

## Сценарий 3. Контроль остатков по акции

**Персона:** региональный операционный менеджер.

**Данные для демо:** таблица остатков по SKU и магазинам, календарь текущих промо-акций, таблица топ-SKU акции.

**Диалог:**
1. «Какие сейчас идут акции и по каким SKU?»
2. «Покажи магазины, где остаток по топ-20 SKU текущей акции ниже 3 дней продаж.»
3. «Сформируй список для догрузки по приоритету (сначала магазины с наибольшим оборотом).»

**Что демонстрирует:** роутинг «Data-вопросы» → SQL-агрегация по таблице остатков (`docs/platform/kalibrovka-politiki-poiska.md`). Естественный мостик к следующему уровню демонстрации — то же самое можно превратить в проактивный алерт (batch-агент), а не ждать, пока менеджер спросит сам.

**Формат артефакта:** лог диалога + короткая заметка «как то же самое работало бы проактивно» (концептуальное расширение, не реализация).

## Сценарий 4. Онбординг продавца-консультанта

**Персона:** новый сотрудник магазина, первая неделя работы.

**Данные для демо:** регламент кассовых операций, инструкция по технике безопасности, скрипты типовых продаж, попутно — в общем индексе платформы может присутствовать посторонний технический контент (код кассового ПО, коммиты) — намеренно, чтобы показать фильтрацию.

**Диалог:**
1. «Как оформить возврат товара без чека?»
2. «Что делать, если сработала защитная бирка на выходе?»
3. «Какая скидка положена держателю карты лояльности уровня "Золото"?»

**Что демонстрирует:** «Промпты персон» — агент отвечает в стиле, подходящем новичку (просто, пошагово); recall из «Мои шаблоны» — на часто задаваемые вопросы подставляется выверенный ответ; политики ранжирования — технический шум (код, коммиты кассового ПО) не просачивается в ответ обычному продавцу, даже если формально «похож» на вопрос про кассу.

**Формат артефакта:** лог диалога + таблица «что было в индексе, что попало в ответ, что отфильтровано» (аналогично мокапу фильтрации чанков в `kalibrovka-politiki-poiska.md`).

## Сценарий 5. Обработка жалобы клиента

**Персона:** специалист службы поддержки.

**Данные для демо:** история покупок и начислений баллов лояльности клиента, текст политики возврата/обмена, лог предыдущих обращений клиента.

**Диалог:**
1. «Клиент Иванов И.И. жалуется, что не получил баллы за покупку от 12.07. Проверь начисления.»
2. «Какая политика возврата баллов при возврате товара?»
3. «Составь ответ клиенту с объяснением и, если применимо, компенсацией.»

**Что демонстрирует:** объединение «CRM-подобных» данных (история покупок, баллы) с документами (политика лояльности) в одном ответе; маскирование персональных данных — специалист поддержки видит нужные для работы поля (история покупок, баллы), но не видит, например, полный номер платёжной карты — та же механика «Графа доступа», что и в сценарии 2, только на уровне колонок с ПДн, а не финансовых показателей.

**Формат артефакта:** лог диалога + пример замаскированного и незамаскированного вида одних и тех же данных для разных ролей.

## Сценарий 6. Пополнение глоссария мерчандайзинга

**Персона:** категорийный менеджер в роли модератора очереди.

**Данные для демо:** новый документ (планограмма или промо-календарь) с новыми кодами категорий/акций, ещё не известными системе.

**Сценарий:**
1. Загружается новый документ с упоминаниями кодов вида `PROMO-24-Q3-SNACKS`, `CAT-NEW-ECO`.
2. Система автоматически предлагает эти коды как кандидаты в глоссарий термина (аналог `document_review`/`glossary_term` из `docs/platform/zadachi-review-pipeline.md`), с оценкой уверенности.
3. Категорийный менеджер заходит в «Задачи → Предложения», видит очередь, одобряет/отклоняет.

**Что демонстрирует:** конвейер human-in-the-loop модерации — система не просто ищет по документам, а *расширяет свои же знания* под присмотром человека, что особенно важно для быстро меняющегося ретейл-ассортимента (сезонные акции, новые категории).

**Формат артефакта:** скриншот-мокап очереди предложений с новыми ретейл-специфичными терминами (по образцу реального скриншота «Предложения», но с ретейл-данными вместо кредитного риска).

## Сценарий 7. Шаблонный отчёт по акции

**Персона:** маркетинг-аналитик.

**Данные для демо:** таблица продаж по акциям, история предыдущих отчётов об эффективности акций.

**Сценарий:**
1. Заводится шаблон: вопрос-триггер «эффективность акции [название]», образец ответа с графиком (прирост продаж, средний чек, охват), обычный (не строгий) режим.
2. Через месяц аналитик спрашивает про уже прошедшую новую акцию с похожей формулировкой — получает ответ той же структуры, но с пересчитанными по свежим данным цифрами и графиком.
3. Для сравнения — тот же вопрос со «строгим» шаблоном, где меняются только цифры, а формулировки остаются буквально теми же.

**Что демонстрирует:** «Мои шаблоны» (`docs/platform/moi-shablony.md`) — обычный режим (структура фиксирована, данные свежие) против строгого (текст фиксирован полностью) — наглядная разница на реальном примере с графиком.

**Формат артефакта:** лог диалога с двумя вариантами ответа (обычный/строгий шаблон) на один и тот же вопрос.

## Сценарий 8. RAG vs Closed-book

**Персона:** менеджер по обучению, проверяющий качество ответов ИИ-агента перед тем, как раскатать его на всех сотрудников.

**Данные для демо:** внутренний регламент по нестандартной ситуации (например, «правила приёма возврата без чека при повреждении упаковки»), которого не может «знать» модель без доступа к документам компании.

**Сценарий:**
1. Вопрос задаётся одновременно двум агентам: обычному RAG-агенту (с доступом к документам компании) и Closed-book агенту (только общие знания модели, аналог `Синапс.Инсайт — Closed-book RAG` из `docs/platform/agenty.md`).
2. RAG-агент отвечает точно, со ссылкой на конкретный пункт регламента.
3. Closed-book агент либо честно отказывается («не располагаю данными о внутреннем регламенте компании»), либо даёт общий, неточный ответ — наглядно показывая, зачем вообще нужен RAG, а не просто чат с LLM.

**Что демонстрирует:** ценность retrieval через прямое сравнение, и заодно — назначение агентов типа Closed-book RAG (эталон/сравнение, а не бесполезный дубликат).

**Формат артефакта:** лог с двумя параллельными ответами на один вопрос.

## Этап 2 — готово

Формат: демонстрация проходит в самой платформе — поэтому вместо готового текста/презентации подготовлен пакет из 15 реальных исходных документов (Word/Excel) для загрузки в «Синапс.Инсайт», плюс сценарий live-демо с вопросами и ожидаемыми ответами.
