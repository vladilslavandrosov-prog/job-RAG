# Раздел «Агенты»

> Скриншот: `Разделы → Агенты`.

## Назначение экрана

Каталог и конструктор агентов платформы.

> «Соберите нового агента на канвасе — он пройдёт утверждение DS→ИБ и появится в селекторе чата. Существующих можно редактировать на канвасе как новую версию.»

## Элементы экрана

| Элемент | Назначение |
|---|---|
| **⭐ Создать агента** | Собрать нового агента на визуальном конструкторе («канвасе») |
| **📋 Реестр агентов** | Полный реестр (за пределами списка «активных» на этой странице) |
| Таблица «Активные агенты (3)» | Агент / Тип / Канвас |
| «Мои заявки (0)» | Заявки текущего пользователя на утверждение — пусто |

### Активные агенты (пример)

| Агент | Тип | Канвас |
|---|---|---|
| Синапс.Инсайт — Аналитик (планировщик) | RAG | системный (без flow) |
| Синапс.Инсайт — Closed-book RAG (системный) | RAG | системный (без flow) |
| Синапс.Инсайт — Closed-book RAG (канвасный) | RAG | [Редактировать на канвасе] |

## Наблюдения

### Разгадан смысл «DS» в «Агенты на утверждении (DS)»

В `zadachi-review-pipeline.md` оставался открытым вопрос, что означает «DS» в заголовке экрана согласования агентов. Формулировка здесь — **«утверждение DS→ИБ»** — вместе с описанием той стадии («проверьте назначение и состав агента — домены данных, узлы и параметры») подсказывает, что DS, скорее всего, означает не «Data Science», а **Data Steward** (роль, ответственная за то, к каким доменам/таблицам данных агенту разрешено обращаться) — что куда лучше согласуется с содержанием проверки (домены данных, узлы, параметры), чем «Data Science». После DS-проверки заявка уходит на «ИБ» (информационную безопасность) — итого двухступенчатое согласование: сначала владелец данных подтверждает, что агенту можно видеть эти данные, потом безопасность подтверждает отсутствие рисков.

### Два класса агентов, теперь видно наглядно

Экран подтверждает архитектуру, предположенную в `zadachi-review-pipeline.md` на основе описания «Промптов персон»:

- **Системные агенты без flow** («системный (без flow)» в колонке «Канвас») — простые, без визуально сконструированного графа обработки; вероятно, это как раз то, чем управляют «Промпты персон» (ролевые системные промпты).
- **Канвасные агенты** («Закрытый-book RAG (канвасный)», с кнопкой «Редактировать на канвасе») — визуально сконструированный граф обработки (flow), полноценный governed-агент, требующий согласования DS→ИБ при создании/правке.

### «Closed-book RAG» — агент, сознательно не использующий retrieval

Два из трёх «активных агентов» называются **«Closed-book RAG»** — «closed-book» в контексте LLM обычно означает «отвечать по собственным (parametric) знаниям модели, без внешнего поиска», то есть прямая противоположность самой идее RAG. Наличие такого агента в системе, ориентированной на RAG, — не противоречие, а осознанный инструмент: вероятно, используется как:
- эталон для сравнения («что отвечает модель без доступа к нашим данным» — полезно для оценки эффекта retrieval'а);
- обработчик вопросов, для которых поиск не нужен или не имеет смысла (общие вопросы, не связанные с корпоративными данными — ср. `TC-NEG-03` из ТЗ, «прогноз рынка», где система должна отвечать «не делаю прогнозов», а не искать в базе).

Существование сразу двух версий («системный» и «канвасный») одного и того же Closed-book RAG агента — стоит уточнить, чем они отличаются в поведении, раз оба закрыты от retrieval.
