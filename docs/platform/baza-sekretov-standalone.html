База секретов

Админка векторной базы коммерческой тайны и настроек DLP-детекции: провайдеры моделей, чанки, реранкинг, словари, кастомные regex-паттерны, управление коллекцией Qdrant и токены интеграции.

Это практическая реализация связки, описанной в документе разработчика: pii-shield (детекция PII) + dlp-secret (проверка политики секретности, вызывается отдельно, только PASS/REVIEW/BLOCK).

03 Наполнение базы и поиск

Добавить (чанк вручную)

Форма добавления фрагмента коммерческой тайны напрямую в базу — без загрузки файла. Поля: текст фрагмента (плейсхолдер «Вставьте текст коммерческой тайны…»), уровень секретности (SECRET / CONFIDENTIAL / INTERNAL / PUBLIC), категория, тип документа, «Подтверждено (логин ИБ)» — необязательное поле, пусто = требует проверки ИБ.

Механика (из встроенной подсказки «Как это работает»):

  1. Текст автоматически бьётся на чанки — ~400 токенов, перекрытие 25%.
  2. Каждый чанк векторизуется моделью ru-en-RoSBERTa (dim=768).
  3. Чанки сохраняются в коллекцию confidential_chunks в Qdrant.
  4. Пайплайн детекции начинает использовать их немедленно — без отдельного шага переиндексации.

Поиск (семантический)

Поиск похожих чанков по смыслу: векторизация запроса + поиск ближайших, без требования точного совпадения слов. Фильтры: уровень секретности (по умолчанию «Все»), статус (по умолчанию active), Top-K результатов (по умолчанию 10).

04 Тест детекции (текст против базы)

Проверка произвольного текста на присутствие коммерческой тайны. Фильтр по уровню секретности, Top-K совпадений на чанк (по умолчанию 3). Кросс-энкодер в этом тесте отключён (CROSS_ENCODER_ENABLED=false) — используется чистая косинусная близость.

Механика (из подсказки «Как работает тест»):

  1. Текст разбивается на чанки.
  2. Каждый чанк проверяется по справочнику ключевых слов.
  3. Каждый чанк векторизуется и ищется в базе коммерческой тайны (косинус).
  4. Максимальный score по чанку определяет решение.
  5. Совпадения по ключевым словам добавляют +0.05 к score (максимум за 3 слова).
ScoreРешение
score < 0.75PASS
0.75–0.88REVIEW
score ≥ 0.88BLOCK

Пороги — глобальные

Пороги PASS/BLOCK совпадают с теми, что показаны на экране «Управление базой» (раздел 8) — значит это глобальная настройка, а не параметр конкретного теста.

05 Реранкинг (тестирование кросс-энкодеров)

06 Словари и блэклист

Ключевые слова (справочник)

Справочник ключевых слов/синонимов, участвующий в скоринге теста детекции (+0.05 к score, см. раздел 4). На момент снимка пуст (0 активных / 0 всего). Фильтры: поиск по слову/синониму/категории, категория, показывать «Только активные». Добавление — кнопка «+ Добавить».

Блэклист ОМ

Термины из OpenMetadata с тегом типа blacklist, загружаются автоматически. На момент снимка пуст (0 активных / 0 всего). Фильтры: поиск по термину/источнику, тип сущности, тип токена, показывать «Только активные». Кнопки «Загрузить из файла» и «Тест детекции».

Тест-площадка: блэклист

Отдельный от общего «Теста детекции» экран (тот тестирует совпадение с базой коммерческой тайны по векторному сходству — PASS/REVIEW/BLOCK). Здесь — поле ввода текста, кнопки «Проверить»/«Очистить», результат вида «Совпадений не найдено» / список совпадений, с пометкой «Детекция через pii-shield».

Проверено на практике (17.08.2026)

Паттерн «Номер договора / брокерский-лицевой счёт (Д8)» (\b[А-Я]{2}\d{4,6}(?:-[А-Я]{2}-\d{1,3})?\b, тип токена CUSTOM) подтверждённо сохранён на экране «Regex-паттерны» и активен («статус: активен»), но тест на этом экране с текстом, содержащим совпадающую строку («ВР33431»), вернул «Совпадений не найдено».

Раз паттерн активен и корректен, а совпадения всё равно нет — это подтверждает, что «Тест-площадка: блэклист» проверяет именно термины блэклиста (catalog_blacklist, точное совпадение по значениям из OM), а не пользовательские regex-паттерны из таблицы custom_patterns, несмотря на пометку «Детекция через pii-shield».

Надёжный способ проверить именно применение кастомного regex-паттерна с заменой на токен маски — не через этот экран, а через реальный чат + «Журнал LLM-сессий» (см. открытый вопрос в реестре и case-03-instrukciya-proverka-maskirovaniya.md).

Политики синхронизации (блэклиста)

Таблица формируется автоматически воркером синхронизации — по одной строке на каждую колонку, извлечённую из OpenMetadata; позволяет отключить отдельную колонку или удалить её вместе со всеми накопленными терминами. На момент снимка пуста — заполняется при первом запуске воркера, требует OM_SYNC_ENABLED=true и заданных OM_URL, OM_TOKEN в .env.

На практике (17.08.2026) добавлены и подтверждены активными оба паттерна из инструкции по новым атрибутам маскирования — «Номер договора / брокерский-лицевой счёт (Д8)» и «Номер лицензии брокера (Д8)», тип токена CUSTOM у обоих.

Найден встроенный тест одного паттерна

По кнопке «Изменить» у строки паттерна разворачивается инлайн-форма редактирования с дополнительным полем «Тестовый текст» и кнопкой «Проверить» — точечная проверка именно этого паттерна на введённом тексте, без похода на отдельный экран «Тест детекции»/«Тест-площадка: блэклист».

Это, вероятно, самый прямой способ проверить конкретный regex-паттерн — важно только вводить в это поле реальный пример текста (например ВР33431), а не сам паттерн: подстановка regex-синтаксиса как тестового текста закономерно даёт «Совпадений не найдено» и ничего не говорит о работоспособности паттерна.

На практике (17.08.2026) в оба поля «Тестовый текст» была вставлена копия самого regex-паттерна вместо примера реальных данных — оба теста закономерно вернули «Совпадений не найдено». Тестирование настоящим примером (ВР33431, 045-07514-100000) ещё предстоит.

Про тип токена

Это не текстовое поле и не совпадает с 20 встроенными PIIType из документа разработчика (там нет PROJECT/PRODUCT, а ORG/COMPANY — разные имена типа). CUSTOM, судя по всему, — общий catch-all для всего, что не подпадает под первые четыре категории; отдельного, узнаваемого префикса маски под конкретный кастомный атрибут (типа [CONTRACT_N]) через этот экран завести нельзя — только общий [CUSTOM_N].

Механика (из подсказки «Как это работает»)

Паттерны хранятся в таблице custom_patterns и выдаются pii-shield через GET /api/v1/shield-config; pii-shield поллит этот endpoint каждые N секунд (интервал — PII_CATALOG_BLACKLIST_SYNC_INTERVAL) и применяет паттерны в своём RegexDetector.

Открытый вопрос

Остаётся не до конца ясным (см. реестр открытых вопросов): это самостоятельный, более простой механизм, чем CustomPIIType из документа разработчика (id/prefix/display_name/валидатор через config.py), или упрощённая UI-надстройка над тем же самым, где prefix в этом конкретном развёртывании зафиксирован пятью значениями.

Это те же значения порогов, что и в «Тест детекции» (раздел 4).

«Опасная зона»

Полный необратимый сброс коллекции (секреты, негативы или обе сразу), подтверждение — ввод слова «УДАЛИТЬ». После сброса требуется заново запустить bootstrap или загрузить документы.

Интеграция (токены)

Управление токенами, которыми pii-shield авторизуется при вызове POST /api/v1/check — через заголовок X-Internal-Token. Форма создания токена (название для идентификации, например pii-shield-prod), таблица активных токенов (название, значение токена, дата создания, кнопка «Отозвать» — независимый отзыв на каждый токен).

Инструкция «Как подключить pii-shield»:

  1. Создать токен, скопировать значение.
  2. В pii-shield указать токен — либо переменной окружения DLP_INTERNAL_TOKEN=..., либо в тестовом чате: sidebar → DLP Integration → Internal token.
  3. Указать endpoint DLP_ENDPOINT=http://localhost:8000.
  4. Включить DLP: DLP_ENABLED=true.

Подтверждение архитектуры

Это прямое подтверждение архитектуры из документа разработчика: dlp-secret (политика секретности PASS/REVIEW/BLOCK) — отдельный сервис от pii-shield (детекция PII), связаны через этот internal-токен и HTTP-вызов, а не общий процесс.
