# Раздел «База секретов»

Отдельный верхнеуровневый пункт меню (наравне с «Платформа», «Качество», «Рабочее место ИБ»), не пересекающийся со «Источники → Документы». Это админка векторной базы коммерческой тайны и настроек детекции DLP — практическая реализация того, что в документе разработчика [`pii-shield-masking-span-registry.docx`](../sources/pii-shield-masking-span-registry.docx) описано как связка `pii-shield` (детекция PII) + `dlp-secret` (проверка политики секретности, вызывается отдельно, только PASS/REVIEW/BLOCK).

Полный список пунктов меню: Список документов, Добавить, Загрузить, Поиск, Тест детекции, Реранкинг, Ключевые слова, Провайдеры, Блэклист ОМ, Загрузить блэклист, Тест детекции, Политики синхронизации, Regex-паттерны, Управление базой, Интеграция. Ниже описаны экраны, увиденные на скриншотах; непросмотренные — в конце статьи.

## Провайдеры

Список из 12 подключённых провайдеров моделей (фильтры по типу — «Облачная LLM» / «Эмбеддинги» — и статусу, по умолчанию `active`). Из увиденного: `ollama ext`, `ollama loc` (обе — Облачная LLM, домен `gpt.iqi.internal`), `TEI (jina-code)`, `TEI (bge-m3)` (обе — Эмбеддинги), `Amazon Bedrock` (Облачная LLM, домен `bedrock-runtime.amazonaws...`). Это, судя по всему, реестр реальных бэкендов, на которые платформа route-ит вызовы моделей — отдельный от селектора модели в самом чате.

## Добавить (чанк вручную)

Форма добавления фрагмента коммерческой тайны напрямую в базу — без загрузки файла. Поля: текст фрагмента (плейсхолдер «Вставьте текст коммерческой тайны…»), уровень секретности (`SECRET` / `CONFIDENTIAL` / `INTERNAL` / `PUBLIC`), категория, тип документа, «Подтверждено (логин ИБ)» — необязательное поле, пусто = требует проверки ИБ.

Механика (из встроенной подсказки «Как это работает»):
1. Текст автоматически бьётся на чанки — ~400 токенов, перекрытие 25%.
2. Каждый чанк векторизуется моделью `ru-en-RoSBERTa` (dim=768).
3. Чанки сохраняются в коллекцию `confidential_chunks` в Qdrant.
4. Пайплайн детекции начинает использовать их немедленно (без отдельного шага переиндексации).

## Поиск (семантический)

Поиск похожих чанков по смыслу (векторизация запроса + поиск ближайших, без требования точного совпадения слов). Фильтры: уровень секретности (по умолчанию «Все»), статус (по умолчанию `active`), Top-K результатов (по умолчанию 10).

## Тест детекции (текст против базы)

Проверка произвольного текста на присутствие коммерческой тайны. Фильтр по уровню секретности, Top-K совпадений на чанк (по умолчанию 3). Кросс-энкодер в этом тесте отключён (`CROSS_ENCODER_ENABLED=false`) — используется чистая косинусная близость.

Механика (из подсказки «Как работает тест»):
1. Текст разбивается на чанки.
2. Каждый чанк проверяется по справочнику ключевых слов.
3. Каждый чанк векторизуется и ищется в базе коммерческой тайны (косинус).
4. Максимальный score по чанку определяет решение: `score < 0.75` → **PASS**, `0.75–0.88` → **REVIEW**, `≥ 0.88` → **BLOCK**.
5. Совпадения по ключевым словам добавляют +0.05 к score (максимум за 3 слова).

Пороги PASS/BLOCK совпадают с теми, что показаны на экране «Управление базой» (см. ниже) — значит это глобальная настройка, а не параметр конкретного теста.

## Реранкинг (тестирование кросс-энкодеров)

Отдельный экран для подбора и сравнения моделей реранкинга. Активная production-модель — `cross-encoder/mmarco-mMiniLMv2-L12-H384-v1` (реранкинг включён, `max_length=512`). Форма теста: текст запроса → векторизация → топ-50 кандидатов → реранжирование выбранной моделью; настраиваются модель, Top-K результатов, фильтр по уровню секретности.

|---|---|---|---|---|---|
| `cross-encoder/mmarco-mMiniLMv2-L12-H384-v1` | 50 языков, вкл. RU | 470 MB | ★★★☆☆ | production | MVP-выбор: CPU-friendly, ~80 мс/чанк |
| `BAAI/bge-reranker-v2-m3` | Многоязычный | 2200 MB | ★★★★★ | не загружена | State-of-the-art; требует ≥8 GB RAM |

## Ключевые слова (справочник)

Справочник ключевых слов/синонимов, участвующий в скоринге теста детекции (+0.05 к score, см. выше). На момент снимка пуст (0 активных / 0 всего). Фильтры: поиск по слову/синониму/категории, категория, показывать «Только активные». Добавление — кнопка «+ Добавить».

## Блэклист ОМ

Термины из OpenMetadata с тегом типа `blacklist`, загружаются автоматически. На момент снимка пуст (0 активных / 0 всего). Фильтры: поиск по термину/источнику, тип сущности, тип токена, показывать «Только активные». Кнопки «Загрузить из файла» и «Тест детекции» (см. следующий раздел).

### Тест-площадка: блэклист

Отдельный от общего «Тест детекции» экран (тот описан выше, тестирует совпадение с базой коммерческой тайны по векторному сходству — PASS/REVIEW/BLOCK). Здесь — поле ввода текста, кнопки «Проверить»/«Очистить», результат вида «Совпадений не найдено» / список совпадений, с пометкой «Детекция через pii-shield».

**Проверено на практике (17.08.2026):** паттерн «Номер договора / брокерский-лицевой счёт (Д8)» (`\b[А-Я]{2}\d{4,6}(?:-[А-Я]{2}-\d{1,3})?\b`, тип токена `CUSTOM`) подтверждённо сохранён на экране «Regex-паттерны» и активен («статус: активен»), но тест на этом экране с текстом, содержащим совпадающую строку («ВР33431»), вернул «Совпадений не найдено». Раз паттерн активен и корректен, а совпадения всё равно нет — это подтверждает, что «Тест-площадка: блэклист» проверяет именно термины блэклиста (`catalog_blacklist`, точное совпадение по значениям из OM), а не пользовательские regex-паттерны из таблицы `custom_patterns`, несмотря на пометку «Детекция через pii-shield». См. открытый вопрос в [`otkrytye-voprosy.md`](otkrytye-voprosy.md#база-секретов) — надёжный способ проверить именно применение кастомного regex-паттерна с заменой на токен маски — не через этот экран, а через реальный чат + «Журнал LLM-сессий» (см. `case-03-instrukciya-proverka-maskirovaniya.md`).

## Политики синхронизации (блэклиста)

Таблица формируется автоматически воркером синхронизации — по одной строке на каждую колонку, извлечённую из OpenMetadata; позволяет отключить отдельную колонку или удалить её вместе со всеми накопленными терминами. На момент снимка пуста — заполняется при первом запуске воркера, требует `OM_SYNC_ENABLED=true` и заданных `OM_URL`, `OM_TOKEN` в `.env`.

## Regex-паттерны (пользовательские)

URL: `/dlp/patterns/`. Форма добавления кастомного regex-паттерна: Название (например «ИНН физлица»), Regex-паттерн (синтаксис Python `re`, валидируется перед сохранением — в примере плейсхолдера `\b\d{12}\b`), Тип токена — **закрытый выпадающий список из 5 значений**: `PERSON`, `PROJECT`, `COMPANY`, `PRODUCT`, `CUSTOM`.

Ниже таблица уже добавленных паттернов: Название, Паттерн, Тип токена, Статус (активен/откл.), Добавлен (дата), действия «Изменить» / «Откл.» / «Удалить». На практике (17.08.2026) добавлены и подтверждены активными оба паттерна из [`instrukciya-novye-atributy-maskirovaniya-otchet-brokera.md`](instrukciya-novye-atributy-maskirovaniya-otchet-brokera.md) — «Номер договора / брокерский-лицевой счёт (Д8)» и «Номер лицензии брокера (Д8)», тип токена `CUSTOM` у обоих.

**Найден встроенный тест одного паттерна.** По кнопке «Изменить» у строки паттерна разворачивается инлайн-форма редактирования с дополнительным полем **«Тестовый текст»** и кнопкой **«Проверить»** — точечная проверка именно этого паттерна на введённом тексте, без похода на отдельный экран «Тест детекции»/«Тест-площадка: блэклист». Это, вероятно, самый прямой способ проверить конкретный regex-паттерн — важно только вводить в это поле реальный пример текста (например `ВР33431`), а не сам паттерн: подстановка regex-синтаксиса как тестового текста закономерно даёт «Совпадений не найдено» и ничего не говорит о работоспособности паттерна.

На практике (17.08.2026) в оба поля «Тестовый текст» была вставлена копия самого regex-паттерна вместо примера реальных данных — оба теста закономерно вернули «Совпадений не найдено». Тестирование настоящим примером (`ВР33431`, `045-07514-100000`) ещё предстоит.

Это не текстовое поле и не совпадает с 20 встроенными `PIIType` из документа разработчика (там нет `PROJECT`/`PRODUCT`, `ORG`/`COMPANY` — разные имена типа). `CUSTOM`, судя по всему, — общий catch-all для всего, что не подпадает под первые четыре категории; отдельного, узнаваемого префикса маски под конкретный кастомный атрибут (типа `[CONTRACT_N]`) через этот экран завести нельзя — только общий `[CUSTOM_N]`.

Механика (из подсказки «Как это работает»): паттерны хранятся в таблице `custom_patterns` и выдаются `pii-shield` через `GET /api/v1/shield-config`; `pii-shield` поллит этот endpoint каждые N секунд (интервал — `PII_CATALOG_BLACKLIST_SYNC_INTERVAL`) и применяет паттерны в своём `RegexDetector`.

Остаётся не до конца ясным (см. реестр открытых вопросов): это самостоятельный, более простой механизм, чем `CustomPIIType` из документа разработчика (`id`/`prefix`/`display_name`/валидатор через `config.py`), или упрощённая UI-надстройка над тем же самым, где `prefix` в этом конкретном развёртывании зафиксирован пятью значениями.

## Управление базой (коммерческой тайны)

Статистика (на момент снимка все нули): активных чанков, всего чанков (вкл. архив), негативных примеров. Конфигурация: основная коллекция `confidential_chunks`, коллекция негативов `negative_examples`, путь к данным Qdrant `./data/qdrant`, порог PASS `0.75`, порог BLOCK `0.88` — те же значения, что и в «Тест детекции» выше.

«Опасная зона»: полный необратимый сброс коллекции (секреты, негативы или обе сразу), подтверждение — ввод слова «УДАЛИТЬ». После сброса требуется заново запустить bootstrap или загрузить документы.

## Интеграция (токены)

Управление токенами, которыми `pii-shield` авторизуется при вызове `POST /api/v1/check` — через заголовок `X-Internal-Token`. Форма создания токена (название для идентификации, например `pii-shield-prod`), таблица активных токенов (название, значение токена, дата создания, кнопка «Отозвать» — независимый отзыв на каждый токен).

Инструкция «Как подключить pii-shield»:
1. Создать токен, скопировать значение.
2. В `pii-shield` указать токен — либо переменной окружения `DLP_INTERNAL_TOKEN=...`, либо в тестовом чате: sidebar → DLP Integration → Internal token.
3. Указать endpoint `DLP_ENDPOINT=http://localhost:8000`.
4. Включить DLP: `DLP_ENABLED=true`.

Это прямое подтверждение архитектуры из документа разработчика: `dlp-secret` (политика секретности PASS/REVIEW/BLOCK) — отдельный сервис от `pii-shield` (детекция PII), связаны через этот internal-токен и HTTP-вызов, а не общий процесс.
