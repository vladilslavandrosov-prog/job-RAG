# Инструкция: домены и распределение доступа

Практическая инструкция для администратора: как создать домен, как создать коллекцию документов и привязать её к домену, и — самое важное — как реально дать команде или пользователю доступ к данным домена. Составлено и проверено по живому интерфейсу платформы.

## Схема действий

1. **Домен** — создать в Каталоге (раздел 2).
2. **Коллекция** — привязать к домену (раздел 3).
3. **Пользователь / команда** — назначить домен + роль `Domain Only Access Role` (раздел 4).
4. **Результат** — пользователь видит только данные своего домена; без назначенного домена — только объекты, у которых тоже не задан домен.

Шаги 1–3 выполняет администратор; шаг «Результат» стоит проверить от лица самого пользователя. Владельцы/Эксперты домена, Персона пользователя и роли раздела «Контроль доступа» в эту цепочку не входят — это отдельные, governance-механизмы (раздел 5).

## 1. Что такое домен

**Домен** — тематическая область данных компании (например, «Инвестиции», «Производство», «Кадры»). Домен решает две задачи одновременно:

- группирует данные и документы по смыслу — какие таблицы, отчёты и коллекции относятся к этой области;
- служит границей доступа — определяет, каким командам и пользователям эта область данных видна.

## 2. Как создать домен

**Путь:** Каталог → **Data Marketplace** → **Домены** → «+ Добавить Домен».

Форма:

| Поле | Обязательно | Что это |
|---|---|---|
| Наименование | Да | Название домена |
| Отображаемое имя | Нет | Как домен называется в интерфейсе, если отличается от наименования |
| Описание | Да | Форматированный текст — назначение домена |
| Теги | Нет | Произвольные метки |
| Термины глоссария | Нет | Связь домена с деловыми терминами компании |
| Тип домена | Да | Закрытый список — см. ниже |
| Владельцы | Нет | Пользователи **или целая команда** — кто отвечает за домен |
| Эксперты | Нет | Пользователи — к кому обращаться по содержанию домена |

**Тип домена** — один из трёх:

- **Source-aligned** — домен привязан к конкретному источнику данных (например, к одной учётной системе).
- **Consumer-aligned** — домен ориентирован на конкретного потребителя данных (подразделение, направление бизнеса).
- **Aggregate** — домен объединяет данные нескольких источников или направлений.

После заполнения — «Сохранить». Домен появляется в общем списке доменов.

> **Важно.** Поля «Владельцы» и «Эксперты» на этом шаге — это **не выдача доступа к данным**, а организационная информация (кто отвечает за домен, к кому обращаться). Реальный доступ к данным домена настраивается отдельно — раздел 4.

## 3. Как создать коллекцию документов и привязать её к домену

**Путь:** Администрирование → Платформа → Коллекции → «Создать коллекцию».

### Основные поля

| Поле | Обязательно | Что это |
|---|---|---|
| Идентификатор коллекции | Да | Технический код, формат `namespace_doc_type`, только латиница/цифры/`_`/`-`. **Нельзя изменить после создания.** |
| Отображаемое название | Да | Название в интерфейсе |
| Домен | Да | Текстовая метка домена (например, `hr`, `finance`). **Нельзя изменить после создания.** |
| Бизнес-домен(ы) ОМ | Нет | Привязка к домену, созданному в разделе 2 (можно выбрать несколько). **Нельзя изменить после создания.** |
| Тип документа | Да | Например, «Регламент» |
| Тип коллекции | Да | Текстовые документы / кодовая коллекция. **Нельзя изменить после создания.** |
| Назначение | Нет | «Обычные документы» или «Библиотека шаблонов» (образцы для сборки документов по шаблону) |
| Описание | Нет | Свободный текст |

> **Частая ошибка.** «Домен» и «Бизнес-домен(ы) ОМ» — два независимых поля, оба обязательно нужно заполнить по отдельности. Выбор домена из списка «Бизнес-домен(ы) ОМ» **не заполняет** текстовое поле «Домен» автоматически — форма не даст сохранить коллекцию, если оно пустое.

Выбранный «Бизнес-домен ОМ» становится частью технического идентификатора коллекции в поиске (например, домен «Инвестиции» → идентификатор коллекции вида `ns_Инвестиции.<код коллекции>`).

Технические поля (эмбеддинги, разбивка на чанки, параметры поиска) заполняются один раз при создании и в норме не требуют ручной настройки — платформа подставляет рабочие значения по умолчанию; их смена после создания требует переиндексации коллекции.

После сохранения — коллекция активна, готова к загрузке документов (раздел «Документы» — см. руководство администратора).

## 4. Как реально дать команде или пользователю доступ к домену

Это ключевой раздел — здесь описан рабочий, проверенный на практике механизм.

### Шаг 1 — назначить домен

Домен можно назначить двумя способами — выбирайте по ситуации:

- **Пользователю индивидуально:** Каталог → Настройки → Команды и пользователи → Пользователи → карточка пользователя → блок «Домены» → выбрать домен(ы) из списка.
- **Команде целиком:** Настройки → Команды и пользователи → Команды → карточка команды → блок «Домены» → выбрать домен(ы) из списка. Все участники команды наследуют назначенные домены автоматически.

### Шаг 2 — назначить роль «Domain Only Access Role»

Одного назначения домена на шаге 1 **недостаточно**. Чтобы домен реально ограничивал видимые данные, пользователю (или его команде) дополнительно нужна роль **«Domain Only Access Role»** — тот же блок «Роли» на карточке пользователя или команды.

Без этой роли пользователь продолжает работать по своей базовой роли (например, «Data Consumer»), а назначенный домен ничего не ограничивает и не расширяет сам по себе.

**Точная логика роли** (техническое имя `DomainOnlyAccessRole`, через политику `Domain Only Access Policy`): «Если у пользователя назначен домен — он получает доступ только к данным этого домена. Если пользователю не назначен ни один домен — он получает доступ только к тем объектам, у которых тоже не задан домен» (дословный перевод описания политики). То есть у роли нет «режима по умолчанию — видно всё»: без домена доступны только объекты без домена, а не общий доступ.

### Практический пример

Пользователю назначен домен «Инвестиции» и роли «Data Consumer» + «Domain Only Access Role». Результат: пользователь видит только данные и коллекции, отнесённые к домену «Инвестиции» — данные других доменов (например, «Производство») ему не видны.

## 5. Что НЕ даёт доступа — частые заблуждения

| Механизм | Где находится | Что реально делает |
|---|---|---|
| Владельцы / Эксперты домена | Карточка домена (раздел 2) | Организационная информация — кто отвечает за домен. Доступа не даёт. |
| Персона пользователя | Карточка пользователя | Настраивает стиль и тон ответов ассистента в чате. К доступу отношения не имеет. |
| Роли и политики в «Контроль доступа» | Настройки → Контроль доступа → Роли / Политики | Права на **редактирование метаданных каталога** (описания, теги, владельцы объектов) — то есть кто может курировать сам каталог, а не кто что видит в чате. |

Реальный доступ к данным домена в чате и поиске задаётся только связкой **«Домен на профиле/команде» + «Роль Domain Only Access Role»** (раздел 4).

> **Персону нельзя привязать к домену или к каталогу вообще — ни на форме создания, ни в дальнейших настройках.** У самой Персоны (Настройки → Персоны → карточка персоны → «Настроить интерфейс») есть только настройка **шаблона страниц** — Навигация, Главная страница, Marketplace, «Руководство» (внутри — Data Product, Domain, Glossary, Glossary Term), Объекты данных. Пункт «Domain» там означает не связь с конкретным доменом, а вид **общей карточки любого домена** (какие вкладки и виджеты видны) для пользователей с этой персоной — не про доступ к данным и не про конкретный домен.

## Глоссарий

- **Домен** — тематическая область данных; одновременно граница доступа.
- **Бизнес-домен ОМ** — привязка коллекции документов к домену каталога.
- **Data Marketplace** — раздел меню Каталога, где находятся Домены и Дата-продукты.
- **Domain Only Access Role** — роль, которая вместе с назначенным доменом ограничивает видимые пользователю данные только этим доменом.
- **Владелец / Эксперт домена** — организационная роль (кто отвечает / к кому обращаться), не связана с техническим доступом.

## Приложение: тест-кейс для заказчика

Готовый сценарий проверки — пройти самостоятельно на пилотном контуре, чтобы убедиться, как именно связка «домен + роль» влияет на то, что реально видно в чате, а не только в самом Каталоге. Пример собран на основе тестового отчёта брокера (тот же документ, что использовался в проверке маскирования персональных данных).

### Предусловия

- Тестовый файл — отчёт брокера (например, «Вариант 2» из инструкции по маскированию), без реальных данных клиентов.
- Права администратора для создания домена, коллекции и тестового пользователя.

### Шаг A — подготовка

1. Создать домен **«Брокерская отчётность (тест)»** (Тип домена: Source-aligned).
2. Создать коллекцию **«Тест — отчёты брокера»**: Домен — `broker_report_test`, Бизнес-домен(ы) ОМ — «Брокерская отчётность (тест)», Тип документа — «Отчёт», Тип коллекции — «Текстовые документы».
3. Загрузить тестовый отчёт брокера в коллекцию через раздел «Документы».
4. Создать тестового пользователя `test_domain_check` — с доменом «Брокерская отчётность (тест)» и ролью «Domain Only Access Role».

### Шаг B — контрольная проверка «до»

5. Войти в чат под `test_domain_check`, спросить что-то по содержимому отчёта (например: «какая сумма сделки указана в отчёте»).
6. **Ожидаемый результат:** ассистент находит документ и отвечает по нему — коллекция доступна.

### Шаг C — создать ещё один домен и ещё одну коллекцию

7. Аналогично шагу A создать ещё один домен, ещё одну коллекцию и загрузить ещё один документ (по какой-либо другой теме, все наименования и документы должны отличаться, например «Кадры (тест)»).
8. Открыть новый чат под `test_domain_check` и задать вопрос уже по новому документу. **Ожидаемый результат:** сообщение о том, что информация по доступным источникам не найдена.

### Шаг D — настроить доступ ко второму домену

9. Добавить пользователю `test_domain_check` доступ ко второму созданному домену.
10. Открыть новый чат под `test_domain_check` и снова задать вопрос по новому документу из второй коллекции. **Ожидаемый результат:** ассистент находит документ и отвечает по нему — коллекция доступна.

### Уборка после теста

Деактивировать тестовую коллекцию (кнопка «Деактивировать»), заблокировать тестового пользователя (не удалять — для сохранения аудиторского следа), при необходимости — удалить тестовый домен.
