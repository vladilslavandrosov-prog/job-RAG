Подключение внешнего клиента к MCP Gateway

Часть I — для интегратора внешней системы (вендора). Часть II — для администратора ИБ, который заводит этот доступ.

Вендору передаётся только Часть I

Часть II содержит внутренние детали стенда — имена служебных скриптов и команды к контейнерам. Для отправки наружу используйте отдельную выгрузку клиентской части.

Часть I

Для интегратора внешней системы

Кому: интегратору внешней агентской системы, которому служба информационной безопасности заказчика выдала доступ к платформе через MCP.

Что это. Платформа отдаёт свои инструменты — поиск по каталогу, запросы к данным, документы — как MCP-сервер. Ваш агент или LLM-хост подключается к нему по стандартному MCP поверх HTTP и вызывает разрешённые вам инструменты.

Данные режутся по вашей персоне

По доменам и правам на строки. Вы видите только то, что вам выделено, независимо от того, какой запрос отправили.

01 Что вам выдаёт администратор ИБ

ЧтоПояснение
URL шлюзаНапример https://<gateway> — тот же хост, что и для completions
client_id / client_secretВыдаются один раз при одобрении заявки (dual-control). Хранить как пароль
Namespace (aud)data__ — инструменты данных (запросы, каталог) и/или om__. Токен привязан к одному namespace
Домены и коллекции персоныНе всегда сообщаются явно. Определяют, к каким данным будет доступ

Набор инструментов задаёт ИБ по вашей персоне

В ответе tools/list придут только разрешённые — по умолчанию не выдаётся ничего. Пустой список — не ошибка подключения (см. §4).

client_secret выдаётся один раз

Повторно его не покажут — при утере потребуется ротация через ИБ. Храните как пароль: в защищённом хранилище, не в репозитории и не в конфигурации, попадающей в логи.

02 Получение токена

OAuth 2.0, grant client_credentials с указанием ресурса (RFC 8707):

curl -s -X POST https://<gateway>/oauth/token \
  -d grant_type=client_credentials \
  -d client_id=<client_id> \
  -d client_secret=<client_secret> \
  -d resource=data__  # запрашиваемый namespace (aud)

# → { "access_token": "pii_ses_...", "token_type": "Bearer", "expires_in": 900 }
  • Время жизни токена: data__ — 900 секунд, остальные namespace — 1800. Кэшируйте токен до expires_in.
  • Один токен — один namespace. Нужен доступ и к data__, и к om__ — берите два токена.
  • Аутентификация клиента: client_secret_post либо заголовок Authorization: Basic base64(client_id:client_secret).
  • Автонастройка: OAuth-дискавери через /.well-known/oauth-authorization-server и /.well-known/oauth-protected-resource.

03 Подключение MCP-клиента

Транспорт — Streamable HTTP, эндпоинт — /mcp, авторизация — заголовок Authorization: Bearer <access_token>.

Конфигурация типового MCP-клиента

{
  "mcpServers": {
    "synapse": {
      "type": "streamable-http",
      "url": "https://<gateway>/mcp",
      "headers": { "Authorization": "Bearer pii_ses_..." }
    }
  }
}

Проверка вручную (JSON-RPC поверх HTTP)

Список доступных вам инструментов:

TOKEN=pii_ses_...
curl -s https://<gateway>/mcp -H "Authorization: Bearer $TOKEN" \
  -H 'Content-Type: application/json' \
  -H 'Accept: application/json, text/event-stream' \
  -d '{"jsonrpc":"2.0","id":1,"method":"tools/list"}'

Вызов инструмента — запрос к данным на естественном языке:

curl -s https://<gateway>/mcp -H "Authorization: Bearer $TOKEN" \
  -H 'Content-Type: application/json' \
  -H 'Accept: application/json, text/event-stream' \
  -d '{"jsonrpc":"2.0","id":2,"method":"tools/call",
       "params":{"name":"data__query_data",
       "arguments":{"question":"сколько сделок за июль"}}}'

Имя инструмента — из ответа tools/list

Оно уже включает ваш namespace, например data__query_data или data__run_sql_query. Инструмент run_sql_query возвращает только строки, разрешённые вашей персоне.

04 Ошибки

ОтветПричинаЧто делать
invalid_clientНеверный секрет, клиент не активен или истёк период ротацииПроверить учётные данные; при ротации — обновить секрет в grace-окне (36 часов)

Пустой tools/listПерсоне не назначены инструментыЗапросить у ИБ видимость нужных инструментов

05 Жизненный цикл доступа

  • Ротация секрета — по инициативе ИБ. Новый активен сразу, старый работает ещё 36 часов.
  • Отзыв доступа — немедленно для новых токенов; выданный токен перестаёт работать в пределах 30 секунд.

Планируйте обработку ротации заранее

Если секрет зашит в конфигурацию, которую нельзя обновить за 36 часов, интеграция остановится. Читайте секрет из хранилища без пересборки и повторно запрашивайте токен при ответе invalid_client.

06 Чеклист подключения

  • Получены URL шлюза, client_id, client_secret и список разрешённых namespace.
  • Секрет положен в защищённое хранилище, не в репозиторий.
  • Токен получен на нужный resource; при необходимости — два токена.
  • Реализовано кэширование токена до expires_in и повторное получение по истечении.
  • tools/list возвращает непустой список, состав согласован с ИБ.
  • Пробный tools/call выполнен успешно.
  • Предусмотрено обновление секрета в 36-часовом окне ротации.
  • Обработаны ответы invalid_client, invalid_target, access_denied.

Часть II · внутреннее, не для вендора

Для администратора ИБ — заведение доступа

Кому: администратору ИБ. Порядок: предпосылки в OpenMetadata → регистрация клиента в рабочем месте ИБ → проверка.

Ключ вендора маппится на одну org-scoped персону OM и на om_user_email — учётную запись, которую нужно имперсонировать. При выдаче токена pii-shield имперсонирует этого пользователя через OM (persona-select-service), и в токен зашиваются домены и RLS-фильтры персоны.

Разница — только в ключе

Никакого отдельного контура для вендора нет: всё разграничение делает персона, как для обычного пользователя.

07 Регистрация клиента (dual-control)

Путь: «Рабочее место ИБ» → «Внешние агентские системы» → «+ Заявка».

ПолеЧто указывать
Вендор, НазначениеСвободный текст — нужен для аудита
Персона (persona_id)Граница доступа: домены и RLS. Список тянется из персон OM
om_user_emailКого имперсонировать. Выпадающий список пользователей OM, боты первыми
Ресурсы (resources)Namespace aud: data__ и/или om__. Один namespace на выдачу
Требуется маскировка ПДнФлажок, по умолчанию включён

Флажок «Требуется маскировка ПДн»

СостояниеЧто получает клиентКогда уместно
Включён (по умолчанию)Обезличенные данные — плейсхолдеры вместо значенийВсегда, если нет причин для обратного
СнятРеальные персональные данные; маскировка — позже, на выходе к моделиТолько доверенный клиент, чей путь к модели идёт через платформу

Не снимайте флажок, если модель вызывается мимо платформы

Иначе инструменты отдадут реальные ПДн, и они уйдут во внешнюю модель без обезличивания. Снимайте только убедившись, что путь клиента к модели проходит через /completions платформы — и зафиксируйте это решение в заявке.

После сохранения заявка получает статус pending. Администратор открывает карточку и нажимает «Одобрить» — генерируется client_secret (в реестре хранится PBKDF2-хеш, открытое значение показывается один раз), статус меняется на active.

Открытый секрет показывается один раз

Если карточку закрыли, не скопировав значение, потребуется ротация. Готовьте защищённый канал передачи до нажатия «Одобрить».

08 Проверка перед передачей вендору

а) Имперсонация выпускает токен — ожидаем HTTP 200 и accessToken:

docker exec <om> curl -s -X POST \
  http://localhost:8585/api/v1/users/persona-select-service \
  -H "Authorization: Bearer <impersonation-bot>" \
  -H "Content-Type: application/json" \
  -w "HTTP %{http_code}" \
  -d '{"userEmail":"<om_user_email>","personaId":"<persona_id>"}'

б) проверка tools/list и tools/call под выданным токеном (см. §3).

На стендах с LDAP

Правка флагов бота имперсонации может конфликтовать с настройками платформенного бота — проверьте его флаги до правки.

Чеклист заведения клиента

  • Поле dataAccessPolicy зарегистрировано для типов user и persona.
  • Учётная запись om_user_email существует, нужная персона назначена.
  • У бота имперсонации выставлены isBot и allowImpersonation.
  • Персоне клиента отмечены нужные инструменты данных в политиках инструментов.
  • Заявка заведена, поля вендора и назначения заполнены для аудита.
  • Защищённый канал передачи готов до нажатия «Одобрить».
  • Проверка (а) — HTTP 200, проверка (б) — непустой tools/list и успешный вызов.
  • Вендору передана только клиентская часть документа (Часть I).
