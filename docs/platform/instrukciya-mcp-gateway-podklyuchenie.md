# Подключение внешнего клиента к MCP Gateway

Документ состоит из двух частей: **Часть I** — для интегратора внешней системы (вендора), **Часть II** — для администратора ИБ, который заводит этот доступ. Составлено на основе документа разработчика.

> **Вендору передаётся только Часть I.** Часть II содержит внутренние детали стенда — имена служебных скриптов и команды к контейнерам. Для отправки наружу используйте отдельную выгрузку клиентской части (только Часть I этого документа).

## Часть I. Для интегратора внешней системы

**Кому:** интегратору внешней агентской системы, которому служба информационной безопасности заказчика выдала доступ к платформе через MCP.

**Что это.** Платформа отдаёт свои инструменты — поиск по каталогу, запросы к данным, документы — как **MCP-сервер**. Ваш агент или LLM-хост подключается к нему по стандартному MCP поверх HTTP и вызывает разрешённые вам инструменты.

> **Данные режутся по вашей персоне** — по доменам и правам на строки. Вы видите только то, что вам выделено, независимо от того, какой запрос отправили.

### 1. Что вам выдаёт администратор ИБ

| Что | Пояснение |
|---|---|
| URL шлюза | Например `https://<gateway>` — тот же хост, что и для completions |
| `client_id` и `client_secret` | Выдаются один раз при одобрении заявки (dual-control). Хранить как пароль |
| Разрешённый namespace (aud) | `data__` — инструменты данных (запросы, каталог) и/или `om__`. Токен привязан к одному namespace |
| Домены и коллекции персоны | Не всегда сообщаются явно. Определяют, к каким данным будет доступ |

> **Набор инструментов задаёт ИБ по вашей персоне.** В ответе `tools/list` придут только разрешённые — по умолчанию не выдаётся ничего. Если список пуст, это не ошибка подключения (см. §4).
>
> **`client_secret` выдаётся один раз.** Повторно его не покажут — при утере потребуется ротация через ИБ. Храните секрет как пароль: в защищённом хранилище, не в репозитории и не в конфигурации, попадающей в логи.

### 2. Получение токена

OAuth 2.0, grant `client_credentials` с указанием ресурса (RFC 8707):

```
curl -s -X POST https://<gateway>/oauth/token \
  -d grant_type=client_credentials \
  -d client_id=<client_id> \
  -d client_secret=<client_secret> \
  -d resource=data__ # запрашиваемый namespace (aud); один из разрешённых вам

# → { "access_token": "pii_ses_...", "token_type": "Bearer", "expires_in": 900 }
```

- **Время жизни токена:** `data__` — 900 секунд, остальные namespace — 1800. По истечении запросите токен заново; кэшируйте его до `expires_in`.
- **Один токен — один namespace.** Нужен доступ и к `data__`, и к `om__` — берите два токена и используйте каждый со своим набором инструментов.
- **Аутентификация клиента:** `client_secret_post` (как в примере выше) либо заголовок `Authorization: Basic base64(client_id:client_secret)`.
- **Автонастройка:** если ваш MCP-клиент умеет OAuth-дискавери, используйте `GET https://<gateway>/.well-known/oauth-authorization-server` и `/.well-known/oauth-protected-resource`.

### 3. Подключение MCP-клиента

Транспорт — **Streamable HTTP**, эндпоинт — `/mcp`, авторизация — заголовок `Authorization: Bearer <access_token>`.

**Конфигурация типового MCP-клиента:**

```json
{
  "mcpServers": {
    "synapse": {
      "type": "streamable-http",
      "url": "https://<gateway>/mcp",
      "headers": { "Authorization": "Bearer pii_ses_..." }
    }
  }
}
```

**Проверка вручную (JSON-RPC поверх HTTP).** Список доступных вам инструментов:

```
TOKEN=pii_ses_...
curl -s https://<gateway>/mcp -H "Authorization: Bearer $TOKEN" \
  -H 'Content-Type: application/json' \
  -H 'Accept: application/json, text/event-stream' \
  -d '{"jsonrpc":"2.0","id":1,"method":"tools/list"}'
```

Вызов инструмента — на примере запроса к данным на естественном языке:

```
curl -s https://<gateway>/mcp -H "Authorization: Bearer $TOKEN" \
  -H 'Content-Type: application/json' \
  -H 'Accept: application/json, text/event-stream' \
  -d '{"jsonrpc":"2.0","id":2,"method":"tools/call",
       "params":{"name":"data__query_data",
       "arguments":{"question":"сколько сделок за июль"}}}'
```

> Имя инструмента в `tools/call` берите из ответа `tools/list` — оно уже включает ваш namespace, например `data__query_data` или `data__run_sql_query`. Инструмент `run_sql_query` возвращает только строки, разрешённые вашей персоне.

### 4. Ошибки

| Ответ | Причина | Что делать |
|---|---|---|
| `invalid_client` на `/oauth/token` | Неверный секрет, клиент не активен или истёк период ротации | Проверить учётные данные; при ротации — обновить секрет в течение grace-окна (36 часов) |
| `invalid_target` при вызове | Токен выдан под другой `aud` | Получить токен с нужным `resource=<namespace>` |
| `access_denied` | Клиент отозван либо сбой резолвера — режим fail-closed | Обратиться в службу ИБ заказчика |
| Пустой `tools/list` | Персоне не назначены инструменты | Запросить у ИБ видимость нужных инструментов |

### 5. Жизненный цикл доступа

- **Ротация секрета** — по инициативе ИБ. Новый секрет активен сразу, старый продолжает работать **36 часов**. За это время нужно обновить конфигурацию.
- **Отзыв доступа** — немедленно для новых токенов; уже выданный токен перестаёт работать в пределах 30 секунд.

> **Планируйте обработку ротации заранее.** Если секрет зашит в конфигурацию, которую нельзя обновить за 36 часов, интеграция остановится. Предусмотрите чтение секрета из хранилища без пересборки и повторное получение токена при ответе `invalid_client`.

### 6. Чеклист подключения

- [ ] Получены URL шлюза, `client_id`, `client_secret` и список разрешённых namespace.
- [ ] Секрет положен в защищённое хранилище, не в репозиторий.
- [ ] Токен получен на нужный `resource`; при необходимости получены два токена.
- [ ] Реализовано кэширование токена до `expires_in` и повторное получение по истечении.
- [ ] `tools/list` возвращает непустой список — состав соответствует согласованному с ИБ.
- [ ] Пробный `tools/call` выполнен успешно.
- [ ] Предусмотрено обновление секрета в течение 36-часового окна ротации.
- [ ] Обработаны ответы `invalid_client`, `invalid_target` и `access_denied`.

## Часть II. Для администратора ИБ — заведение доступа

*Внутренний раздел — не передавать вендору.*

**Кому:** администратору ИБ, который заводит внешнему вендору доступ к MCP. Порядок: сначала предпосылки в OpenMetadata — без них токен не выпустится или список инструментов придёт пустым, — затем регистрация клиента в рабочем месте ИБ, затем проверка.

### Как это устроено

Ключ вендора маппится на **одну org-scoped персону** OM и на `om_user_email` — учётную запись, которую нужно имперсонировать. При выдаче токена pii-shield имперсонирует этого пользователя через OM (persona-select-service), и в токен зашиваются домены и RLS-фильтры персоны. Данные режутся так же, как обычному пользователю; набор инструментов определяется видимостью персоны в реестре инструментов.

> Различие между внутренним и внешним потребителем — только в ключе. Никакого отдельного контура для вендора нет: всё разграничение делает персона.

### Шаг 1. Регистрация клиента (dual-control)

**Рабочее место ИБ → Внешние агентские системы → «+ Заявка».**

Поля:

| Поле | Что указывать |
|---|---|
| Вендор, Назначение | Свободный текст — нужен для аудита |
| Персона (`persona_id`) | Граница доступа: домены и RLS. Список тянется из персон OM |
| `om_user_email` | Кого имперсонировать. Выпадающий список пользователей OM, боты первыми |
| Ресурсы (`resources`) | Namespace aud: `data__` (запросы, каталог) и/или `om__`. Токен привязан к **одному** namespace на выдачу |
| Домены, Scopes, Владелец | Необязательные поля |
| Требуется маскировка ПДн | Флажок, по умолчанию **включён**. Определяет, приходят ли клиенту обезличенные данные |

#### Флажок «Требуется маскировка ПДн»

Тот же признак, что и флаг у провайдера модели, но заданный на уровне клиента. По умолчанию включён — в общем случае так и оставляйте.

| Состояние | Что получает клиент | Когда уместно |
|---|---|---|
| Включён (по умолчанию) | Инструменты возвращают обезличенные данные — вместо реальных значений плейсхолдеры | Всегда, если нет причин для обратного |
| Снят | Инструменты возвращают реальные персональные данные; маскировка происходит позже, на выходе к модели | Только для доверенного клиента, чей путь к модели идёт через платформу |

**Зачем это нужно.** Если у клиента два независимых подключения — например, в n8n отдельная LLM-нода и отдельный MCP-клиент, — то маска, наложенная при вызове инструмента, не раскроется в ответе модели: это разные сессии обезличивания, и пользователь увидит в результате `[PERSON_1]` вместо значения. Снятие флажка устраняет проблему, потому что обезличивание переносится на единственный выход к модели.

> **Не снимайте флажок, если модель клиента вызывается мимо платформы.** В этом случае инструменты отдадут реальные персональные данные, и они уйдут во внешнюю модель без обезличивания. Прежде чем снять флажок, убедитесь, что путь клиента к модели проходит через `/completions` платформы, и зафиксируйте это решение в назначении заявки.

После сохранения заявка получает статус **pending**.

1. Администратор ИБ открывает карточку и нажимает «Одобрить». Генерируется `client_secret`: в реестре хранится PBKDF2-хеш, открытое значение показывается один раз.
2. Статус меняется на **active**.
3. Передайте вендору защищённым каналом: URL шлюза, `client_id`, `client_secret` и разрешённый namespace `aud`. Дальше вендор действует по Части I.

> **Открытый секрет показывается один раз.** Если карточку закрыли, не скопировав значение, потребуется ротация. Готовьте защищённый канал передачи до того, как нажмёте «Одобрить».

### Шаг 2. Проверка перед передачей вендору

**а) Имперсонация выпускает токен** — ожидаем HTTP 200 и `accessToken`:

```
docker exec <om> curl -s -X POST \
  http://localhost:8585/api/v1/users/persona-select-service \
  -H "Authorization: Bearer <impersonation-bot>" \
  -H "Content-Type: application/json" \
  -w "HTTP %{http_code}" \
  -d '{"userEmail":"<om_user_email>","personaId":"<persona_id>"}'
```

**б)** проверка `tools/list` и `tools/call` под выданным токеном (см. Часть I, §3).

Ожидаемый результат: в пункте (а) — HTTP 200; в пункте (б) — непустой `tools/list`, все инструменты в namespace `data__`, и успешный `tools/call`.

### Шаг 0. Возможные ошибки

*(Диагностика ниже ссылается на эти пункты как 0.1–0.3.)*

#### 0.1. Учётная запись `om_user_email` существует, и ей назначена персона

- **Симптомы:** несуществующий адрес → 404 `user not found`; персона не назначена → 400 `PERSONA_NOT_ASSIGNED`.
- **Проверка:** `GET /api/v1/users?fields=personas` — у нужного пользователя персона должна быть в списке.

#### 0.2. Бот имперсонации имеет флаги `isBot` и `allowImpersonation`

- Речь о боте из `OM_SERVICE_TOKEN` сервиса pii-shield.
- **Симптом:** persona-select-service отвечает 403 `requires a bot with allowImpersonation=true`.
- **Фикс (одноразовый):** `PATCH /api/v1/users/<bot_id>` с json-patch `add /allowImpersonation=true`; добавьте `/isAdmin=true`, если тот же бот правит типы.

> На стендах с LDAP этот пункт может конфликтовать с настройками платформенного бота — проверьте его флаги до правки.

#### 0.3. Персоне клиента проставлена видимость нужных инструментов данных

- **Симптом:** `tools/list` пустой.
- Мета-инструменты (`list_personas`, `select_persona`, `security_alert`) внешнему клиенту скрыты намеренно.
- Инструменты данных вида `data__run_sql_query` отдаются, только если персона входит в `personas_allowed` инструмента **и** у инструмента `review_state = reviewed`. Режим fail-closed.
- **Где настроить:** Рабочее место ИБ → Политики инструментов — отметить нужные инструменты для персоны клиента.

### Диагностика

| Симптом | Причина | Что делать |
|---|---|---|
| 404 `user ... not found` | Неверный `om_user_email` | См. §0.1 |
| 400 `PERSONA_NOT_ASSIGNED` | Персона не назначена пользователю | См. §0.1 — назначить персону |
| 403 `requires a bot with allowImpersonation` | У бота нет нужного флага | См. §0.2 |
| `tools/list` пуст | Персона без видимости инструментов данных | См. §0.3 — политики инструментов |
| `invalid_target` при вызове | Токен выдан под другой `aud` | Взять токен с нужным `resource=` |
| `access_denied` | Клиент отозван либо резолвер недоступен (fail-closed) | Проверить статус клиента в карточке |

### Чеклист заведения клиента

- [ ] Поле `dataAccessPolicy` зарегистрировано для типов `user` и `persona` (после последнего ре-бутстрапа OM тоже).
- [ ] Учётная запись `om_user_email` существует, нужная персона ей назначена.
- [ ] У бота имперсонации выставлены `isBot` и `allowImpersonation`.
- [ ] Персоне клиента отмечены нужные инструменты данных в политиках инструментов.
- [ ] Заявка заведена, поля вендора и назначения заполнены для аудита.
- [ ] Защищённый канал передачи готов **до** нажатия «Одобрить».
- [ ] Проверка (а) вернула HTTP 200, проверка (б) — непустой `tools/list` и успешный вызов.
- [ ] Вендору передана только клиентская часть документа (Часть I).

Ротация секрета и отзыв доступа выполняются в карточке клиента; порядок действий вендора при этом описан в Части I, §5.
