# Инструкция: добавить новые атрибуты маскирования для отчёта брокера (Вариант 2)

Практический шаг от разбора «Вариант 2» ([`primer-podhoda-maskirovaniya-otchet-brokera.html`](../analysis/primer-podhoda-maskirovaniya-otchet-brokera.html)) к реальному экрану платформы. Что делать в системе, чтобы номер договора и номер счёта в отчёте брокера тоже начали скрываться — сейчас это два поля из «7 из 8», которые не покрыты встроенными типами.

## 1. Что именно не покрыто

Из таблицы Вариант 2:

| Поле | Встроенный тип? | Что делать |
|---|---|---|
| ФИО клиента и сотрудников | Да — `PERSON`/`FULL_NAME` | ничего, уже работает |
| Название компании | Да — `ORG` | ничего, уже работает |
| Адрес брокера («г. Москва, Пресненский р-н») | Да — `ADDRESS` (газеттир КЛАДР/ФИАС) | ничего, уже работает — только убедиться, что `ADDRESS_GAZETTEER_ENABLED=true` |
| **Номер договора / брокерский / лицевой счёт** | **Нет** | завести кастомный regex-паттерн (ниже) |
| **Номер лицензии брокера** | **Нет** | завести отдельный кастомный regex-паттерн (ниже) |

Номер договора и оба счёта в тестовых данных — один и тот же формат («ВР33431», «ВР33431-МО-01»), поэтому это один паттерн, а не три.

## 2. Где заводить: «База секретов» → «Regex-паттерны»

Экран описан в [`baza-sekretov.md`](baza-sekretov.md#regex-паттерны-пользовательские). Форма: **Название**, **Regex-паттерн** (синтаксис Python `re`, валидируется перед сохранением), **Тип токена** (выпадающий список).

## 3. Конкретные значения для формы

**Паттерн 1 — номер договора / брокерский / лицевой счёт**

| Поле формы | Значение |
|---|---|
| Название | `Номер договора / брокерский-лицевой счёт (Д8)` |
| Regex-паттерн | `\b[А-Я]{2}\d{4,6}(?:-[А-Я]{2}-\d{1,3})?\b` |
| Тип токена | см. п. 4 ниже |

Проверено на примерах: `ВР33431` → совпадение, `ВР33431-МО-01` → совпадение. Ложных срабатываний на соседних полях того же отчёта не даёт: баланс (`16 634,88`), дата (`24.09.2019`), код ценной бумаги (`ОФЗ-ПД225`, `RU000A0ZYUB7`) — ни один не матчится.

**Паттерн 2 — номер лицензии брокера**

| Поле формы | Значение |
|---|---|
| Название | `Номер лицензии брокера (Д8)` |
| Regex-паттерн | `№\s?\d{3}-\d{3,6}` |
| Тип токена | см. п. 4 ниже |

Проверено на примере `№ 045-0751` → совпадение. В исходном документе номер обрезан многоточием («045-0751…») — полный формат лицензии стоит уточнить у заказчика перед включением на реальных документах: `\d{3,6}` во втором блоке — предположение с запасом, не факт.

## 4. Открытый вопрос перед вводом — что выбрать в «Тип токена»

Это единственное, что нельзя закрыть без проверки в самой системе (см. [`otkrytye-voprosy.md`](otkrytye-voprosy.md#база-секретов)):

- **Если список открыт для ввода нового значения** — вписать свой код напрямую в форму, например `CONTRACT` (токен маски получится `[CONTRACT_N]`) и `LICENSE` (`[LICENSE_N]`). Это соответствует конфигурации, уже предложенной в `pokrytie-maskirovaniya-perechen-d8.xlsx`, лист «Три слоя маскирования», раздел 4.
- **Если список ограничен только существующими 20 встроенными типами** (в примере на скриншоте был выбран `PERSON`) — через этот экран новый префикс маски завести нельзя, паттерн можно только приклеить к уже существующему типу, что технически некорректно для номера договора (это не ФИО и не организация). В этом случае нужно эскалировать в команду платформы напрямую конфиг `CustomPIIType` в обход UI — см. `pii_shield/config.py:151-200` (описано в [`pii-shield-masking-span-registry.docx`](../sources/pii-shield-masking-span-registry.docx), §2) — и передать им готовые id/prefix/regex из раздела 4 листа «Три слоя маскирования».

Практически: сначала попробовать создать паттерн через UI с новым кодом (`CONTRACT`) — если форма примет, вопрос закрыт. Если нет (ошибка валидации или список строго ограничен) — сразу понятно, что нужен путь через платформенную команду.

## 5. Проверка после добавления

1. «База секретов» → «Тест детекции».
2. Вставить фрагмент реального отчёта или тестовый пример: «Договор № ВР33431 от 24.09.2019. Брокерский / лицевой счёт ВР33431 / ВР33431-МО-01. Лицензия № 045-0751».
3. Убедиться, что номер договора/счёта и номер лицензии заменились на токены (`[CONTRACT_N]`, `[LICENSE_N]` либо на тот тип, что реально принял UI), а дата, баланс, ISIN — нет.
4. Отдельно прогнать через тест кусок с портфелем и балансом («ОФЗ-ПД225 — 1 шт», «16 634,88 ₽») — паттерны выше не должны их зацепить (см. самопроверку в п. 3).
5. Если платформа настроена с ненулевым `PII_CATALOG_BLACKLIST_SYNC_INTERVAL` — `pii-shield` подхватывает новые паттерны не мгновенно, а по опросу `GET /api/v1/shield-config`; если тест сразу не сработал, стоит подождать один цикл синхронизации, прежде чем считать паттерн нерабочим.
