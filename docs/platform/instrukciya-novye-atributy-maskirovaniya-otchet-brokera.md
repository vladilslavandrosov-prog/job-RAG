# Инструкция: добавить новые атрибуты маскирования для отчёта брокера (Вариант 2)

Практический шаг от разбора «Вариант 2» ([`primer-podhoda-maskirovaniya-otchet-brokera.html`](../analysis/primer-podhoda-maskirovaniya-otchet-brokera.html)) к реальному экрану платформы. Что делать в системе, чтобы номер договора и номер счёта в отчёте брокера тоже начали скрываться — сейчас это два поля из «7 из 8», которые не покрыты встроенными типами.

## 1. Что именно не покрыто

Из таблицы Вариант 2:

| Поле | Встроенный тип? | Что делать |
|---|---|---|
| ФИО клиента и сотрудников | Да — `PERSON`/`FULL_NAME` | ничего, уже работает |
| Название компании | Да — `ORG` | ничего, уже работает |
| Адрес брокера («г. Москва, Пресненский р-н») | Да — `ADDRESS` (газеттир КЛАДР/ФИАС) | ничего, уже работает — только убедиться, что `ADDRESS_GAZETTEER_ENABLED=true` |
| **Номер договора / брокерский / лицевой счёт** | **Нет** | завести кастомный regex-паттерн (ниже) |
| **Номер лицензии брокера** | **Нет** | завести отдельный кастомный regex-паттерн (ниже) |

Номер договора и оба счёта в тестовых данных — один и тот же формат («ВР33431», «ВР33431-МО-01»), поэтому это один паттерн, а не три.

## 2. Где заводить: «База секретов» → «Regex-паттерны»

Экран описан в [`baza-sekretov.md`](baza-sekretov.md#regex-паттерны-пользовательские). Форма: **Название**, **Regex-паттерн** (синтаксис Python `re`, валидируется перед сохранением), **Тип токена** (выпадающий список).

## 3. Конкретные значения для формы

**Паттерн 1 — номер договора / брокерский / лицевой счёт**

| Поле формы | Значение |
|---|---|
| Название | `Номер договора / брокерский-лицевой счёт (Д8)` |
| Regex-паттерн | `\b[А-Я]{2}\d{4,6}(?:-[А-Я]{2}-\d{1,3})?\b` |
| Тип токена | см. п. 4 ниже |

Проверено на примерах: `ВР33431` → совпадение, `ВР33431-МО-01` → совпадение. Ложных срабатываний на соседних полях того же отчёта не даёт: баланс (`16 634,88`), дата (`24.09.2019`), код ценной бумаги (`ОФЗ-ПД225`, `RU000A0ZYUB7`) — ни один не матчится.

**Паттерн 2 — номер лицензии брокера**

| Поле формы | Значение |
|---|---|
| Название | `Номер лицензии брокера (Д8)` |
| Regex-паттерн | `№\s?\d{2,3}-\d{4,6}-\d{4,6}` |
| Тип токена | см. п. 4 ниже |

**Формат подтверждён реальным документом** (реквизиты Д8): «Лицензия профессионального участника рынка ценных бумаг на осуществление брокерской деятельности № 045-07514-100000 от 17.03.2004 г., выдана: ФКЦБ России». Полный номер — три группы цифр через дефис (`045-07514-100000`), не две, как предполагалось изначально по обрезанному примеру. Проверено на этом реальном номере → совпадение целиком, без обрезания. Ложных срабатываний на дате выдачи (`17.03.2004`), адресе (`помещ. 1-5`) и номере счёта (`ВР33431-МО-01`) не даёт.

## 4. Что выбрать в «Тип токена» — проверено на скриншоте

Список закрытый (не текстовое поле) и состоит всего из 5 значений: `PERSON`, `PROJECT`, `COMPANY`, `PRODUCT`, `CUSTOM`. Свой префикс (например `CONTRACT`) вписать нельзя.

Ни один из первых четырёх вариантов номеру договора/счёта/лицензии не подходит по смыслу (это не человек, не проект, не компания, не продукт) — значит для обоих паттернов из п. 3 нужно выбрать **`CUSTOM`**.

Важное следствие: маска для обоих атрибутов получится одинаковой по типу — `[CUSTOM_N]`, а не отдельные узнаваемые `[CONTRACT_N]`/`[LICENSE_N]`, как было в первоначальном предложении из раздела 4 листа «Три слоя маскирования». Порядковый номер `N` всё равно будет разным для разных значений (консистентность по `original_text` в рамках сессии сохраняется), но по самому токену в тексте нельзя будет на глаз отличить, что именно скрыто — номер договора это или номер лицензии.

Если это неприемлемо (например, аналитику важно видеть в замаскированном тексте, что перед ним номер счёта, а не что-то другое) — вариант через UI не подходит, и нужно эскалировать в команду платформы прямой конфиг `CustomPIIType` в обход этого экрана: `pii_shield/config.py:151-200` (описано в [`pii-shield-masking-span-registry.docx`](../sources/pii-shield-masking-span-registry.docx), §2), с готовыми id/prefix/regex из раздела 4 листа «Три слоя маскирования». Остаётся не до конца ясным (см. реестр открытых вопросов), совпадает ли этот путь технически с механизмом `custom_patterns` за экраном «Regex-паттерны», или это два разных пути внутри платформы — стоит уточнить у команды платформы напрямую.

## 5. Проверка после добавления

**Статус на 17.08.2026:** паттерн 1 (номер договора/счёта) сохранён на экране «Regex-паттерны» и активен. Паттерн 2 (номер лицензии) в списке не появился — форму нужно заполнить и нажать «Добавить» ещё раз, проверить, что он тоже попал в таблицу со статусом «активен».

**Как НЕ проверять** (проверено на практике, не работает для этой цели): «База секретов» → «Блэклист ОМ» → «Тест-площадка: блэклист» — этот экран проверяет термины блэклиста (`catalog_blacklist`/OpenMetadata), не пользовательские regex-паттерны. Тест с активным, корректно сохранённым паттерном 1 и текстом, где он должен сработать, дал «Совпадений не найдено» — это не баг паттерна, это не тот тестовый экран (см. `otkrytye-voprosy.md`).

**Надёжный способ проверки:**

1. Отправить тестовый текст в обычный чат платформы (как в `case-03-instrukciya-proverka-maskirovaniya.md`): «Договор № ВР33431 от 24.09.2019. Брокерский / лицевой счёт ВР33431 / ВР33431-МО-01. Лицензия № 045-07514-100000».
2. Открыть «Администрирование» → «Рабочее место ИБ» → «Журнал LLM-сессий», найти свою сессию.
3. В сводке сессии убедиться, что номер договора/счёта и номер лицензии попали в найденные PII-spans и заменились на токены `[CUSTOM_N]` (с разным порядковым номером на разные значения), а дата, баланс, ISIN — нет.
4. Отдельно прогнать через тот же чат кусок с портфелем и балансом («ОФЗ-ПД225 — 1 шт», «16 634,88 ₽») — паттерны выше не должны их зацепить (самопроверка на ложные срабатывания — см. раздел 3).
5. Если платформа настроена с ненулевым `PII_CATALOG_BLACKLIST_SYNC_INTERVAL` — `pii-shield` подхватывает новые паттерны не мгновенно, а по опросу `GET /api/v1/shield-config`; если сразу не сработало, стоит подождать один цикл синхронизации, прежде чем считать паттерн нерабочим.
