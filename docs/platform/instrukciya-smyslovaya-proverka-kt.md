# Инструкция: смысловая проверка коммерческой тайны

Практическая инструкция для ИБ-аналитика: как настроить смысловую проверку запросов в чат-ассистенте на предмет конфиденциальных сведений. Модуль «Защита» (dlp-secret), экран «База секретов» (см. также `baza-sekretov.md`).

## Схема действий

1. **Запрос** — сотрудник пишет запрос в чат-ассистента; система проверяет его до того, как запрос уйдёт дальше.
2. **Признаки** — сверка по смыслу с Базой коммерческой тайны, точное совпадение с ключевыми словами, гриф во вложении, структурный шаблон (раздел 2).
3. **Решение** — Разрешено / На проверку / Заблокировано (раздел 1).
4. **Итог** — разрешённые запросы обрабатываются обычным образом; спорные попадают в очередь инспектору (раздел 5); заблокированные дальше не уходят.

Параллельно и независимо от этой цепочки работает Чёрный список — принудительная маскировка наименований (раздел 4, шаг 5): он не блокирует запрос, а скрывает перечисленные слова в тексте, который проверка пропустила.

## 1. Что делает эта проверка

Когда сотрудник пишет запрос в чат-ассистента, система (до того, как запрос уйдёт дальше) сверяет его с перечнем конфиденциальных сведений компании — по смыслу, а не только по словам.

Обычный фильтр ищет точные слова из «стоп-листа» — его легко обойти: переставить слова, пересказать своими словами, заменить термин синонимом. Смысловая проверка сравнивает, о чём написано, поэтому улавливает пересказ, перефразировку и «обходные» формулировки, даже если ни одного «запретного» слова в тексте нет.

По каждому запросу система выносит одно из трёх решений:

| Решение | Что происходит | Что видит сотрудник |
|---|---|---|
| Разрешено | Запрос не похож на конфиденциальный — пропускается | Ничего: запрос обрабатывается обычным образом |
| На проверку | Запрос выглядит спорно — попадает в очередь, инспектор ИБ решает вручную | Запрос ожидает решения инспектора или сразу отклоняется с предложением переформулировать |
| Заблокировано | Запрос явно раскрывает защищаемые сведения — не пропускается | Уведомление об отказе; запрос дальше не уходит |

> **Смысловая проверка — не единственный барьер.** Она работает вместе с обезличиванием персональных данных, принудительной маскировкой по чёрному списку и точечными правилами (грифы, структурные шаблоны).

## 2. Из чего складывается решение

Система принимает решение по нескольким признакам одновременно:

1. Похоже по смыслу на образцы из Базы коммерческой тайны — основной механизм.
2. Содержит защищаемое наименование из списка ключевых слов — кодовое название проекта, имя внутренней системы.
3. Приложен документ с грифом — гриф считывается из колонтитулов вложения.
4. Совпадает со структурным шаблоном (например, формат номера договора или внутреннего кода).
5. Если признаки противоречивы — подключается автоматический арбитр, который «читает» спорный фрагмент и уточняет решение.
6. Остаются сомнения — фрагмент уходит человеку на разбор, и его решение система запоминает.

> **Задача аналитика.** Пункты 1–3 нужно наполнить материалом организации. Пункт 4 работает без настройки. Пункт 5 настройки не требует, но требует ежедневного участия — раздел 5.

## 3. Что подготовить заранее

До начала настройки соберите:

- Перечень сведений, составляющих коммерческую тайну (или иной документ, определяющий, что конфиденциально), — по разделам и категориям.
- Примеры реальных формулировок по каждой категории: короткие фрагменты текста, как эти сведения обычно выглядят в документах и переписке. Именно на примерах система учится узнавать смысл — чем разнообразнее формулировки одного и того же, тем надёжнее.
- Список защищаемых наименований: кодовые названия проектов, имена внутренних систем, продуктов, обозначения, которые сами по себе выдают конфиденциальность.
- Перечень категорий и матрицу доступа: какие категории сведений каким контрагентам допустимы. Категория — не только группировка, по ней проверяется доступ.
- Список наименований для принудительной маскировки — то, что не должно уходить дальше в открытом виде.
- Структурные признаки, если есть: как устроены номера договоров, внутренние коды, идентификаторы.

> **Совет.** 5–10 разнообразных примеров на категорию на старте лучше, чем один «идеальный». Базу всегда можно дополнить.

## 4. Пошаговая настройка

Все действия — в веб-интерфейсе модуля «Защита», под учётной записью инспектора или аналитика ИБ.

### Шаг 1 — наполнить Базу коммерческой тайны (главное)

**Путь:** База секретов → Список документов.

Это ядро смысловой проверки — набор эталонных материалов, с которыми сравнивается каждый запрос.

Два способа наполнения:

- **Загрузка из папки** — укажите папку с документами и общую категорию, система разберёт их сама. Удобно для большого объёма.
- **Добавление по одному** (кнопка «Добавить») — заполните:

| Поле | Что это |
|---|---|
| Текст фрагмента | Реальная формулировка конфиденциальных сведений — небольшой связный отрывок, а не отдельное слово |
| Уровень секретности | Насколько сведения чувствительны. Влияет на отображение и фильтрацию в списке Базы; **на решение не влияет** |
| Категория | Раздел перечня, к которому относится фрагмент. **Ключевое поле** — по категории проверяется доступ по матрице контрагентов, а не по уровню секретности |
| Тип документа | Откуда фрагмент (договор, отчёт, служебная записка и т. п.), по желанию |
| Кем внесено | Логин — для фиксации авторства записи |

Ручное добавление удобно для отдельных формулировок, которых нет в документах: устные договорённости, типовые фразы из переписки, «обходные» варианты, замеченные в очереди разбора.

> **Частая ошибка.** Ошибка в категории меняет результат проверки доступа — заполняйте её внимательно, не «на глаз».

> **Совет.** Наполняйте по категориям, а не вперемешку: так проще поддерживать и понимать, какой раздел перечня уже покрыт примерами, а какой — нет.

### Шаг 2 — ключевые слова

**Путь:** Ключевые слова.

Сюда вносятся точные наименования, которые сами по себе выдают конфиденциальность: кодовые названия проектов, имена внутренних систем, продуктов, обозначения. Каждому наименованию назначается категория.

Проверяется весь текст запроса — совпадение ищется как вхождение, независимо от регистра. Если наименование встретилось, а смысловая проверка ничего не нашла, запрос уходит на разбор инспектору: сам по себе список ключевых слов не блокирует.

> **Важно.** Категория ключевого слова участвует в проверке доступа наравне с категорией фрагмента Базы — не оставляйте её произвольной.

### Шаг 3 — грифы в приложенных документах

Если сотрудник прикладывает к запросу документ, система читает колонтитулы — шапку и подвал — и ищет там гриф: «Коммерческая тайна», «Конфиденциально» и подобные отметки.

Найденный гриф повышает строгость решения: чем выше гриф, тем ближе результат к блокировке — от направления на разбор до прямого запрета, независимо от того, что показала смысловая проверка содержимого.

Настройка от аналитика здесь не требуется — перечень распознаваемых грифов и их вес задаются в конфигурации системы. Нестандартные формулировки грифов передайте администратору для внесения.

> **Ограничение механизма.** Гриф считывается только из документов формата DOCX и только из колонтитулов. Гриф, оформленный таблицей внутри колонтитула, картинкой или размещённый в теле документа, распознан не будет — такие материалы страхуйте через Базу коммерческой тайны и ключевые слова.

### Шаг 4 — структурные шаблоны

**Путь:** Шаблоны.

Если есть сведения со строгой структурой (номера договоров определённого формата, внутренние коды), опишите их здесь — система будет узнавать их по форме записи. См. также готовые примеры regex-паттернов в `instrukciya-novye-atributy-maskirovaniya-otchet-brokera.md`.

### Шаг 5 — чёрный список (принудительная маскировка)

**Путь:** Чёрный список.

Это не часть смысловой проверки: на решение «Разрешено / На проверку / Заблокировано» он не влияет.

Сюда вносятся слова и наименования, которые нужно всегда скрывать: кодовые названия проектов, имена внутренних систем и продуктов, отдельные фамилии и обозначения, которые не должны уходить дальше в открытом виде.

Список ведётся здесь, а сама замена выполняется модулем обезличивания — тем же, что скрывает персональные данные. Запрос при этом не блокируется: он идёт дальше, но перечисленные наименования в нём уже скрыты. Результат маскировки виден не в журнале смысловой проверки, а в журнале обезличивания.

> **Чёрный список — обезличивание, а не блокировка.** Если сведения нельзя пропускать вовсе — их место в Базе коммерческой тайны (Шаг 1), а не здесь. Если сведения пропускать можно, но упоминать наименование нельзя — тогда сюда.

### Шаг 6 — проверить на примерах

**Путь:** База секретов → Проверка, Чёрный список → Проверка.

Введите пробную формулировку и посмотрите, какое решение вынесет система, — не дожидаясь реальных запросов.

Прогоните два набора: «явно секретные» формулировки и «заведомо безобидные». Первые должны блокироваться, вторые — проходить. Результат — основание для следующего шага.

> **Совет.** Сохраните оба набора: их удобно прогонять повторно после каждого изменения настроек и пополнения Базы коммерческой тайны.

### Шаг 7 — настроить чувствительность

**Путь:** Калибровка (настройка порогов).

Регулирует, насколько строго система реагирует — границу между тремя решениями. Подстраивайте по результатам Шага 6, а не вслепую.

- **Строже** — больше запросов уходит на проверку и в блок. Меньше риск утечки, но больше ложных срабатываний и лишняя нагрузка на инспектора.
- **Мягче** — меньше помех сотрудникам, но выше риск пропустить «пограничный» запрос.

> **Рекомендация.** Начните с настройки по умолчанию, неделю-две последите за очередью разбора и журналом (раздел 6), затем аккуратно подстройте. Резких изменений не делайте — двигайте границу небольшими шагами и после каждого сдвига перепроверяйте контрольные наборы из Шага 6.

## 5. Разбор спорных случаев (ежедневная работа)

**Путь:** Очередь на разбор.

Сюда попадают запросы с решением «На проверку». По каждому аналитик решает: пропустить или заблокировать.

Это не только оперативное решение — система запоминает вердикт и учитывает его в дальнейшем. Регулярный разбор очереди делает проверку точнее со временем: чем больше размеченных спорных случаев, тем реже система ошибается на похожих.

> **Разбирайте очередь регулярно.** Накопленные без разбора спорные случаи — это и задержки для сотрудников, и упущенная возможность «дообучить» систему.

## 6. Поддержание в актуальном состоянии

- **Журнал и статистика** — периодически просматривайте: какие запросы блокируются, нет ли всплеска ложных срабатываний, какие категории конфиденциальных сведений задействованы.
- **Пополняйте Базу коммерческой тайны**, когда появляются новые виды документов или формулировок, либо когда в очереди разбора регулярно встречаются похожие спорные случаи — добавляйте их как эталоны.
- **Обновляйте ключевые слова, чёрный список и шаблоны** при появлении новых проектов, систем, форматов кодов. Новые формулировки грифов передавайте администратору.

## 7. Важные принципы

- **Полнота Базы коммерческой тайны важнее точных настроек.** Смысловая проверка узнаёт только то, на что даны примеры. Никакие пороги не спасут пустой или скудный набор эталонов.
- **Разнообразие формулировок.** Один и тот же смысл, записанный по-разному, стоит внести несколькими примерами.
- **Смысловая проверка не заменяет обезличивание.** Блокировка и маскировка — разные задачи разных модулей, они работают вместе. Одно и то же наименование может и вести к разбору инспектором (ключевые слова), и скрываться в тексте (чёрный список) — это не дублирование.
- **Начинайте мягко, ужесточайте по наблюдениям.** Слишком строгая настройка «с порога» завалит инспектора ложными срабатываниями и вызовет отторжение у сотрудников.
- **Спорные случаи — это ресурс, а не помеха.** Каждый разобранный случай повышает точность.

> Вопрос, какие сведения относить к какой категории и с каким уровнем секретности, — решение владельца режима коммерческой тайны в организации, а не техническая настройка.

## Глоссарий

- **База коммерческой тайны** — набор эталонных фрагментов текста, с которыми смысловая проверка сравнивает каждый запрос.
- **Смысловая проверка** — сравнение запроса с эталонами по смыслу, а не по точному совпадению слов.
- **Ключевые слова** — точные защищаемые наименования (проекты, системы, продукты), совпадение с которыми направляет запрос на разбор инспектору.
- **Гриф** — отметка о конфиденциальности («Коммерческая тайна», «Конфиденциально»), считываемая из колонтитулов приложенного DOCX-документа.
- **Чёрный список** — список наименований для принудительной маскировки; не блокирует запрос, а скрывает перечисленные слова через модуль обезличивания.
- **Арбитр** — автоматический механизм, который «читает» спорный фрагмент и уточняет решение при противоречивых признаках.
- **Очередь на разбор** — список запросов с решением «На проверку», которые инспектор ИБ разбирает вручную.
