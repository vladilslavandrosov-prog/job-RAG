# Экран «Внешние агентские системы» — рабочее место ИБ

Инструкция по разделу рабочего места ИБ, где администратор управляет доступом внешних агентских систем (n8n, GigaChat, Just AI и т.п.) к данным платформы через **MCP Gateway** по протоколу **OAuth 2.1 (client_credentials)**. Составлена по скриншотам живого стенда — реестр, карточка клиента, блок «Жизненный цикл».

> Это инструкция по **UI-экрану ИБ**. Техническая часть — сам OAuth-flow, curl-примеры, диагностика ошибок клиента — уже подробно описана в [`instrukciya-mcp-gateway-podklyuchenie.md`](instrukciya-mcp-gateway-podklyuchenie.md); здесь эти два документа дополняют друг друга, не дублируются.

## 1. Как попасть на экран

Верхняя навигация → **«Рабочее место ИБ»** (выпадающее меню) → **«Внешние агентские системы»** — пункт в нижнем блоке меню, рядом с «Типы действий инструментов» и «Настройки развёртывания».

URL: `.../dlp/external-clients/`

## 2. Реестр

Экран «Внешние агентские системы» показывает три очереди подряд:

| Очередь | Что в ней |
|---|---|
| **Ожидают апрува ИБ** | Поданные, но ещё не одобренные заявки |
| **Активные** | Клиенты со статусом `active` — реально могут получать токены и вызывать инструменты |
| **Отозванные** | История клиентов, доступ которым закрыт |

В каждой очереди — таблица с колонками **client_id**, **Персона**, **Namespace (aud)**, **Владелец**, и (кроме «Ожидают апрува») кнопка **«Открыть →»** на карточку клиента.

Новая заявка подаётся кнопкой **«+ Заявка»** в правом верхнем углу экрана. Сама форма заявки (поля «Вендор», «Назначение», «Персона», `om_user_email`, «Ресурсы» / namespace, флажок «Требуется маскировка ПДн» и т.д.) и порядок одобрения — подробно в `instrukciya-mcp-gateway-podklyuchenie.md`, Часть II, Шаг 1. Здесь не повторяется.

## 3. Карточка клиента

Открывается по кнопке «Открыть →» из реестра: `.../dlp/external-clients/<client_id>`.

| Поле | Что это |
|---|---|
| `client_id` | Идентификатор клиента, присвоенный при регистрации |
| Статус | `active` / отозванные показываются с соответствующим статусом |
| Метод аутентификации | `client_secret` — единственный наблюдаемый на стенде вариант |
| Persona ID | UUID персоны — граница доступа (домены, RLS-фильтры) этого клиента |
| OM service-account | Учётная запись OpenMetadata, которую клиент имперсонирует (`om_user_email` из заявки) |
| Namespace (aud) | Один или несколько: `data__`, `om__` — к каким наборам инструментов есть доступ |
| Домены | «(по персоне)» — домены не задаются отдельно на клиенте, а наследуются от персоны |
| Scopes | Дополнительная область действия; «—», если не используется |
| Владелец / заказчик | Кому принадлежит доступ / для кого заведён — в наблюдаемых примерах оба поля пустые (`—`) |
| Создал / одобрил | Кто подал заявку и кто её одобрил — могут совпадать (самоодобрение сотрудником ИБ) |
| Создан | Таймстемп создания заявки |
| Одобрен | Таймстемп перехода в `active` |
| Ротация | Таймстемп последней ротации `client_secret` |
| Access-токен (Ф7) | Таймстемп выдачи последнего `access_token` этому клиенту |

## 4. Блок «Жизненный цикл (admin)»

На карточке клиента, под таблицей полей — три действия:

- **Ротация секрета**
- **Перевыпустить токен**
- **Отозвать** — с обязательным текстовым полем «Причина отзыва» (например, «ручной отзыв»)

Подтверждено самим интерфейсом — при нажатии каждой кнопки платформа показывает диалог подтверждения с точной формулировкой:

| Действие | Диалог подтверждения | Эффект |
|---|---|---|
| **Ротация секрета** | «Ротация: старый секрет останется валиден в grace-окно. Продолжить?» | Меняет `client_secret`. **Старый секрет продолжает работать** в течение grace-окна (в общей инструкции по MCP Gateway для стандартного `client_secret` это 36 часов — вероятно, то же значение и здесь). Клиент не теряет доступ мгновенно, время на обновление credential есть. |
| **Перевыпустить токен** | «Перевыпуск access-токена: прежний pii_ext_-токен сразу станет недействителен. Продолжить?» | Выпускает новый `access_token`. **Прежний `pii_ext_`-токен становится недействительным немедленно**, без grace-окна. |

> **Практический вывод.** Для обезвреживания скомпрометированного токена без риска обрыва интеграции — начинать с **«Ротация секрета»** (есть время передать новое значение клиенту до истечения grace-окна). **«Перевыпустить токен»** — более резкая мера: использовать, когда нужно немедленно оборвать доступ по текущему токену (например, точно известно, что он уже используется третьей стороной), не дожидаясь grace-окна.

**Когда что использовать:**
- Секрет или токен клиента случайно скомпрометирован (например, отправлен открытым текстом в чат/скриншотом) → обезвредить утёкшее значение ротацией/перевыпуском, не трогая «Отозвать» — так регистрация клиента и его права остаются на месте, обновить нужно только credential на стороне клиента.
- Клиент больше не должен иметь доступ вообще → «Отозвать» с указанием причины.

## 5. MCP-вызовы (аудит)

Ниже блока «Жизненный цикл» — таблица **«MCP-вызовы (последние N)»**: инструменты, вызванные этим конкретным агентом, с результатом **в маскированном виде** — сырые значения ПДн в этом логе не показываются. Удобно для точечной проверки, что именно и когда вызывал конкретный внешний клиент, без риска раскрыть ПДн через сам аудит-лог.
