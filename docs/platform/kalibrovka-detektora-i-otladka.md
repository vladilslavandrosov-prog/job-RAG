# Раздел «Калибровка»: детектор таблиц и отладка диалогов

> Скриншоты: `Калибровка детектора` (таблиц) и `Отладка сессий` — два из трёх пунктов подраздела «Калибровка» (третий — «Политики поиска», уже описан отдельно в `kalibrovka-politiki-poiska.md`).

## Калибровка детектора таблиц

> «Пороги детектора рег-коллекция и живая переразметка реальных таблиц. Корни measure для range-роутера — на вкладке «Корни measure».»

Инструмент настройки **детектора**, который на этапе индексации определяет, является ли фрагмент документа таблицей. Именно этот детектор, судя по всему, выставляет метаданные `is_table`, которые потом использует политика `таблица-схема-boost` в разделе «Политики поиска» (`kalibrovka-politiki-poiska.md`) — то есть это два звена одной цепи: сначала детектор размечает чанк как таблицу, потом политика ранжирования решает, поднимать ли такой чанк в выдаче.

### Вкладки

| Вкладка | Назначение (по названию) |
|---|---|
| **Калибровка порогов** (активна на скриншоте) | Настройка порогов срабатывания детектора; на скриншоте — только выбор коллекции (`— системная/командная —`), содержимое не раскрыто |
| Чанкинг | Вероятно, настройки разбиения на фрагменты именно для табличного контента |
| Документы | Проверка/предпросмотр детекции на конкретных документах |
| Обслуживание | Служебные операции (переиндексация, обслуживание) |
| Корни measure | Настройка для **range-роутера** — судя по названию, отдельный механизм маршрутизации вопросов про числовые диапазоны/меры (связано с категорией «Data-вопросы» из `kalibrovka-politiki-poiska.md`) |

### Наблюдение

«Range-роутер» и «корни measure» — ещё один слой роутинга вопросов, отдельный от того, что описан в блоке «Роутинг вопросов» на странице «Политики поиска». Похоже, там был описан не единственный механизм маршрутизации, а был замечен только один из нескольких. Стоит на будущих скриншотах выяснить, как соотносятся друг с другом «Роутинг вопросов» (фразы/regex) и «range-роутер» (корни measure) — конкурирующие механизмы или разные уровни одного пайплайна.

## Отладка сессий

> «Диалоги пользователей с оценками. Клик — разбор сессии (инструменты, план, ответы).»

Это ровно тот **технический reasoning log**, необходимость которого обсуждалась в `case-02-tz-deep-analysis-and-proposals.md` (рекомендация 4.6) и который частично предвосхищает переключатель «Рассуждения» в `chat.md`: клик по диалогу должен раскрывать разбор сессии — какие инструменты вызывались, какой план был построен, какие ответы получены.

### Элементы экрана

| Элемент | Назначение |
|---|---|
| Поиск по пользователю + «Найти» | Найти диалоги конкретного пользователя |
| Таблица: Пользователь / Диалог / Модель / Обновлён | Список диалогов с базовыми метаданными |
| Пагинация («← Назад / 0 / Вперёд →») | Постраничная навигация по диалогам |

### ⚠ Критическая находка: аудит-БД не сконфигурирована

На скриншоте — предупреждение: **«Аудит-БД не сконфигурирована»**, и таблица диалогов пуста («Нет диалогов»), несмотря на то что реальные диалоги в системе точно были (см. `docs/analysis/case-01-d8-014-brief.md` — лог по клиенту D8-014).

Это прямо объясняет, почему разбор Кейса 01 пришлось делать **вручную по тексту ответов агента**, а не через штатный инструмент отладки: сам инструмент, который позволил бы кликнуть на сессию D8-014 и увидеть точный план, вызовы инструментов и сгенерированный (упавший) SQL-запрос, **в этом окружении не настроен и не работает**. Возможность существует в продукте, но фактически не эксплуатируется.

Это прямая, конкретная иллюстрация к находке 2.4 из `case-02-tz-deep-analysis-and-proposals.md` («Нет аудита промежуточных шагов рассуждения») — только теперь понятно, что дело не в отсутствии *функции* в продукте (она есть, вот этот самый экран), а в том, что она **не включена/не подключена** в данном развёртывании. Рекомендация: включение аудит-БД для этого экрана должно быть отдельным пунктом в списке приоритетных доработок — это единственный найденный на сегодня штатный инструмент, который закрыл бы главный пробел, вскрытый Кейсом 01.
