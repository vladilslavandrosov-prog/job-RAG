# Раздел «Мои шаблоны»

> Скриншот: экран `Разделы → Мои шаблоны` (`https://sinapse.itq-group.com:12452/shell/templates`).

## Назначение экрана

Механизм **курируемых образцов ответов**: администратор/аналитик заранее задаёт пару «вопрос-триггер → образец ответа», и при похожем вопросе в чате система подставляет этот образец вместо того, чтобы каждый раз генерировать ответ с нуля.

> «Курируемые образцы ответов: recall подставляет их в чате на похожий вопрос. «Строгий» — вернуть как есть, заменив актуальные данные. Форма (график/таблица) воспроизводится по свежим данным. Тексты обезличены.»

## Поля формы

| Поле | Назначение |
|---|---|
| **Вопрос-триггер** | Формулировка вопроса, при похожести на которую сработает шаблон (поиск по смыслу — «recall») |
| **Ответ-образец** | Текстовый шаблон ответа |
| **График** (`— нет —`) | Выбор типа графика, который должен сопровождать ответ, если применимо |
| ☑ **таблица** | Ответ включает табличную форму |
| ☐ **строгий шаблон** | См. ниже — режим точного возврата vs пересчёта данных |
| **Сохранить** / **Отмена** | Сохранить шаблон или отменить создание |

## Как работает recall и режим «строгий»

Судя по описанию, у шаблона два режима:

1. **Обычный (не строгий) режим** — по похожему вопросу текст ответа берётся из шаблона (структура, тон, формулировки), но **форма (график/таблица) пересчитывается по свежим данным** на момент вопроса. То есть шаблон фиксирует *как* отвечать, а не *что именно* было в цифрах в прошлый раз.
2. **Строгий шаблон** — ответ возвращается **как есть**, только подставляя актуальные данные вместо значений в шаблоне (то есть более жёсткая привязка к точной формулировке образца, без права модели переформулировать).

**«Тексты обезличены»** — важная деталь: сам шаблон-образец не должен содержать реальные ФИО/данные конкретного клиента, только структуру ответа. Это подтверждает, что где-то в системе действительно применяется обезличивание данных (см. открытый вопрос 1.1 в `case-02-tz-deep-analysis-and-proposals.md` про противоречие между маскированием ПДн и поиском по ФИО/ИНН) — здесь, по крайней мере, обезличивание точно применяется на уровне куратора шаблонов, вручную.

## Связь с находками Кейса 01 и Кейса 02

Это отдельный, **не автоматический** механизм повторного использования готовых ответов — принципиально иной, чем рекомендация 4.1 из `case-02-tz-deep-analysis-and-proposals.md` (память сессии, автоматическое переиспользование уже подтверждённых в диалоге данных). Стоит явно развести эти два механизма:

| | Память сессии (рекомендация 4.1, `case-02`) | Шаблоны (`Мои шаблоны`) |
|---|---|---|
| Кто заводит | Система автоматически | Куратор/аналитик вручную |
| Область действия | В рамках одного диалога | Кросс-сессионно, для всех похожих вопросов от любого пользователя |
| Что фиксируется | Уже полученный результат конкретного под-запроса | Общая структура/формулировка ответа на типовой вопрос |
| Актуальность данных | Всегда те данные, что уже были получены в сессии | Пересчитываются заново (кроме строгого режима) |

**Не решает, но может частично компенсировать** дефект 3 из `case-01-d8-014-brief.md` (потеря уже подтверждённых данных на шаге финального синтеза брифа): если завести шаблон с вопросом-триггером вида «собери бриф к встрече с клиентом» и образцом ответа, повторяющим структуру брифа (портрет → позиции → P&L → обращения), система будет **гарантированно** идти по этой структуре и пересчитывать данные заново по каждому пункту — вместо того, чтобы полагаться на то, соберёт ли LLM всё сама. Это не чинит саму причину сбоя (недостающий reuse верифицированных данных сессии/некорректный SQL при синтезе), но снижает шанс, что *структура* итогового ответа развалится так, как в Кейсе 01 — при условии, что сам пересчёт данных по каждому пункту шаблона всё равно устойчив.
