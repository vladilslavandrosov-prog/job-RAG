# Руководство администратора информационной безопасности платформы «Камерата»

Это руководство — для сотрудника ИБ (Оператор ИБ / Администратор ИБ): управление доступом, защита персональных данных и коммерческой тайны, аудит, реагирование на инциденты и соответствие требованиям регулятора. Это более глубокая, специализированная версия материала, чем в общем «Руководстве администратора» — там та же тема дана компактно, здесь — с полными процедурами, таблицами соответствия и техническими деталями, нужными именно ИБ-специалисту.

Учётная запись администратора ИБ не предназначена для аналитических запросов к данным — если ИБ-специалисту по работе нужен доступ к данным, для этого заводится отдельная учётная запись с обычной ролью пользователя.

## 1. Зона ответственности

| Зона ответственности | Что включает | Что НЕ включает |
|---|---|---|
| Управление доступом | Пользователи, роли, коллекции, политики доступа (OPA) | Инфраструктура, сетевые правила, firewall |
| Аудит и мониторинг | Журналы событий, операции с персональными данными, активность пользователей | Системные логи Docker/Kubernetes, метрики Prometheus |
| Защита данных | Настройки PII Shield, теги персональных данных, пороги обнаружения, база секретов | Шифрование носителей, резервное копирование |
| Реагирование на инциденты | Блокировка пользователей, экспорт журналов аудита, эскалация | Восстановление системы, обновление платформы |

Настройка инфраструктуры, резервное копирование и обновление платформы — ответственность технической команды (DevOps/SRE), не администратора ИБ.

## 2. Три системы, которые легко перепутать

- **Каталог** — единая витрина данных компании и исходная личность пользователя (единый вход), плюс права на сам каталог.
- **«Сотрудники ИБ»** — отдельный, суверенный реестр того, кто может войти в раздел администрирования с ролью **Оператор ИБ** или **Администратор ИБ**. Не наследуется из корпоративного каталога никогда — добавление себя или коллеги в группу каталога не даёт полномочий ИБ автоматически. Это осознанное архитектурное решение: полномочия надзора не должны выдаваться средствами общей ИТ-инфраструктуры.
- **«Пользователи и доступ»** — какие языковые модели и с каким лимитом токенов доступны пользователю в чате; к входу в администрирование отношения не имеет.

**Оператор ИБ** не может редактировать других сотрудников ИБ и менять настройки безопасности; **Администратор ИБ** — полные права в разделе администрирования. Роль в «Сотрудники ИБ» — надстройка поверх базовой роли платформы (Пользователь/Администратор), а не замена ей; возможна комбинация «Пользователь + Оператор ИБ».

**Разделение обязанностей.** Администратор платформы (эксплуатация, развёртывание, обновления) и администратор ИБ (политики, классы данных, состав тех, кто наделён полномочиями надзора) — два ортогональных набора полномочий, ни один не приобретает полномочий другого автоматически. Тот, кто настраивает платформу технически, не получает вместе с этим право решать, что можно выпускать наружу и кто может просматривать журналы.

## 3. Управление пользователями

### Создание пользователя

1. Открыть «Сотрудники ИБ» → «+Добавить» (для роли в самой админке) либо Каталог → «Пользователи»/«Админы» (для базовой роли платформы — см. «Руководство администратора», раздел 2, там же оба практических кейса пошагово).
2. Заполнить обязательные поля: логин (латиница и цифры, нельзя изменить после создания), email, роль, при необходимости — подразделение (для группировки и аудита).
3. Назначить доступные коллекции — пользователь получит доступ только к выбранным, других данных не увидит.
4. Сохранить.

Изменение назначений коллекций вступает в силу немедленно — следующий запрос пользователя уже учитывает новые права, без перезапуска и без прерывания активной сессии для уже открытых прежде коллекций.

### Блокировка, разблокировка, удаление

Блокировка немедленно завершает все активные сессии пользователя и запрещает новые входы; данные пользователя и история его запросов сохраняются. Следующий запрос заблокированного пользователя получает отказ, уже выполняющиеся запросы завершаются штатно. Для разблокировки — открыть карточку пользователя и разблокировать, при необходимости одновременно сбросив пароль.

**Удаление необратимо.** История запросов и записи аудита сохраняются, но сама учётная запись восстановлению не подлежит. Для удаления требуется двойное подтверждение (ввод имени пользователя + отдельное нажатие). Для уволившихся сотрудников рекомендуется блокировать, а не удалять — это сохраняет аудиторский след.

### Периодическая проверка

Регулярно сверяйте, у кого есть доступ к коллекциям с чувствительными данными — раздел коллекции показывает всех пользователей с назначенным к ней доступом. Колонка «Последний вход» в списке пользователей помогает выявить неактивные учётные записи, которые стоит заблокировать.

## 4. Модель доступа: домены, коллекции, построчная фильтрация

Коллекция — единица данных и одновременно граница доступа: пользователь видит только те коллекции, которые ему назначены явно.

**Построчная фильтрация (row-level security)** реализована через политики авторизации (OPA — Open Policy Agent) поверх федеративных SQL-запросов: политики формируют row-фильтры на основе бизнес-доменов каталога, назначенных роли/персоне пользователя. Формируются **автоматически** из доменов каталога — пользователю доступны строки таблиц, отнесённых к доменам его роли. Правила выражены на языке Rego и синхронизируются из метаданных каталога.

Редактирование политик через интерфейс недоступно — это намеренное ограничение против случайного изменения. Изменение политик — операция высокого риска, выполняется только технической командой через конфигурационные файлы платформы, с версионированием. Если текущие политики не соответствуют требованиям ИБ — оформляется запрос на изменение через внутреннюю процедуру, а не правится напрямую.

Маскирование персональных данных в ответах и разрешения на экспорт настраиваются отдельно (PII Shield и роли пользователей), не политиками доступа — это две разные системы, решающие разные задачи (см. также раздел 6 общего руководства администратора о том, что «домен» = что можно читать, а «класс данных» = куда можно отправить — независимые оси).

**Ключевой принцип:** разграничение доступа применяется **до** обезличивания. Замаскированный ответ по записи, к которой у пользователя нет доступа, — тоже нарушение; платформа не показывает такую запись вовсе, даже в маскированном виде.

### Кейс: как проверить и выдать доступ по домену/коллекции

С точки зрения ИБ здесь два разных действия — назначение доступа и проверка того, что он реально соответствует построчным правилам.

1. **Назначение коллекции пользователю** — «Пользователи и доступ» → карточка пользователя → «Доступ к данным» → «Добавить коллекцию» → выбрать из списка → «Сохранить». Действует немедленно, без перезапуска и без прерывания уже открытой сессии — ограничение или расширение доступа применится со следующего запроса пользователя.
2. **Отзыв** — тем же путём, «Отозвать» у нужной коллекции. Тоже немедленно, с той же оговоркой про уже открытую сессию.
3. **Массовое назначение «на команду» не предусмотрено** — доступ к коллекциям выдаётся индивидуально каждому пользователю, даже если все они в одном подразделении. Подразделение (команда) в Каталоге — это группировка для аудита и, опционально, область бюджета, не единица прав на данные.
4. **Периодический аудит по коллекции** — «Источники данных» → нужная коллекция → «Пользователи»: список всех, у кого есть к ней доступ. Используется для регулярной проверки (раздел 9) — что доступ к чувствительным коллекциям соответствует текущим должностям.
5. **Построчный доступ проверять отдельно** — сами правила (Rego, из бизнес-доменов каталога) администратор ИБ не редактирует; для проверки, что фильтр реально применяется к конкретному домену, используется предпросмотр «как будет выглядеть выборка под такой-то ролью» и «Карта покрытия» (раздел «Управление данными» общего руководства администратора) — показывает, какие таблицы/колонки уже покрыты правилами, а какие ещё нет.

> **Важно.** Назначение коллекции (шаг 1) и построчный доступ внутри неё (шаг 5) — независимые слои. Выдать пользователю коллекцию и ожидать, что построчные правила автоматически «подхватят» нового человека, нельзя проверить на глаз — оба слоя стоит сверять по отдельности, особенно для коллекций с чувствительными данными.

## 5. Защита персональных данных: PII Shield

PII Shield — встроенный компонент защиты персональных данных. Автоматически обнаруживает персональные данные в ответах агентов и маскирует их перед выдачей пользователю, без ручной проверки. Все операции маскирования журналируются.

### Три механизма обнаружения одновременно

1. **Аннотации каталога метаданных** — основной механизм для структурированных данных: поле, помеченное в каталоге как персональное, маскируется всегда, по факту разметки, без разбора содержимого.
2. **Формальные правила для типизированных идентификаторов** — свыше 250 встроенных правил (телефон, email, ИНН, СНИЛС, паспорт, банковские карты/счета, ОГРН, IBAN, VIN, даты рождения, IP-адреса, госномера, токены доступа), с проверкой контрольных соотношений для 6 типов — это исключает ложные срабатывания на похожих по формату числах.
3. **NER для свободного текста** — раздельно для русского и английского языков, покрывает то, что не описано разметкой каталога и не подходит под формальные правила.

Отсутствие разметки каталога не создаёт незащищённый путь наружу — защита работает и без неё, за счёт двух других механизмов. Разметка делает защиту **предсказуемой**: чем больше размечено, тем большая доля маскирования выполняется по объявленному правилу, а не по распознаванию — поэтому работа куратора данных по разметке каталога напрямую конвертируется в надёжность защиты.

### Настройка порогов обнаружения

| Параметр | По умолчанию | Описание |
|---|---|---|
| Минимальный порог обнаружения | 0,4 (40%) | Уверенность модели, при которой сущность считается персональными данными. Снижение → больше ложных срабатываний, повышение → риск пропуска |
| Сканирование ответов | Включено | Отключение разрешает передачу немаскированных персональных данных — требует явного обоснования ИБ |
| Колоночное маскирование | Включено | Учитывает теги персональных данных из каталога для точного маскирования по столбцам |
| Стратегия маскирования | Токенизация | `PERSON_1`, `PHONE_1` и т.д.; альтернативы — псевдонимизация, полное скрытие |

Снижение порога ниже 0,3 может приводить к маскированию нечувствительных данных и заметному снижению качества ответов — изменять осторожно, с фиксацией обоснования.

### Теги персональных данных по коллекциям

Назначение тегов — задача куратора данных, но администратор ИБ должен периодически проверять полноту разметки.

| Тег | Тип данных | Рекомендуемая стратегия |
|---|---|---|
| PII.FullName | ФИО | Токенизация (`PERSON_N`) |
| PII.Phone | Телефон | Маскирование (частичное) |
| PII.Email | Email | Маскирование (частичное) |
| PII.TaxID | ИНН | Токенизация (`INN_N`) |
| PII.SNILS | СНИЛС | Полное скрытие |
| PII.PassportID | Паспортные данные | Полное скрытие |
| PII.BankCard | Номер карты | Маскирование (последние цифры) |
| PII.SensitiveData | Специальные категории персональных данных | Полное скрытие |

### Журнал маскирования

Каждая запись содержит временную метку, пользователя, коллекцию, тип обнаруженной персональной данной (не само значение), применённую стратегию и статус операции. Фильтры — по дате, пользователю, типу, коллекции; экспорт — CSV за выбранный период.

Регулярно проверяйте записи со статусом «Ошибка маскирования» — случаи, когда персональные данные были обнаружены, но маскирование не выполнено; каждый такой случай требует ручного разбора.

### Таблица соответствий и восстановление

Таблица соответствий «метка ↔ исходное значение» живёт только внутри контура, привязана к сессии, срок жизни по умолчанию — 60 минут, и не передаётся во внешнюю модель ни при каких условиях. Обратное восстановление исходного значения из метки невозможно без этой таблицы. Если хранилище соответствий недоступно при старте — компонент защиты **не запускается**: тихого отката в менее защищённый режим нет.

### Задержка обработки

Формальные правила — медиана 0,05 мс; NER — медиана 1,08 мс, p95 1,56 мс; совокупно — не более 2 мс при p95. Для табличных данных из источников — до 0,5 секунды при лимите 150–200 строк.

## 6. База секретов: коммерческая тайна

Отдельный от персональных данных механизм — защищает коммерческую тайну компании (внутренние регламенты, коммерческие условия, реквизиты договоров) с ручным решением при обнаружении совпадения. Не путать с PII Shield (раздел 5) — тот работает автоматически и всегда, без участия человека, и именно для персональных, а не коммерческих данных.

### Как работает детекция

Текст фрагмента коммерческой тайны заводится вручную (текст, уровень секретности `SECRET`/`CONFIDENTIAL`/`INTERNAL`/`PUBLIC`, категория, тип документа). Дальше автоматически: текст режется на фрагменты (~400 токенов, 25% перекрытие), каждый векторизуется и сохраняется в базу — используется сразу, без отдельного шага переиндексации. При проверке нового текста каждый его фрагмент ищется в базе по смысловой близости; максимальное совпадение решает исход:

| Оценка совпадения | Исход |
|---|---|
| ниже 0,75 | **PASS** — пропустить |
| 0,75–0,88 | **REVIEW** — на ручную проверку |
| 0,88 и выше | **BLOCK** — заблокировать |

Совпадение по справочнику ключевых слов добавляет небольшой бонус к оценке. Эти же пороги используются в экране «Управление базой» — общая настройка, а не параметр отдельной проверки.

### Кастомные атрибуты маскирования (регулярные выражения)

База секретов → «Regex-паттерны». Форма: название (понятное имя), regex-паттерн (синтаксис Python `re`, валидируется перед сохранением), тип токена. Тип токена — закрытый список из 5 значений: `PERSON`, `PROJECT`, `COMPANY`, `PRODUCT`, `CUSTOM`; свой префикс вписать нельзя — если ни один из первых четырёх не подходит по смыслу, выбирается `CUSTOM` (у которого единый общий префикс маски `[CUSTOM_N]`, без собственного узнаваемого имени).

Проверка — по кнопке «Изменить» у сохранённого паттерна, поле «Тестовый текст» и кнопка «Проверить». **Частая ошибка:** в поле «Тестовый текст» нужно вводить реальный пример данных, а не сам regex-паттерн — вставка самого паттерна вместо примера закономерно даёт «Совпадений не найдено», это не значит, что паттерн не работает.

**Важно:** «Тест-площадка: блэклист» проверяет только термины блэклиста — она не проверяет пользовательские regex-паттерны, даже если рядом написано «Детекция через pii-shield». Проверять кастомный паттерн нужно через инлайн-тест конкретного паттерна (выше) либо через реальный чат и журнал LLM-сессий.

## 7. Журнал аудита

Записи хранятся в PostgreSQL; доступ к журналу ограничен ролью администратора ИБ. Аудит разнесён по трём независимым журналам:

- **LLM-сессии** (`pii_audit`) — вопрос пользователя, вызовы инструментов, факт и объём маскирования персональных данных. Просмотр — раздел «Журнал LLM-сессий».
- **Привилегированные действия** (`admin_audit_log`) — операции администраторов и куратора данных: создание/деактивация учётных записей, изменение политик, согласования. Поля: оператор, действие, объект, время, значения до/после.
- **SQL-запросы** (`sql_audit`) — сгенерированные SQL-запросы к источникам: пользователь, таблицы и колонки, длительность, результат.

Общие поля записи: временная метка (UTC), пользователь и роль, тип и объект события, результат (успех / отказ / маскировано), контекст.

### Фильтрация и типовые сценарии

| Задача | Фильтр |
|---|---|
| Проверить все неудачные попытки входа за неделю | Тип: аутентификация, Результат: отказ, Период: 7 дней |
| Найти все обращения к коллекции с персональными данными | Тип: доступ к данным, Коллекция: [имя] |
| Проверить, кто изменял настройки безопасности | Тип: изменение конфигурации |
| Расследовать активность конкретного пользователя | Пользователь: [логин], все типы событий |
| Найти все случаи маскирования за день | Тип: маскирование ПДн, Период: сегодня |

### Экспорт

Форматы — CSV, JSON; экспортируются все записи по текущим фильтрам. Для передачи регулятору или во внешнюю SIEM-систему рекомендуется JSON. Для больших периодов удобно разбивать экспорт по датам; для потоковой передачи в SIEM — регулярный экспорт по расписанию.

Экспортированный журнал содержит чувствительную информацию о поведении пользователей — храните файлы в защищённом месте с ограниченным доступом.

### Мониторинг и внешние интеграции

Метрики безопасности (счётчики маскирования, ошибки, нагрузка сервисов) экспонируются в Prometheus и визуализируются в Grafana; пороговые оповещения (email/мессенджер) настраиваются средствами Alertmanager/Grafana. Встроенного в интерфейс движка правил с автоматической блокировкой платформа не предоставляет — реагирование на события выполняется человеком, средствами мониторинга и внешней SIEM.

Формат экспорта в SIEM — CEF или JSON (ECS) через syslog/HTTP, с очередью повторных попыток при недоступности приёмника.

## 8. Реагирование на инциденты

### Подозрение на компрометацию учётной записи

1. Немедленно заблокировать учётную запись через карточку пользователя.
2. Проверить историю активности за последние 7 дней — необычное время входа, нетипичные коллекции, массовые запросы данных, попытки изменения настроек.
3. Экспортировать журнал аудита за период, зафиксировать IP-адреса, время и характер запросов, передать материалы в службу ИБ организации.
4. После расследования — разблокировать со сбросом пароля, если инцидент не подтверждён; оставить заблокированной и завести новую учётную запись, если компрометация подтверждена.

### Обнаружение утечки данных через поиск

Признаки: необычно большое число обращений к одной коллекции, систематические запросы вида «перечисли все записи», запросы на данные вне рабочих задач пользователя.

1. Проверить журнал аудита по подозреваемому пользователю (тип: доступ к данным, результат: успех).
2. Временно отозвать доступ к коллекции.
3. Проверить журнал маскирования PII Shield — были ли в ответах обнаружены персональные данные и применено ли маскирование.
4. Эскалировать: передать экспортированные журналы в службу ИБ. При подтверждённой утечке персональных данных — уведомить ответственного за ПДн в организации согласно внутреннему регламенту и требованиям ФЗ-152: **уведомление Роскомнадзора в течение 24 часов** с момента обнаружения. Это требование закона, не рекомендация.

### Обнаружение попытки внедрения инструкций (prompt injection)

Признаки в журнале: запросы, содержащие инструкции агенту («забудь предыдущие инструкции», «действуй как», «игнорируй ограничения»); нетипичные ответы агента; запросы, пытающиеся выяснить системный промпт.

1. Найти подозрительные запросы в журнале аудита (поиск по ключевым словам вида «inject», «ignore», «system prompt»).
2. Заблокировать пользователя при подтверждении.
3. Передать команде поддержки платформы текст запросов, ответы агента и временные метки — для анализа обхода защит и, при необходимости, усиления платформенных рамок промпта.

### Классификация по серьёзности

| Уровень | Что произошло | Что делать сразу |
|---|---|---|
| Критический | Несанкционированный доступ к данным, утечка персональных данных, взлом учётной записи администратора | Немедленно изолировать платформу, сообщить руководителю ИБ, запустить план реагирования, уведомление Роскомнадзора за 24 часа при подтверждённой утечке ПДн |
| Высокий | Подозрительное поведение ассистента, аномальные запросы, сбои входа | Разобрать журнал, заблокировать подозрительную учётную запись, эскалировать |
| Средний | Ошибки доступа, предупреждения мониторинга | Разобрать метрики и журнал, сообщить администратору |
| Низкий | Технические сбои без признаков атаки | Обычная процедура устранения неполадок |

## 10. Интеграции и аутентификация

- **Корпоративный вход** — LDAP/AD, SAML 2.0, OIDC/OAuth2 (включая Azure AD, Okta, Auth0, Google, Cognito) — реализовано. Kerberos/SPNEGO — явно не поддерживается.
- Единый корпоративный вход и локальные пароли каталога — переключатель «либо/либо», не два параллельных способа одновременно; при включении единого входа локальные пароли перестают работать для всех, кроме заранее выделенных аварийных (break-glass) учётных записей. Это отдельный механизм от break-glass-пароля «Сотрудников ИБ», который продолжает работать в обход единого входа независимо.
- Авторизация для двух корпоративных доменов одновременно не поддерживается — конфигурация рассчитана на один домен.
- **SIEM** — CEF или JSON (ECS) через syslog/HTTP, с очередью повторных попыток.
- Прокси с аутентификацией — на дорожной карте поставщика; централизованное управление секретами (Vault) — также на дорожной карте, сроки уточняются у поставщика на момент внедрения.

## 12. Модель угроз

**Типы нарушителей:** внешний нарушитель высокого потенциала (целенаправленная атака, доступ только к публичным интерфейсам платформы); внутренний нарушитель — обычный пользователь (низкий/средний потенциал, попытки расширить доступ в рамках своей роли); внутренний нарушитель — администратор платформы (высокий потенциал, полный доступ к конфигурации и журналам); привилегированный пользователь/подрядчик (средний/высокий потенциал, доступ к инфраструктуре и секретам).

**Актуальные угрозы:**

| Угроза | Вектор | Контрмеры |
|---|---|---|
| Несанкционированный доступ к данным через API | Перехват/подбор токена, обход авторизации | Строгая аутентификация, короткий срок жизни токенов, аудит всех вызовов |
| Компрометация контекста ассистента (внедрение инструкций) | Инструкции в запросе, обход ограничений агента | Неизменяемая рамка системного промпта, правила на вывод, аудит запросов |
| Атака на цепочку поставок (образы, зависимости) | Компрометация базовых образов при сборке | Только образы из реестра поставщика, изолированное развёртывание, проверка хэшей и подписи |
| Утечка данных через поиск по документам | Запросы, извлекающие чужие данные из индекса | Доступ по коллекциям, пользователь видит только назначенное |
| Эскалация привилегий внутри кластера | Избыточные права служебных учётных записей | Минимальные права, изоляция рабочих нагрузок |

**Признаны неактуальными** (архитектурно исключены или вне периметра платформы): несанкционированный доступ к резервным копиям (хранятся на инфраструктуре клиента); атака на инфраструктуру/DoS (закрытый периметр без прямого выхода в интернет); внешний нарушитель низкого потенциала (нет публичных интерфейсов).

**Угрозы, специфичные для платформ с LLM:** внедрение инструкций прямое (в самом запросе) и косвенное (через содержимое проиндексированных документов, срабатывает при поиске); попытка извлечь системный промпт через многошаговый диалог; последовательное «вытягивание» данных через много запросов к поиску; попытка восстановить исходный текст из векторных представлений (архитектурно затруднена — прямого доступа к векторам без аутентификации нет).

## Глоссарий

- **Оператор ИБ / Администратор ИБ** — роли в суверенном реестре «Сотрудники ИБ»; не наследуются из корпоративного каталога.
- **PII Shield** — компонент автоматического обнаружения и маскирования персональных данных.
- **База секретов** — отдельный механизм защиты коммерческой тайны, с ручным решением PASS/REVIEW/BLOCK.
- **Построчная фильтрация (row-level security, OPA/Rego)** — автоматическое ограничение видимых строк таблиц по доменам каталога.
- **Таблица соответствий** — временное, привязанное к сессии хранилище пар «метка ↔ исходное значение»; не покидает контур.
- **pii_audit / admin_audit_log / sql_audit** — три независимых журнала аудита: LLM-сессии, привилегированные действия, SQL-запросы.
- **ФСТЭК** — регулятор, чьи приказы №17/21 задают технические требования к защите информационных систем.
- **ФЗ-152** — федеральный закон «О персональных данных»; при подтверждённой утечке требует уведомления Роскомнадзора в течение 24 часов.
- **КС2/УЗ-3** — класс защищённости и уровень защищённости персональных данных, для которого выполнена оценка соответствия в этом документе.
