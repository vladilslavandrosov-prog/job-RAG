# Руководство администратора платформы «Синапс.Инсайт»

Сводное руководство администратора, собранное из официальной документации разработчика (`docs/sources/synaps-insight/`) и находок, подтверждённых на практике по скриншотам живой системы (`aiplatform.iqi.internal`, `docs/platform/*.md`). Там, где источники расходятся, вендорский текст взят за основу, а расхождение с практикой вынесено в примечание — курсивом и с явной пометкой источника.

## 1. Архитектура в двух словах

Платформа развёртывается в изолированном периметре клиента (on-premises, поддерживается air-gap) зональным дистрибутивом из четырёх зон:

| Зона | Назначение | Ключевые компоненты | Обязательность |
|---|---|---|---|
| 0 — Фундамент | Базовый слой безопасности и доступа | PostgreSQL, pii-shield, dlp-secret (+ ib_ui), audit-service, Redis | Обязательна |
| 1 — Core | Основной функциональный слой | Qdrant, MinIO, TEI ×2 (bge-m3/jina-code), dwh, ds-workstation, agent-runtime, orchestrator, Синапс.Каталог (OpenMetadata + OpenSearch), Nginx | Обязательна, требует Зону 0 |
| 2 — Синапс.Данные | Полнотекстовый поиск и автоматический ingestion | OpenSearch, ingestion-пайплайн | Опциональна, требует только Зону 1 |
| 3 — Синапс.Агенты | Визуальный конструктор агентов и LLM-обсервабилити | LangFlow, Langfuse | Опциональна, требует только Зону 1 |

Единственная точка входа снаружи — HTTPS/443 через Nginx; все остальные порты компонентов закрыты для внешней сети. Платформа не инициирует исходящих соединений в интернет.

*В примерах вендорской документации домены даны как плейсхолдеры (`app.example.local`, `om.example.local`, `dlp.example.local`) — в реальном развёртывании это подставляется реальный домен клиента (`aiplatform.iqi.internal` в нашем случае).*

Подробный реестр компонентов, портов и версий — [`docs/sources/synaps-insight/doc4-arch.md`](../sources/synaps-insight/doc4-arch.md); порядок установки по зонам — [`doc1-install-guide.md`](../sources/synaps-insight/doc1-install-guide.md).

## 2. Пользователи, роли и права

### 2.1 Ролевая модель

Базовые роли платформы (по `docs/sources/synaps-insight/doc8-budgets-rights.md`, раздел B.1 — самый подробный из вендорских источников):

| Роль | Доступные разделы/функции |
|---|---|
| **Администратор** | Полный доступ |
| **Стюард данных (DataSteward)** | Каталог, глоссарий, политики доступа |
| **Офицер ИБ** | Управление безопасностью, аудит |
| **Создатель агентов** | Конструирование агентов |
| **FinanceOps** | Раздел «Биллинг» (опциональный модуль) |
| **Аналитик/пользователь** | Чат, документы, каталог |

Отдельно — **«Персона»**: влияет на поведение агента в чате (доступный контекст, акценты), назначается администратором.

Роль и персона назначаются администратором; пользователь не меняет их сам.

> **Примечание (расхождение с практикой, 19.08.2026).** Вендорская документация в разных местах называет разные наборы ролей (`doc3-sec-admin-guide.md` — 4 роли, `doc5-security-passport.md` — 3 роли, `doc8` — 6 ролей выше), и ни один из этих списков явно не совпадает с найденным на практике по скриншотам разделением **«Администратор» / «Оператор ИБ»** внутри отдельного экрана «Сотрудники ИБ» (`/dlp/staff/`) — см. [`administrirovanie-polzovateli.md`](administrirovanie-polzovateli.md). Наиболее вероятное объяснение: экран «Сотрудники ИБ» — это отдельный, более узкий контур допуска именно в саму админку («Рабочее место ИБ»), а роли из таблицы выше — более общая ролевая модель уровня Каталога/платформы. Это не подтверждено вендором явно и требует сверки с командой платформы перед тем, как выдавать клиенту как единую непротиворечивую картину.

### 2.2 Управление пользователями

- Пользователи заводятся администратором (создание, блокировка, смена пароля, удаление).
- При интеграции с корпоративным каталогом (AD/LDAP) пользователи входят по доменной учётной записи — единый провайдер на всех, либо LDAP, либо локальные пароли, не оба одновременно (см. `administrirovanie-polzovateli.md`, раздел про AD/LDAP).
- Блокировка — мгновенная: следующий запрос заблокированного пользователя получает 401, активные сессии не прерываются. Удаление — необратимо, требует двойного подтверждения (ввод логина + отдельная кнопка); рекомендуется блокировать, а не удалять учётные записи уволившихся — для сохранения аудиторского следа.
- Самостоятельный запрос доступа пользователем (Data Access Request) и централизованный сброс пароля администратором — в дорожной карте, ещё не реализованы.

### 2.3 Как складываются права — четыре уровня

Из `doc8-budgets-rights.md`, раздел B.4 — самое ясное объяснение модели прав в вендорской документации:

1. **Роль** → какие разделы и функции UI вообще открыты.
2. **Коллекции + домены** → какие документы и данные в области видимости.
3. **RLS / маскирование по столбцам** (раздел «Доступ», `/access`) → какие строки и столбцы внутри уже доступных данных видны, что обезличено.
4. **Маскирование ПДн в ответах** (PII Shield) → работает **всегда, поверх остального**, независимо от предыдущих уровней.

Изменения на всех уровнях применяются к запросам автоматически — пользователю не нужно учитывать это в формулировке вопроса, обойти правила через формулировку нельзя.

RLS-политики формируются автоматически из бизнес-доменов OpenMetadata (Rego-правила через OPA) и синхронизируются из каталога; редактирование напрямую через UI недоступно — только через конфигурационные файлы DevOps/SRE, с версионированием. Экран «Доступ» даёт предпросмотр («как выглядит выборка под конкретной ролью»), карту покрытия и синхронизацию — не прямое редактирование Rego.

## 3. Источники данных: коллекции

Коллекция — тематическая группа документов с собственными настройками индексации, доступа и (для кода) привязки к каталогу; одновременно коллекция = граница ACL — пользователь получает доступ к коллекции целиком (архитектурное решение ADR-01).

- **Тип коллекции** — `text` (регламенты, инструкции; индексируется bge-m3/RoSBERTa, section-aware чанкинг по умолчанию, 512 токенов/64 перекрытие) или `code` (исходники; код-эмбеддер jina-code; источник графа «код → таблица»). Задаётся при создании, не меняется.
- Домен, тип документа, тип коллекции — все неизменяемы после создания.
- Смена модели эмбеддера или стратегии чанкинга требует переиндексации коллекции; смена отображаемого имени/описания — нет.
- Системные коллекции (`is_system=true`, например «Справка») — только для чтения из UI.
- Наполнение — либо ручная загрузка через экран «Документы», либо коннектор-источник (Confluence, GitLab и т. п.) с ручной или инкрементальной синхронизацией.
- Для кодовых коллекций и связанных с ними текстовых — привязка к OM-сервису/OM-БД задаёт границу резолва имён таблиц из SQL для линеажа «код → таблица»; без привязки резолв идёт глобально по всему каталогу.

> *Подтверждено на практике (17.08.2026): при загрузке файла форма даёт выбор «Назначение» — «В коллекцию» (нужно заранее создать коллекцию) или «Личные документы» (по умолчанию, коллекция не нужна вообще — файл уходит в личное пространство, доступ определяется видимостью «Только мне» / «Команде» / «Всем»). Вендорский пользовательский гайд (`ug-03-documents.md`) описывает шаг загрузки так, будто выбор коллекции обязателен всегда — это, вероятно, упрощение в пользовательском тексте, а не отличие в поведении платформы.*

Подробнее — [`docs/sources/synaps-insight/doc6-collections.md`](../sources/synaps-insight/doc6-collections.md) и [`istochniki-dokumenty.md`](istochniki-dokumenty.md).

## 4. Провайдеры и модели

Все LLM, эмбеддеры и генераторы изображений подключаются через единый реестр «контрагент × модель» (раздел «Провайдеры», доступен только роли администратора — скрыт для оператора ИБ).

- **Контрагент (провайдер)** — внешний или локальный сервис (Anthropic, OpenAI, локальный Ollama, OpenRouter и т. п.); несёт настройки доступа, доверия и маскирования.
- **Модель** — конкретная запись под контрагентом; несёт технические параметры и стоимость.
- **Уровень доверия (`trust_tier`)**: `local` (без egress наружу), `ru_cloud` (доверенное российское облако), `external`.
- **Маскирование ПДн перед отправкой** (`pii_masking_required`) и типы маскируемых сущностей — настраиваются на уровне контрагента. **Политика по умолчанию — fail-safe**: если для модели/домена политика не найдена, маскирование считается обязательным.
- Модель появляется в чат-селекторе пользователя, когда контрагент имеет тип `cloud_llm` (или `image_generation`) **и** модель активна. Эмбеддеры в чат-селектор не попадают — выбираются только в настройках коллекций.

Подробнее — [`docs/sources/synaps-insight/doc7-providers-models.md`](../sources/synaps-insight/doc7-providers-models.md).

## 5. Защита данных: PII Shield и guard rails

PII Shield — встроенный компонент, обнаруживающий и маскирующий персональные данные в ответах агентов перед выдачей пользователю.

- Порог обнаружения по умолчанию — **0.4 (40%)**; ниже 0.3 растёт риск маскирования нечувствительных данных.
- Стратегии: **токенизация** (`PERSON_1`, `PHONE_1` и т. п., по умолчанию), псевдонимизация, полное скрытие — настраивается по типу ПД.
- **Column-aware masking** — точное маскирование по столбцам с учётом тегов ПД из каталога (назначение тегов — задача Data Steward, администратор периодически проверяет полноту разметки).
- Каждая операция маскирования журналируется в audit-service.

### Guard rails — что блокирует, а что только фиксирует

| Контроль | Режим | Компонент |
|---|---|---|
| Аутентификация (OAuth 2.0 + PKCE) | Enforcement | pii-shield |
| Защита от подбора пароля (блокировка + rate-limit) | Enforcement | OpenMetadata / pii-shield |
| RLS по бизнес-доменам; коллекция = граница доступа | Enforcement | OPA / оркестратор / Qdrant |
| Маскирование ПДн в ответах | Enforcement + Observability | pii-shield / dlp-secret |
| Контроль утечки в ответе модели (повторный скан) | Enforcement + Observability | pii-shield |
| Безопасный egress (наружу уходит только маскированное) | Enforcement | pii-shield |
| Неизменяемая рамка системного промпта | Enforcement | agent-runtime |
| Карантин недоверенного контента (защита от косвенных инъекций) | Enforcement | agent-runtime |
| SQL «только чтение» | Enforcement | оркестратор |
| Аудит LLM-сессий | Observability | audit-service (pii_audit) |
| Сигнал о попытке обхода (`security_alert`) | Observability | audit-service |
| Аудит SQL-запросов | Observability | sql_audit |
| Аудит привилегированных действий | Observability | admin_audit_log |
| Передача в SIEM | Observability | pii-shield |
| Мониторинг и оповещения | Observability | Prometheus / Grafana |
| Периметр (единая точка входа, air-gap) | Enforcement | Nginx / инфраструктура |

Встроенного в UI движка автоблокировки по правилам поверх `security_alert` нет — это в roadmap; реагирование пока — задача администратора ИБ.

Подробнее, включая полную модель угроз и таблицу соответствия ФСТЭК №17/21 (статус реализации по каждой мере) — [`docs/sources/synaps-insight/doc5-security-passport.md`](../sources/synaps-insight/doc5-security-passport.md).

## 6. Аудит и реагирование на инциденты

Три раздельных журнала в PostgreSQL, каждый со своей ролью БД без прав UPDATE/DELETE (целостность на уровне СУБД):

- **pii_audit** (LLM-сессии) — вопрос, вызовы инструментов, факт и объём маскирования. Просмотр — «Журнал LLM-сессий».
- **admin_audit_log** (привилегированные действия) — создание/деактивация учётных записей, изменение политик, аппрувы, значения «до/после».
- **sql_audit** — сгенерированный SQL, задействованные таблицы/колонки, длительность, результат.

Категории инцидентов и первичные действия:

| Категория | Признаки | Первичные действия |
|---|---|---|
| Критический (P1) | НСД к данным, утечка ПД, компрометация УЗ администратора | Немедленная изоляция, уведомление CISO, план реагирования |
| Высокий (P2) | Подозрительная активность агентов, сбои аутентификации | Анализ логов, блокировка УЗ, эскалация |
| Средний (P3) | Ошибки авторизации, предупреждения Prometheus | Анализ метрик/логов, уведомление администратора |
| Низкий (P4) | Технические сбои без признаков атаки | Стандартная процедура устранения |

**Готовые сценарии** (подробные шаги — `doc3-sec-admin-guide.md`, раздел 8): подозрение на компрометацию учётной записи; обнаружение утечки данных через RAG; обнаружение попытки prompt injection.

> При подтверждённой утечке ПД — обязательное уведомление Роскомнадзора **в течение 24 часов** с момента обнаружения (ст. 21 ФЗ-152, действует с 01.03.2023).

## 7. Бюджеты и лимиты (опциональный модуль)

Раздел «Биллинг» доступен, только если модуль установлен в поставке; доступ — роль FinanceOps или администратор.

- **Тариф** — цена модели за 1000 входящих/исходящих токенов; без тарифа стоимость не считается, но учёт токенов ведётся всегда.
- **Бюджет** ограничивает расходы в разрезе `global` / `team` / `user`, период `month` (по умолчанию) или `day`, порог оповещения по умолчанию — 80% от лимита.
- **При исчерпании бюджета** обращения к платным моделям блокируются с ответом **«Превышен бюджет» (HTTP 402)** до нового периода или повышения лимита.
- Свод расходов и счета (invoices) — экспорт в XLSX/CSV.

## 8. Резервное копирование и восстановление

| Компонент | Периодичность | Способ |
|---|---|---|
| PostgreSQL | Ежедневно | `pg_dumpall` / `pg_dump` по конкретной БД |
| Qdrant | Еженедельно (или после крупных переиндексаций) | Остановка контейнера + tar volume, либо Snapshot API без остановки |
| MinIO | Ежедневно, инкрементально | `mc mirror` в локальную директорию или внешний S3-совместимый таргет |

Резервное копирование данных на физических носителях (at rest), физическая безопасность серверов и шифрование бэкапов — ответственность клиента, не входят в периметр платформы.

## 9. Обновление платформы

Перед обновлением — обязательное резервное копирование PostgreSQL и Qdrant.

**Docker Compose:** пометить текущие образы `:prev` → загрузить новые образы → `docker compose up -d --force-recreate` → применить миграции по release notes. Откат — вернуть тег `:prev` → `:latest`, пересоздать контейнеры.

**Kubernetes:** `helm upgrade` с обновлённым `values.yaml`; откат — `helm rollback`.

## 10. Мониторинг

Prometheus + Grafana поставляются в составе дистрибутива. Grafana — порт 3000 (тот же порт по умолчанию у Langfuse из Зоны 3 — при совместном развёртывании нужно явно развести порты, вендорская документация этот потенциальный конфликт не оговаривает). Prometheus — порт 9090, при конфликте с Cockpit — 9091.

Основные таргеты: pii-shield (`:8093/metrics`), dlp-secret (`:8089/metrics`), agent-runtime и orchestrator (`:8000/metrics`), Qdrant (`:6333/metrics`), TEI (`:8099/metrics`). Production-доступ к Grafana/Prometheus — через SSH-туннель, не прямая публикация в сеть.

## 11. Известные проблемы эксплуатации

Из `docs/sources/synaps-insight/doc2a-troubleshooting.md` — 9 задокументированных случаев, симптом → причина → решение:

1. **OM-токен невалиден на свежей БД** — `/api/v1/system/version` обманчиво отвечает 200 без аутентификации; нужен переаутентифицируемый эндпоинт для проверки. Решение — переиздать токен `ingestion-bot`.
2. **firewalld блокирует межсервисный трафик** — Docker использует FORWARD, а не INPUT; решение — добавить IP смежных хостов в зону `trusted`.
3. **Эмбеддеры недоступны после смены IP** — адрес TEI прописан в двух независимых местах (env + конфиг провайдера в БД), нужно обновить оба; рекомендация — использовать DNS-имена вместо IP.
4. **OAuth redirect_uri mismatch** — pii-shield кэширует конфигурацию OAuth-клиентов в Redis, перезапуск без сброса кэша не помогает.
5. **SSO Каталога не работает** — браузер блокирует Service Worker при недоверенном TLS-сертификате; нужно добавить корневой сертификат в доверенные хранилища клиентских машин и перезапустить браузер целиком.
6. **Qdrant не запускается** — требует `ulimits nofile ≥ 65536`, системный лимит по умолчанию ниже.
7. **TEI падает с OOMKilled** — модели требуют больше памяти на пике первого запроса, чем в установившемся режиме; занижен `mem_limit`.
8. **Коллекция не индексируется** — одна из причин: TEI недоступен, модель не синхронизирована, коллекции не назначен эмбеддер, либо недоступен Qdrant — диагностика по шагам.
9. **Загрузка данных через dwh падает без внятной ошибки** — миграции Alembic не применяются автоматически при старте контейнера; без ручного `alembic upgrade head` загрузка завершается ошибкой «relation does not exist».

**Общая закономерность (случаи 1, 6, 9):** несколько сервисов «успешно» стартуют без выполнения обязательного шага инициализации (выпуск токена, ulimits, миграции), и health-check с ответом 200 может вводить в заблуждение — стоит держать это в уме при диагностике вместо того, чтобы доверять первому «зелёному» статусу.

## 12. Регулярные задачи администратора ИБ

| Периодичность | Задача |
|---|---|
| Ежедневно | Проверить алерты безопасности; просмотреть ошибки маскирования PII Shield; проверить неудачные попытки аутентификации за 24 часа |
| Еженедельно | Проверить неактивные учётные записи (нет входа более 30 дней); проверить актуальность всех учётных записей с ролью администратора |
| Ежемесячно | Аудит назначений коллекций на соответствие текущим должностям; проверить полноту тегов ПД в чувствительных коллекциях |
| Ежеквартально | Экспортировать журнал аудита за квартал в архив ИБ; проверить статус политик OPA на предмет неактивных/устаревших |
| При изменениях | При увольнении — заблокировать учётную запись в день увольнения; при смене должности — скорректировать роль и коллекции |
