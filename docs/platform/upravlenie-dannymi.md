# Раздел «Управление данными»: анализ схем и граф процедур

> Скриншоты: `Анализ схем` и `Граф процедур` — два из четырёх пунктов подраздела «Управление данными» (ещё не увидены: «Граф код→таблица», «Граф доступа»).

## Анализ схемы таблицы

Простой инструмент: поле «Таблица (FQN)» с поиском по имени/полному пути таблицы, и две кнопки — **🔑 Предпросмотр** и **▶ Запустить анализ**.

Судя по всему, это инструмент, которым система «понимает» структуру конкретной таблицы БД — колонки, типы, вероятно, генерирует описания полей. Это напрямую поддерживает текст-в-SQL пайплайн для «Data-вопросов» (см. `kalibrovka-politiki-poiska.md`): прежде чем агент сможет надёжно писать SQL-запросы к таблице, платформе нужно знать её схему, и этот экран, похоже, и есть то место, где эта схема анализируется/документируется.

FQN (Fully Qualified Name) — полный путь к таблице (обычно вида `схема.таблица` или `база.схема.таблица`), что подразумевает работу с несколькими схемами/базами одновременно — согласуется с находкой о мульти-доменности платформы (`zadachi-review-pipeline.md`): разные домены (брокер, охрана труда, кредитный риск), скорее всего, лежат в разных схемах/базах, и этот инструмент — то, чем администратор регистрирует/анализирует каждую из них по отдельности.

## Граф процедур (lineage)

Инструмент отслеживания **lineage** (происхождения/связей) хранимых процедур — какая процедура что вызывает, от каких таблиц зависит.

### Элементы экрана

| Элемент | Назначение |
|---|---|
| Дропдаун «(нет сервисов в ОМ)» | Выбор источника/сервиса из «ОМ» (вероятно, «Объектная модель» или «Операционная модель») — на скриншоте не настроено ни одного |
| **↻ Обновить** | Обновить отображаемые данные |
| «Свежесть» | Карточка (пустая на скриншоте) — вероятно, показывает, насколько давно граф пересчитывался |
| «Переизвлечение» | Запуск пересчёта графа |
| ☑ «только устаревшие/новые (инкремент по hash; без изменений → no-op)» | Инкрементальный режим: пересчитывать только то, что изменилось (по хэшу), не трогая неизменившиеся процедуры — экономит время на переизвлечении |
| **Переизвлечь граф** | Кнопка запуска |
| «Покрытие (из последнего извлечения)» | Показывает, какая доля процедур покрыта анализом — пока «Нет данных, запустите переизвлечение» |

### Наблюдение

Инкрементальный принцип «по hash, без изменений → no-op» — то же самое проектное решение, что и в НФТ ТЗ для инкрементальной синхронизации данных (раздел 3.1, ≤15 минут для обновлений за сутки), только применённое здесь к анализу кода/процедур, а не к документам. Это говорит о последовательной архитектурной практике: инкрементальность через хэш применяется на нескольких уровнях платформы, не только к документам.

Связь с разделом «Политики поиска»: чанки класса `код-процедур-шум` / `процедура-документация-шум` (см. `kalibrovka-politiki-poiska.md`) — это, вероятно, как раз контент, извлечённый этим самым графом процедур, проиндексированный и затем отфильтрованный/поднятый политиками ранжирования в зависимости от интента запроса. То есть «Граф процедур» — это, похоже, источник данных, а «Политики поиска» — потребитель, который решает, насколько эти данные уместны в конкретном ответе.

## Открытые вопросы

- Что такое «ОМ» (объектная/операционная модель) и почему в примере «нет сервисов в ОМ» — это значит, что источник процедур ещё не подключён?
- Как выглядит заполненный граф — можно ли увидеть визуализацию связей процедур, или это только текстовые метрики покрытия?
- Что покажет «Анализ схем» после запуска — просто список колонок, или сгенерированные текстовые описания для использования в RAG?
- Как соотносятся «Граф процедур», «Граф код→таблица» и «Граф доступа» (два последних ещё не увидены) — это разные графы одной и той же lineage-системы, или независимые инструменты?
