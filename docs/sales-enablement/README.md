# Методика продаж «ИИ-Платформа» — разбор внутреннего материала

Источник — загруженный сейлз-энейблмент лендинг (`source/index.html`, ~590 строк, полностью автономный HTML) плюс сопутствующий `source/robots.txt`. Это внутренний учебный материал для сейлз-менеджеров: структура питча, аргументы для встречи с клиентом, кейсы внедрений, инструкции по подготовке живого демо и готовый разбор возражений. Ссылки на `images/*` и `videos/video{1..4}.mp4` в файле не разрешаются — сами медиа не были частью загрузки, сохранён только HTML/CSS-каркас страницы.

Важная оговорка: страница нигде не называет продукт «Синапс.Инсайт» — везде используется общее название «ИИ-Платформа» с блоками AI Gateway / Данные и поиск / Безопасность / Развёртывание. Это может быть либо тот же продукт под маркетинговым именем, либо более широкая продуктовая линейка вендора, частью которой является «Синапс.Инсайт». Материал сам по себе не даёт однозначного ответа — см. открытый вопрос ниже.

## Структура лендинга

- **Обложка / «Знакомо?»** — сравнение «обычный чат» vs «корпоративный ИИ» (не видит документы / данные уходят наружу vs работает с данными компании в защищённом контуре).
- **«Почему так происходит»** — 6-шаговый цикл согласований (ИТ → бюджет → безопасность → серверы → внедрение → поддержка), который платформа призвана сократить.
- **Целевая архитектура** — «Ваши данные → Платформа (единый ИИ-слой / семантический слой) → Сценарии»; тезис, что 80–90% результата зависит от качества настройки семантического слоя (как система понимает термины «выручка», «клиент», «отгрузка» именно у конкретного заказчика).
- **Что входит в платформу** — 4 компонента: **AI Gateway** (единая точка всех ИИ-запросов компании, выбор модели под задачу, контроль расходов), **Данные и поиск** (поиск по документам с учётом прав доступа и источника), **Безопасность** (маскирование чувствительных данных перед отправкой в облако, разграничение по ролям, полное протоколирование запросов), **Развёртывание** (on-premise/облако/гибрид, наращивание сценариев без переделки).
- **Что решает** — вопросы к данным без SQL (text-to-SQL), поиск по документам со ссылкой на источник, «агенты-исполнители» (действие, а не только ответ).
- **ROI-аргумент** — инфраструктура строится один раз, каждый следующий сценарий дешевле предыдущего.
- **Кейсы клиентов** — Московская биржа (агенты код-ревью/контроля зависимостей), Солид (поисковый ассистент по документации), **МКБ + Veai** (3 пилота: performance review инженеров, анализ падений автотестов, разбор XML), AXIOM JDK (генерация тестов), отдельный блок **Сбер НПФ + Veai** (JetBrains-плагин, вдвое быстрее юнит-тесты).
- **«Кому подходит / не подходит»** — платформа явно позиционируется как избыточная для разовой изолированной задачи.
- **4 видеоинструкции по демо** — см. ниже, прямое подтверждение методики `docs/demo-retail/`.
- **FAQ по возражениям** — 5 тематических блоков: семантический слой, безопасность, доступ и роли, команда/инфраструктура, оплата.

## Значимая новая информация для этой базы знаний

### 1. «Veai» — новый факт, обновляет открытый вопрос в `otkrytye-voprosy.md`

FAQ по оплате прямо отвечает на два вопроса:

> «Как платить в рублях?» — Через партнёра Veai. Скидка до 40%, один счёт.
> «Данные идут через Veai?» — Нет, Veai — только биллинг.

При этом в разделе кейсов Veai фигурирует не только как биллинговый партнёр, а как соисполнитель самих пилотов («МКБ **+ Veai**», «Сбер НПФ **+ Veai**»). Это меняет прежнюю гипотезу: «veai» — не столько «команда/тег окружения», сколько **имя партнёра-интегратора**, который одновременно (а) участвует во внедрении конкретных сценариев и (б) обеспечивает биллинговый шлюз для оплаты иностранных LLM-провайдеров в рублях. Применительно к селектору модели в чате (`OpenAI/gpt-5.4 · veai`, см. `docs/platform/chat.md`) это лучше всего объясняет суффикс как метку **AI Gateway/биллингового прокси**, через который реально проходит вызов облачной модели — то есть ближе к варианту A исходного вопроса (внутренний шлюз), но с явно подтверждённой биллинговой функцией, а не только маршрутизацией.

Статус вопроса в `otkrytye-voprosy.md`: обновлён с полностью открытого на «прояснено косвенно, не подтверждено напрямую командой платформы» — сама расшифровка/устройство «veai» разгадана правдоподобно, но это внешний общий материал по продажам, а не документация конкретно «Синапс.Инсайт», поэтому 100%-го подтверждения по-прежнему нет.

### 2. Комплаенс-вопрос не снят, а заострён

FAQ по безопасности прямо описывает архитектуру: *«Перед тем как запрос уходит в облачную модель, встроенный фильтр вырезает из текста всё чувствительное… Фильтр понимает смысл, а не просто ищет по шаблону.»*

Это прямое подтверждение, что **запросы реально уходят во внешнее облако** (иначе фильтрация «перед отправкой в облачную модель» была бы бессмысленной формулировкой) — платформа полагается на контекстно-осознанное маскирование данных перед отправкой, а не на физическое неразмыкание периметра. Для критерия приёмки №8 ТЗ (раздел 3.2, «данные не должны покидать периметр компании», см. `docs/analysis/case-02-tz-deep-analysis-and-proposals.md`, п. 1.1) это значимое уточнение: «не покидает периметр» в реальной архитектуре вендора, по-видимому, означает «не покидает периметр **в чувствительном виде**», а не «вызовов внешних API нет вообще». Это может быть приемлемым решением с точки зрения комплаенса — распространённый паттерн для корпоративных ИИ-гейтвеев, — но это **другое** требование, чем буквальная формулировка критерия №8, и разницу стоит явно сверить с клиентом/командой платформы, а не считать вопрос закрытым.

### 3. Подтверждение методики `docs/demo-retail/`

Видео-раздел лендинга описывает пошаговый процесс подготовки живого демо:
1. Убедиться, что в системе создана нужная коллекция документов под кейс (пример — коллекция «Автозавод»).
2. Загрузить набор документов из заранее подготовленного бизнес-кейса — платформа принимает разные форматы: регламенты, оргструктуры, таблицы, инструкции.
3. Открыть новый чат и самостоятельно позадавать вопросы из документов кейса до встречи с клиентом.
4. Кейсы организованы по одной папке на отрасль — на встрече выбирается кейс, ближе всего к бизнесу клиента; если подходящего кейса нет — обратиться к аналитику заранее с чёткими вводными (клиент, отрасль, документы, задачи).

Это **точно совпадает** с тем, как был построен пакет `docs/demo-retail/dataset/` (папки-коллекции по сценариям, реальные Word/Excel-документы для загрузки, вопросы для проверки в новом чате) — то есть работа над ретейл-кейсом велась в соответствии с реальной внутренней методикой продаж, а не абстрактно. Пакет для «ТоргЛайн» — по сути точный аналог примера «Автозавод» из видео, только для отрасли ретейла.

### 4. Прочее, для справки

- Список клиентских кейсов (Мосбиржа, Солид, МКБ, AXIOM JDK, Сбербанк НПФ) — полезный референсный контекст при подготовке питча ретейлеру («у кого уже работает»), самостоятельной технической ценности для разбора RAG-агента не несёт.
- Тезис «80–90% результата зависит от качества семантического слоя» согласуется с находками этой базы про роутинг/политики поиска/шаблоны (`docs/platform/kalibrovka-politiki-poiska.md`) — успех сильно завязан на тонкой настройке, а не только на самой модели.

## Открытый вопрос, добавленный этим материалом

**«ИИ-Платформа» из методики продаж и «Синапс.Инсайт» — один и тот же продукт под разными именами, или разные продукты одного вендора?** Прямых текстовых пересечений (общее имя, общий скриншот интерфейса) в лендинге нет — совпадают только сами возможности (AI Gateway, поиск по данным с учётом прав, маскирование). Стоит сверить напрямую с командой платформы.
