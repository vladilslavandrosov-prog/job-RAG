**#1 OM-токен невалиден на свежей базе данных**

  -----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------
  **Симптом:** Запросы к агентам возвращают ошибки, связанные с OpenMetadata. Сервисы orchestrator или pii-shield пишут в лог «Invalid token» или «401 Unauthorized». При этом curl GET /api/v1/system/version возвращает 200 --- это вводит в заблуждение.

  -----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------

  ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------
  **Причина:** После развёртывания на свежей базе данных OpenMetadata токен ingestion-bot не существует в БД. GET /api/v1/system/version не требует аутентификации и всегда возвращает 200 независимо от состояния токена. Токен из старой инсталляции или env-шаблона невалиден для новой БД.

  ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------

**Решение:**

Проверить симптом через аутентифицируемый эндпоинт:

+-----------------------------------------------------------------------+
| curl -s -o /dev/null -w \'%{http_code}\' \\                           |
|                                                                       |
| -H \'Authorization: Bearer \${OPENMETADATA_TOKEN}\' \\                |
|                                                                       |
| http://openmetadata-server:8585/api/v1/metadata/types/name/aiApplication |
|                                                                       |
| \# 401 → токен невалиден, нужен reissue                               |
|                                                                       |
| \# 200 → токен валиден, проблема в другом                             |
+-----------------------------------------------------------------------+

Выпустить новый токен (подробная процедура --- Руководство администратора, раздел 3.3):

+-----------------------------------------------------------------------------------+
| \# Получить зашифрованный токен из БД                                             |
|                                                                                   |
| docker compose exec postgres psql -U openmetadata_user -d openmetadata_db -tAc \\ |
|                                                                                   |
| \"SELECT json-\>\'authenticationMechanism\'-\>\'config\'-\>\>\'JWTToken\'         |
|                                                                                   |
| FROM user_entity WHERE name=\'ingestion-bot\'\"                                   |
|                                                                                   |
| \# Расшифровать через скрипт в образе pii-shield                                  |
|                                                                                   |
| bash /opt/synapse/om-bootstrap/issue-pat.sh                                       |
|                                                                                   |
| \# Обновить в env-файлах и перезапустить сервисы                                  |
|                                                                                   |
| \# OPENMETADATA_TOKEN и PII_MCP_DEFAULT_TOKEN --- оба нужно обновить              |
|                                                                                   |
| docker compose up -d \--force-recreate pii-shield orchestrator agent-runtime      |
+-----------------------------------------------------------------------------------+

  ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------
  **Как не допустить:** Включить проверку OM-токена в smoke-тест после каждого развёртывания на свежей БД. Использовать аутентифицируемый эндпоинт /api/v1/metrics/types/name/aiApplication, не /api/v1/system/version. Занести процедуру reissue в чеклист первого запуска.

  ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------

**#2 firewalld блокирует межсервисный трафик**

  -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------
  **Симптом:** Сервисы app-стека не могут подключиться к сервисам на другом хосте (например, agent-runtime не достигает TEI-эмбеддеров на отдельном сервере). Прямой curl между хостами зависает или возвращает Connection refused. При этом ping между хостами проходит.

  -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------

  ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------
  **Причина:** Docker использует цепочку FORWARD и DNAT для маршрутизации трафика контейнеров. firewalld по умолчанию блокирует FORWARD-трафик. Добавление правила на INPUT (\--add-port или rich-rule на input) не помогает --- Docker-трафик через INPUT не проходит. Проблема проявляется при размещении компонентов на разных хостах в одной подсети.

  ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------

**Решение:**

+-----------------------------------------------------------------------+
| \# Добавить исходящий IP в зону trusted                               |
|                                                                       |
| \# (заменить 192.168.X.X на реальный IP сервера-источника трафика)    |
|                                                                       |
| firewall-cmd \--permanent \--zone=trusted \--add-source=192.168.X.X   |
|                                                                       |
| firewall-cmd \--reload                                                |
|                                                                       |
| \# Проверить, что правило применилось                                 |
|                                                                       |
| firewall-cmd \--zone=trusted \--list-sources                          |
|                                                                       |
| \# Проверить связность                                                |
|                                                                       |
| curl -s http://REMOTE_HOST:8099/health                                |
+-----------------------------------------------------------------------+

  -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------
  **Примечание:** Rich-rule на зоне public с \--add-port работает только для трафика, адресованного напрямую хосту (INPUT). Docker-контейнеры используют FORWARD --- для них нужен trusted-source или явное разрешение FORWARD в firewalld.

  -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------

  -----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------
  **Как не допустить:** При многохостовом развёртывании заранее добавить IP всех хостов платформы в зону trusted на каждом узле. Включить проверку связности между хостами в чеклист развёртывания до запуска сервисов.

  -----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------

**#3 Эмбеддеры недоступны после смены IP сервера**

  -----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------
  **Симптом:** Индексирование коллекций падает с ошибкой подключения к эмбеддеру. В логах agent-runtime или orchestrator --- Connection refused или timeout на старый IP. Провайдеры эмбеддеров в интерфейсе администратора показывают статус «недоступен».

  -----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------

  ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------
  **Причина:** IP-адрес сервера с TEI-сервисами (bge-m3, jina-code) изменился --- например, после переналива виртуальной машины или изменения сетевой конфигурации. Адрес TEI прописан в env-переменных и/или в конфигурации провайдеров эмбеддеров в БД платформы. Оба места необходимо обновить независимо друг от друга.

  ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------

**Решение:**

Шаг 1. Обновить IP в env-файлах (все файлы, где упоминается старый IP):

+------------------------------------------------------------------------------+
| \# Найти все вхождения старого IP в конфигах                                 |
|                                                                              |
| grep -r \'192.168.OLD.IP\' /opt/synapse/app/envs/ /opt/synapse/data/         |
|                                                                              |
| \# Заменить во всех найденных файлах                                         |
|                                                                              |
| sed -i \'s/192.168.OLD.IP/192.168.NEW.IP/g\' /opt/synapse/app/envs/\*.env    |
|                                                                              |
| \# Перезапустить затронутые сервисы                                          |
|                                                                              |
| docker compose up -d \--force-recreate agent-runtime orchestrator pii-shield |
+------------------------------------------------------------------------------+

Шаг 2. Обновить адрес провайдера в интерфейсе платформы:

-   Настройки → Провайдеры → \[провайдер TEI\] → Редактировать → обновить base_url

-   Выполнить синхронизацию моделей: Провайдеры → \[провайдер\] → Синхронизировать модели

Шаг 3. Проверить доступность TEI напрямую:

+-----------------------------------------------------------------------+
| curl -s http://192.168.NEW.IP:8099/health                             |
|                                                                       |
| \# Ожидается: {\"status\": \"ok\"}                                    |
|                                                                       |
| curl -s http://192.168.NEW.IP:8100/health                             |
|                                                                       |
| \# Ожидается: {\"status\": \"ok\"}                                    |
+-----------------------------------------------------------------------+

  -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------
  **Как не допустить:** Использовать DNS-имена вместо IP-адресов для всех межсервисных соединений там, где это возможно. Для TEI на выделенном хосте --- зарегистрировать A-запись в локальном DNS или /etc/hosts на всех хостах платформы. При изменении IP автоматически обновляется только DNS, env-файлы не требуют правки.

  -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------

**#4 OAuth redirect_uri mismatch**

  --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------
  **Симптом:** После входа по OAuth браузер возвращает ошибку «redirect_uri mismatch» или «invalid_request». Логин через OAuth полностью не работает. Проблема появляется после изменения домена платформы или правки pii-shield.config.yml.

  --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------

  ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------
  **Причина:** pii-shield кэширует конфигурацию OAuth-клиентов в Redis (ключи oauth_client:\* и pii:config:canonical_hash). После изменения redirect_uris в конфигурационном файле сервис продолжает использовать старые значения из кэша до явного его сброса. Перезапуск контейнера без сброса кэша не помогает --- кэш сохраняется в Redis между перезапусками.

  ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------

**Решение:**

+-----------------------------------------------------------------------+
| \# 1. Убедиться, что redirect_uris в pii-shield.config.yml обновлены  |
|                                                                       |
| grep -A5 \'redirect_uris\' /opt/synapse/app/pii-shield.config.yml     |
|                                                                       |
| \# 2. Сбросить кэш OAuth в Redis                                      |
|                                                                       |
| docker compose exec redis redis-cli -n 1 DEL \\                       |
|                                                                       |
| oauth_client:synapse-shell \\                                         |
|                                                                       |
| oauth_client:dlp-secret \\                                            |
|                                                                       |
| pii:config:canonical_hash                                             |
|                                                                       |
| \# 3. Перезапустить pii-shield                                        |
|                                                                       |
| docker compose restart pii-shield                                     |
|                                                                       |
| \# 4. Проверить логин                                                 |
+-----------------------------------------------------------------------+

  -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------
  **Примечание:** Ключи в Redis могут отличаться, если имена OAuth-клиентов в конфигурации нестандартные. Полный список ключей: docker compose exec redis redis-cli -n 1 KEYS \'oauth_client:\*\'

  -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------

  -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------
  **Как не допустить:** При смене домена или изменении redirect_uris всегда выполнять сброс Redis-кэша как обязательный шаг --- включить его в чеклист изменения конфигурации OAuth. Не проверять результат по логину без предварительного сброса кэша.

  -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------

**#5 SSO каталога OpenMetadata не работает**

  ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------
  **Симптом:** Пользователи открывают om.example.local, видят страницу каталога, но автоматический вход (SSO) не происходит. В консоли браузера --- ошибки Service Worker: «Failed to register» или «SSL certificate error». Ручной логин через форму работает, SSO --- нет.

  ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------

  ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------
  **Причина:** Service Worker (механизм SSO в OpenMetadata) не регистрируется в браузере, если TLS-сертификат сервера не является доверенным. Браузер блокирует регистрацию Service Worker для источников с ненадёжным сертификатом --- даже если пользователь нажал «принять риск» для основного домена.

  ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------

**Решение:**

На клиентской машине добавить корневой сертификат УЦ в доверенное хранилище:

+-----------------------------------------------------------------------+
| \# macOS:                                                             |
|                                                                       |
| sudo security add-trusted-cert -d -r trustRoot \\                     |
|                                                                       |
| -k /Library/Keychains/System.keychain /path/to/ca.crt                 |
|                                                                       |
| \# Windows (PowerShell от администратора):                            |
|                                                                       |
| Import-Certificate -FilePath C:\\path\\to\\ca.crt \\                  |
|                                                                       |
| -CertStoreLocation Cert:\\LocalMachine\\Root                          |
|                                                                       |
| \# Linux (Debian/Ubuntu):                                             |
|                                                                       |
| sudo cp ca.crt /usr/local/share/ca-certificates/synapse-ca.crt        |
|                                                                       |
| sudo update-ca-certificates                                           |
|                                                                       |
| \# Linux (RHEL/Rocky/AltLinux):                                       |
|                                                                       |
| sudo cp ca.crt /etc/pki/ca-trust/source/anchors/synapse-ca.crt        |
|                                                                       |
| sudo update-ca-trust                                                  |
+-----------------------------------------------------------------------+

После добавления сертификата --- полностью перезапустить браузер (не просто вкладку). Проверить, что Service Worker зарегистрирован: DevTools → Application → Service Workers.

  ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------
  **Как не допустить:** В корпоративной среде использовать сертификат от корпоративного УЦ, предустановленного на рабочих станциях сотрудников. При выдаче самоподписанного сертификата для пилота --- добавить инструкцию по установке CA в пакет документов для тестеров. Сертификат должен покрывать все домены платформы (SAN: app.\*, om.\*, dlp.\*).

  ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------

**#6 Qdrant не запускается**

  -----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------
  **Симптом:** Контейнер qdrant циклически перезапускается (статус Restarting) или сразу завершается с exit code 1. В логах: «Too many open files» или «ulimit: can\'t set file limit». docker compose ps показывает qdrant в состоянии (Restarting).

  -----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------

  ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------
  **Причина:** Qdrant требует высокий лимит на количество открытых файловых дескрипторов (nofile ≥ 65536). Системный лимит по умолчанию на большинстве дистрибутивов --- 1024 или 4096. Docker наследует лимиты хоста, если они не переопределены явно в docker-compose.yml через ulimits.

  ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------

**Решение:**

Проверить текущие лимиты хоста:

+-----------------------------------------------------------------------+
| ulimit -n                                                             |
|                                                                       |
| \# Если \< 65536 --- нужно исправить                                  |
+-----------------------------------------------------------------------+

Вариант 1 --- задать ulimits в docker-compose.yml (рекомендуется):

+-----------------------------------------------------------------------+
| \# /opt/synapse/data/docker-compose.yml                               |
|                                                                       |
| services:                                                             |
|                                                                       |
| qdrant:                                                               |
|                                                                       |
| image: qdrant/qdrant:v1.13.6                                          |
|                                                                       |
| ulimits:                                                              |
|                                                                       |
| nofile:                                                               |
|                                                                       |
| soft: 65536                                                           |
|                                                                       |
| hard: 65536                                                           |
+-----------------------------------------------------------------------+

Вариант 2 --- поднять лимит на уровне хоста:

+-----------------------------------------------------------------------------------------+
| \# /etc/security/limits.conf                                                            |
|                                                                                         |
| \* soft nofile 65536                                                                    |
|                                                                                         |
| \* hard nofile 65536                                                                    |
|                                                                                         |
| \# После правки --- перелогиниться или перезагрузить хост                               |
|                                                                                         |
| \# Для Docker daemon также добавить в /etc/systemd/system/docker.service.d/limits.conf: |
|                                                                                         |
| \[Service\]                                                                             |
|                                                                                         |
| LimitNOFILE=65536                                                                       |
|                                                                                         |
| systemctl daemon-reload && systemctl restart docker                                     |
+-----------------------------------------------------------------------------------------+

  ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------
  **Как не допустить:** Всегда задавать ulimits для Qdrant явно в docker-compose.yml --- это надёжнее системных настроек и не зависит от конфигурации хоста. Включить проверку ulimits в чеклист подготовки хоста перед развёртыванием.

  ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------

**#7 Контейнер TEI падает с OOMKilled**

  ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------
  **Симптом:** Контейнер сервиса tei-bge-m3 или tei-jina-code внезапно останавливается. docker inspect \<container\> показывает OOMKilled: true. Сервис перезапускается, но через некоторое время падает снова. Эмбеддинги недоступны, индексирование прерывается.

  ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------

  ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------
  **Причина:** Модели TEI (bge-m3: \~2.5 ГБ, jina-code: \~1.5 ГБ) загружают веса в RAM/VRAM при старте. Если контейнеру выставлен жёсткий лимит памяти (mem_limit в compose или limits.memory в K8s) ниже необходимого --- ядро Linux убивает процесс через OOM Killer. Пиковое потребление при первом запросе выше, чем в установившемся состоянии.

  ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------

**Решение:**

Проверить факт OOM и потребление памяти:

+-----------------------------------------------------------------------+
| \# Проверить OOMKilled                                                |
|                                                                       |
| docker inspect tei-bge-m3 \| grep -i oom                              |
|                                                                       |
| \# Посмотреть текущее потребление                                     |
|                                                                       |
| docker stats tei-bge-m3 tei-jina-code \--no-stream                    |
+-----------------------------------------------------------------------+

Убрать или поднять лимит памяти в docker-compose.yml:

+-----------------------------------------------------------------------+
| \# /opt/synapse/data/docker-compose.yml или отдельный compose TEI     |
|                                                                       |
| services:                                                             |
|                                                                       |
| tei-bge-m3:                                                           |
|                                                                       |
| \# Убрать mem_limit если он выставлен, или поднять:                   |
|                                                                       |
| mem_limit: 8g \# не менее 4g для bge-m3                               |
|                                                                       |
| memswap_limit: 8g                                                     |
|                                                                       |
| tei-jina-code:                                                        |
|                                                                       |
| mem_limit: 4g \# не менее 3g для jina-code                            |
|                                                                       |
| memswap_limit: 4g                                                     |
+-----------------------------------------------------------------------+

  ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------
  **Примечание:** Ориентировочные минимальные требования к RAM: bge-m3 (dim 1024) --- 4 ГБ, jina-code (dim 768) --- 3 ГБ. При использовании GPU потребление RAM снижается, но требуется VRAM соответствующего объёма.

  ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------

  ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------
  **Как не допустить:** Не выставлять mem_limit для контейнеров TEI без предварительного измерения реального потребления через docker stats под нагрузкой. Закладывать 1.5× от наблюдаемого пика. Мониторить метрику container_memory_usage_bytes в Prometheus с alerting-порогом 80% от лимита.

  ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------

**#8 Коллекция не индексируется**

  -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------
  **Симптом:** Запуск индексирования коллекции через UI или API завершается с ошибкой или зависает. В разделе Задачи статус задачи --- «Ошибка» или задача не появляется вовсе. Семантический поиск по коллекции не возвращает результатов.

  -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------

  -----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------
  **Причина:** Одна из нескольких причин: (1) сервис TEI-эмбеддера недоступен --- не запущен или неверный адрес; (2) модель не синхронизирована после регистрации провайдера; (3) коллекции не назначена эмбеддинговая модель; (4) Qdrant недоступен.

  -----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------

**Решение:**

Диагностика по шагам:

+------------------------------------------------------------------------------------+
| \# 1. Проверить доступность Qdrant                                                 |
|                                                                                    |
| curl -s http://qdrant:6333/readyz                                                  |
|                                                                                    |
| \# Ожидается: HTTP 200                                                             |
|                                                                                    |
| \# 2. Проверить доступность TEI-эмбеддеров                                         |
|                                                                                    |
| curl -s http://TEI_HOST:8099/health \# bge-m3                                      |
|                                                                                    |
| curl -s http://TEI_HOST:8100/health \# jina-code                                   |
|                                                                                    |
| \# 3. Посмотреть логи orchestrator (задачи индексирования)                         |
|                                                                                    |
| docker compose logs \--tail=50 orchestrator \| grep -i \'embed\\\|index\\\|error\' |
|                                                                                    |
| \# 4. Проверить статус задачи через API                                            |
|                                                                                    |
| curl -s https://app.example.local/api/v1/admin/tasks \\                            |
|                                                                                    |
| -H \'Authorization: Bearer \${ADMIN_TOKEN}\' \| python3 -m json.tool               |
+------------------------------------------------------------------------------------+

Если эмбеддер доступен, но модель не синхронизирована:

-   Настройки → Провайдеры → \[провайдер\] → Синхронизировать модели

-   Убедиться, что коллекции назначена модель: Источники → \[коллекция\] → Настройки эмбеддинга

  ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------
  **Как не допустить:** После регистрации нового провайдера эмбеддеров всегда выполнять синхронизацию моделей до запуска индексирования. Добавить в smoke-тест проверку доступности всех TEI-эндпоинтов. Назначение модели коллекции --- обязательный шаг при создании коллекции, не пропускать.

  ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------

**#9 Загрузка данных через dwh падает без внятной ошибки**

  ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------
  **Симптом:** Попытка загрузить данные через модуль dwh не приводит к результату: задача создаётся, но зависает или завершается без сообщения об ошибке в UI. В логах dwh-backend присутствуют ошибки вида «relation does not exist» или «column X of relation Y does not exist».

  ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------

  ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------
  **Причина:** Контейнер dwh-backend запускается успешно даже без применения миграций базы данных --- entrypoint не выполняет alembic upgrade head автоматически. Схема БД при этом отсутствует или устарела. Ошибка проявляется только при первой попытке использовать функциональность загрузки данных.

  ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------

**Решение:**

Проверить статус миграций:

+------------------------------------------------------------------------------+
| docker compose exec dwh-backend sh -c \'cd /app && alembic current\'         |
|                                                                              |
| \# Если вывод пустой или показывает старую ревизию --- миграции не применены |
+------------------------------------------------------------------------------+

Применить миграции:

+---------------------------------------------------------------------------+
| docker compose exec dwh-backend sh -c \'cd /app && alembic upgrade head\' |
|                                                                           |
| \# Ожидается: Running upgrade \... -\> \<hash\>, OK                       |
|                                                                           |
| \# Проверить итоговую ревизию                                             |
|                                                                           |
| docker compose exec dwh-backend sh -c \'cd /app && alembic current\'      |
+---------------------------------------------------------------------------+

Проверить результат --- повторить загрузку данных через UI или API.

  ------------------------------------------------------------------------------------------------------------------
  **Результат:** После успешного применения миграций загрузка данных должна заработать без перезапуска контейнера.

  ------------------------------------------------------------------------------------------------------------------

  ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------
  **Как не допустить:** Включить применение миграций dwh в чеклист первого запуска как обязательный шаг сразу после старта контейнера. При обновлении платформы также проверять необходимость применения новых миграций согласно release notes. Рассмотреть добавление проверки alembic current в скрипт smoke-тестов.
