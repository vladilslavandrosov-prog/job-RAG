## Область ответственности

Администратор безопасности платформы отвечает за управление доступом пользователей, контроль политик безопасности и аудит событий. Все операции выполняются через интерфейс платформы без прямого доступа к инфраструктуре.

  --------------------------- ----------------------------------------------------------- -----------------------------------------------
  **Зона ответственности**    **Что включает**                                            **Что НЕ включает**

  Управление доступом         Пользователи, роли, коллекции, политики OPA                 Инфраструктура, сетевые правила, firewall

  Аудит и мониторинг          Журналы событий, операции с ПД, активность пользователей    Системные логи Docker/K8s, метрики Prometheus

  Защита данных               Настройки PII Shield, теги ПД, пороги обнаружения           Шифрование носителей, резервное копирование

  Реагирование на инциденты   Блокировка пользователей, экспорт логов аудита, эскалация   Восстановление системы, обновление платформы
  --------------------------- ----------------------------------------------------------- -----------------------------------------------

  -----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------
  **Примечание:** Настройка инфраструктуры, резервное копирование и обновление платформы --- ответственность DevOps/SRE. Документ для них: Руководство администратора (Документ 2).

  -----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------

## Вход в систему и интерфейс

### 2.1 Вход

**1. Открыть браузер и перейти по адресу платформы**

Адрес платформы предоставляется при первичной настройке: https://app.example.local/ (заменить на фактический домен).

**2. Ввести учётные данные и выполнить вход**

Используйте учётную запись с ролью admin, выданную при установке платформы. При первом входе рекомендуется сменить пароль.

  ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------
  **⚠ Внимание:** Учётная запись администратора безопасности не должна использоваться для аналитических запросов к данным. Для анализа данных заведите отдельную учётную запись с ролью analyst.

  ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------

### 2.2 Структура интерфейса

После входа доступны следующие разделы боковой навигации:

  --------------------------- -------------------------------------------------- ---------------------
  **Раздел**                  **Назначение**                                     **Доступен ролям**

  Чат / Аналитика             Диалоговые запросы к данным                        analyst, viewer

  Источники данных            Управление коллекциями и индексами                 admin, analyst

  ib_ui → «Пользователи и доступ»    Управление учётными записями                       admin

  Настройки → Роли и доступ   Управление ролями и политиками                     admin

  Настройки → PII Shield      Настройка защиты персональных данных               admin

  Настройки → Политики OPA    Просмотр и управление политиками авторизации       admin

  Аудит                       Журнал событий безопасности и операций с данными   admin
  --------------------------- -------------------------------------------------- ---------------------

## Управление пользователями

### 3.1 Просмотр списка пользователей

  -----------------------------------------------------------------------
  **Путь:** ib_ui → «Пользователи и доступ»

  -----------------------------------------------------------------------

Таблица пользователей показывает: имя, email, роль, статус (активен / заблокирован), дату последнего входа, назначенные коллекции.

  -----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------
  **💡 Совет:** Используйте фильтр по роли и статусу для быстрого поиска. Колонка «Последний вход» помогает выявить неактивные учётные записи, которые следует заблокировать или удалить.

  -----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------

### 3.2 Создание пользователя

  -----------------------------------------------------------------------
  **Путь:** ib_ui → «Пользователи и доступ» → Добавить пользователя

  -----------------------------------------------------------------------

**1. Заполнить обязательные поля**

  ------------------ --------------------------------------------------- ---------------------
  **Поле**           **Описание**                                        **Пример**

  Имя пользователя   Уникальный логин; только латиница, цифры, \_        ivanov_as

  Email              Корпоративный адрес; используется для уведомлений   ivanov@company.ru

  Роль               Выбрать из списка: admin / DS / ИБ / аналитик        аналитик

  Подразделение      Опционально; для группировки и аудита               Отдел аналитики
  ------------------ --------------------------------------------------- ---------------------

**2. Назначить коллекции (для ролей analyst и viewer)**

В разделе «Доступ к данным» выбрать коллекции из списка доступных. Пользователь получит доступ только к выбранным коллекциям --- других данных он не увидит.

**3. Сохранить**

Учётная запись создаётся в разделе «Пользователи и доступ». Аутентификация пользователя выполняется через корпоративный вход (OAuth) --- отдельный пароль на стороне платформы не создаётся. Самостоятельный запрос доступа пользователем (Data Access Request, DAR) --- в дорожной карте.

### 3.3 Блокировка и разблокировка пользователя

  -----------------------------------------------------------------------
  **Путь:** ib_ui → «Пользователи и доступ» → \[пользователь\] → Действия

  -----------------------------------------------------------------------

Блокировка немедленно завершает все активные сессии пользователя и запрещает новые входы. Данные пользователя и история запросов сохраняются.

**1. Открыть карточку пользователя**

**2. Нажать «Заблокировать» → подтвердить действие**

**3. Убедиться, что статус изменился на «Заблокирован»**

  ------------------------------------------------------------------------------------------------------------------------------------------------------------------
  **Примечание:** Блокировка применяется мгновенно: следующий запрос заблокированного пользователя получит ответ 401. Уже выполняющиеся запросы завершатся штатно.

  ------------------------------------------------------------------------------------------------------------------------------------------------------------------

Для разблокировки: открыть карточку пользователя → «Разблокировать». При необходимости сбросить пароль одновременно с разблокировкой.

### 3.4 Управление паролем

Смена пароля выполняется пользователем самостоятельно на форме входа (pii-shield → «Сменить пароль»). Централизованный сброс пароля администратором и self-service восстановление доступа --- в дорожной карте.

### 3.5 Удаление пользователя

  ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------
  **⛔ Важно:** Удаление пользователя необратимо. История запросов и аудит-записи сохраняются, но учётная запись восстановлению не подлежит. Рекомендуется блокировать, а не удалять учётные записи уволившихся сотрудников --- для сохранения аудиторского следа.

  ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------

  -----------------------------------------------------------------------
  **Путь:** ib_ui → «Пользователи и доступ» → \[пользователь\] → Удалить

  -----------------------------------------------------------------------

Для удаления требуется двойное подтверждение: ввод имени пользователя и нажатие кнопки «Удалить безвозвратно».

## Управление ролями и доступом к коллекциям

### 4.1 Модель ролей

  ---------- ------------------------------------------------------------------------------------------------------------------------ --------------------------------------------------------------------------------

  аналитик   Диалоговые запросы к данным в назначенных доменах/коллекциях; экспорт результатов                                        Управление пользователями, настройки ИБ, доступ к доменам без назначения
  ---------- ------------------------------------------------------------------------------------------------------------------------ --------------------------------------------------------------------------------

  ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------
  **Примечание:** Роль admin предоставляет полный доступ к управлению платформой, но не предназначена для повседневной аналитической работы. Если администратору нужен доступ к данным --- создайте отдельную учётную запись с ролью analyst.

  ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------

### 4.2 Управление доступом к коллекциям

Коллекция --- единица данных и одновременно граница доступа. Пользователь видит только те коллекции, которые ему назначены явно.

Назначение коллекции пользователю

  ----------------------------------------------------------------------------------------------
  **Путь:** ib_ui → «Пользователи и доступ» → \[пользователь\] → Доступ к данным → Добавить коллекцию

  ----------------------------------------------------------------------------------------------

Выбрать коллекцию из списка доступных → «Сохранить». Изменение вступает в силу немедленно: следующий запрос пользователя уже будет иметь доступ к новой коллекции без перезапуска.

Отзыв доступа к коллекции

  ----------------------------------------------------------------------------------------------------
  **Путь:** ib_ui → «Пользователи и доступ» → \[пользователь\] → Доступ к данным → \[коллекция\] → Отозвать

  ----------------------------------------------------------------------------------------------------

Отзыв вступает в силу немедленно. Активные сессии пользователя не прерываются, но следующий запрос к данным отозванной коллекции получит ответ «Доступ запрещён».

Просмотр всех назначений по коллекции

  -----------------------------------------------------------------------
  **Путь:** Источники данных → \[коллекция\] → Пользователи

  -----------------------------------------------------------------------

Показывает всех пользователей с доступом к коллекции. Используйте для периодического аудита --- проверки, что доступ к чувствительным данным имеют только нужные сотрудники.

## Политики OPA

OPA (Open Policy Agent) применяется для построчной фильтрации (row-level security) федеративных SQL-запросов через Trino: политики формируют row-фильтры на основе бизнес-доменов OpenMetadata, назначенных роли/персоне пользователя. Маскировка ПДн в ответах выполняется отдельно, в pii-shield (не через OPA).

### 5.1 Просмотр активных политик

  -----------------------------------------------------------------------
  **Путь:** Настройки → Политики OPA

  -----------------------------------------------------------------------

Список политик показывает: название, область применения (какой сервис / ресурс), статус (активна / неактивна), дату последнего изменения.

Для просмотра содержимого политики --- нажать на название. Политика отображается в формате Rego (язык OPA). Редактирование политик через UI недоступно --- это намеренное ограничение для предотвращения случайного изменения.

  -----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------
  **Примечание:** Изменение политик OPA --- операция высокого риска, выполняется только DevOps/SRE-инженером через конфигурационные файлы платформы. Если текущие политики не соответствуют требованиям ИБ --- создайте запрос на изменение через внутреннюю процедуру.

  -----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------

### 5.2 Как формируются политики

Row-фильтры формируются автоматически из бизнес-доменов OpenMetadata: пользователю доступны строки таблиц, отнесённых к доменам его роли/персоны. Правила выражены на языке Rego и синхронизируются в OPA из метаданных каталога. Ручное изменение --- через конфигурационные файлы (DevOps/SRE) с версионированием.

Маскировка ПДн в ответах и разрешения на экспорт настраиваются отдельно (pii-shield и роли пользователей), а не политиками OPA.

## Управление PII Shield

PII Shield --- встроенный компонент защиты персональных данных. Автоматически обнаруживает ПД в ответах агентов и маскирует их перед выдачей пользователю. Все операции маскирования журналируются.

### 6.1 Статус и метрики PII Shield

  -----------------------------------------------------------------------
  **Путь:** Настройки → PII Shield → Обзор

  -----------------------------------------------------------------------

Панель обзора показывает за выбранный период:

-   Всего обработанных ответов агентов

-   Из них: с обнаруженными ПД / без ПД

-   Количество операций маскирования по типам (ФИО, телефон, email, ИНН, СНИЛС, карта)

-   Топ пользователей по числу запросов, в ответах на которые были обнаружены ПД

### 6.2 Настройка порогов обнаружения

  -----------------------------------------------------------------------
  **Путь:** Настройки → PII Shield → Конфигурация

  -----------------------------------------------------------------------

Ключевые параметры:

  ------------------------------- ------------------ ----------------------------------------------------------------------------------------------------------------------------
  **Параметр**                    **По умолчанию**   **Описание**

  Минимальный порог обнаружения   0.4 (40%)          Уверенность модели, при которой сущность считается ПД. Снижение → больше ложных срабатываний, повышение → риск пропуска ПД

  Сканирование ответов            Включено           PII_RESPONSE_SCAN_ENABLED. Отключение разрешает передачу немаскированных ПД --- требует обоснования ИБ

  Колоночное маскирование         Включено           Учёт тегов ПД из Синапс.Каталога для точного маскирования по столбцам

  Стратегия маскирования          Токенизация        PERSON_1, PHONE_1 и т.д. Альтернативы: псевдонимизация, полное скрытие
  ------------------------------- ------------------ ----------------------------------------------------------------------------------------------------------------------------

  --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------
  **⚠ Внимание:** Снижение порога обнаружения ниже 0.3 может приводить к маскированию нечувствительных данных и снижению качества ответов агентов. Изменяйте порог осторожно и фиксируйте обоснование в журнале изменений.

  --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------

### 6.3 Просмотр операций маскирования

  -----------------------------------------------------------------------
  **Путь:** Настройки → PII Shield → Журнал маскирования

  -----------------------------------------------------------------------

Каждая запись журнала содержит: временну́ю метку, пользователя, коллекцию, тип обнаруженной ПД (не само значение), применённую стратегию маскирования, статус операции.

Фильтры: по дате, пользователю, типу ПД, коллекции. Экспорт журнала: кнопка «Выгрузить CSV» --- формирует файл за выбранный период.

  ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------
  **💡 Совет:** Регулярно проверяйте записи с типом «Ошибка маскирования» --- это случаи, когда ПД была обнаружена, но маскирование не выполнено. Каждый такой случай требует ручного разбора.

  ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------

### 6.4 Теги ПД в коллекциях

  -----------------------------------------------------------------------
  **Путь:** Источники данных → \[коллекция\] → Метаданные → Теги ПД

  -----------------------------------------------------------------------

Теги ПД указывают, какие столбцы источника содержат персональные данные. Используются PII Shield для точечного маскирования (column-aware masking). Назначение тегов --- задача Data Steward, но администратор безопасности должен периодически проверять полноту разметки.

  ------------------- -------------------------- ----------------------------------
  **Тег**             **Тип ПД**                 **Рекомендуемая стратегия**

  PII.FullName        ФИО                        Токенизация (PERSON_N)

  PII.Phone           Телефон                    Маскирование (\* \*\* \*\* \*\*)

  PII.Email           Email                      Маскирование (a\*\*\*@domain)

  PII.TaxID           ИНН                        Токенизация (INN_N)

  PII.SNILS           СНИЛС                      Полное скрытие

  PII.PassportID      Паспортные данные          Полное скрытие

  PII.BankCard        Номер карты                Маскирование (\*\*\*\*N)

  PII.SensitiveData   Специальные категории ПД   Полное скрытие
  ------------------- -------------------------- ----------------------------------

## Журнал аудита

Журнал аудита фиксирует значимые события платформы: операции с данными, действия пользователей, изменения конфигурации, события безопасности. Записи хранятся в PostgreSQL (LLM-сессии --- pii_audit; привилегированные действия --- admin_audit_log); доступ к журналу ограничен ролью администратора ИБ.

### 7.1 Контуры аудита

Аудит разнесён по трём журналам:

-   **LLM-сессии** (pii_audit) --- вопрос пользователя, вызовы инструментов, факт и объём маскирования ПДн. Просмотр --- ib_ui, раздел «Журнал LLM-сессий».

-   **Привилегированные действия** (admin_audit_log) --- операции администраторов и Data Steward (создание/деактивация учётных записей, изменение политик, аппрувы). Поля: оператор, действие, объект, время, значения до/после.

-   **SQL-запросы** (sql_audit) --- сгенерированные SQL к источникам: пользователь, таблицы и колонки, длительность, результат.

Общие поля записи: временна́я метка (UTC), пользователь и роль, тип и объект события, результат (успех / отказ / маскировано), контекст (тип ПДн, HTTP-статус и т. п.).

### 7.2 Фильтрация событий

Доступные фильтры:

-   Период (с / по) --- обязательный параметр; по умолчанию последние 24 часа

-   Пользователь --- конкретный логин или «все»

-   Тип события --- одно или несколько из категорий

-   Результат --- SUCCESS / FAILURE / MASKED

-   Коллекция --- конкретная коллекция

Типовые сценарии фильтрации:

  -------------------------------------------------- -----------------------------------------------
  **Задача**                                         **Фильтр**

  Проверить все неудачные попытки входа за неделю    Тип: AUTH, Результат: FAILURE, Период: 7 дней

  Найти все обращения к коллекции с ПД               Тип: DATA_ACCESS, Коллекция: \[имя\]

  Проверить, кто изменял настройки безопасности      Тип: CONFIG_CHANGE

  Расследовать активность конкретного пользователя   Пользователь: \[логин\], все типы событий

  Найти все случаи маскирования ПД за день           Тип: PII_MASK, Период: сегодня
  -------------------------------------------------- -----------------------------------------------

### 7.3 Экспорт журнала аудита

  -----------------------------------------------------------------------
  **Путь:** Аудит → Журнал событий → Экспорт

  -----------------------------------------------------------------------

Доступные форматы экспорта: CSV, JSON. Экспортируются все записи, соответствующие текущим фильтрам. Для передачи регулятору или во внешнюю SIEM-систему рекомендуется формат JSON.

Для больших периодов экспорт удобно разбивать по датам. Для потоковой передачи во внешнюю SIEM используйте регулярный экспорт по расписанию.

  -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------
  **⚠ Внимание:** Экспортированный журнал аудита содержит чувствительную информацию о поведении пользователей. Храните экспортированные файлы в защищённом месте и ограничьте к ним доступ.

  -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------

### 7.4 Оповещения и мониторинг

Метрики безопасности (счётчики маскирования, ошибки, нагрузка сервисов) экспонируются в Prometheus и визуализируются в Grafana; пороговые оповещения (email/мессенджер) настраиваются средствами Alertmanager/Grafana. Для событийного мониторинга журналы аудита экспортируются во внешнюю SIEM организации. Встроенного в UI движка правил с автоблокировкой платформа не предоставляет --- реагирование выполняется средствами мониторинга и SIEM.

## Реагирование на инциденты безопасности

### 8.1 Подозрение на компрометацию учётной записи

**1. Немедленно заблокировать учётную запись**

  -----------------------------------------------------------------------
  **Путь:** ib_ui → «Пользователи и доступ» → \[пользователь\] → Заблокировать

  -----------------------------------------------------------------------

**2. Проверить историю активности**

  -------------------------------------------------------------------------------
  **Путь:** Аудит → Журнал событий → фильтр по пользователю за последние 7 дней

  -------------------------------------------------------------------------------

Обратить внимание на: необычное время входа, нетипичные коллекции, массовые запросы данных, попытки изменения настроек.

**3. Зафиксировать инцидент**

Экспортировать журнал аудита за период активности. Зафиксировать IP-адреса, время, характер запросов. Передать материалы в службу ИБ организации.

**4. Принять решение о восстановлении доступа**

После расследования: разблокировать со сбросом пароля --- если инцидент не подтверждён; оставить заблокированной --- если компрометация подтверждена. Завести новую учётную запись при необходимости.

### 8.2 Обнаружение утечки данных через RAG

Признаки: необычно большое число обращений к одной коллекции, систематические запросы вида «перечисли все записи», запросы на данные вне рабочих задач пользователя.

**1. Проверить журнал аудита**

  ----------------------------------------------------------------------------------------------------------
  **Путь:** Аудит → Журнал событий → Тип: DATA_ACCESS, Пользователь: \[подозреваемый\], Результат: SUCCESS

  ----------------------------------------------------------------------------------------------------------

**2. Временно отозвать доступ к коллекции**

  ----------------------------------------------------------------------------------------------------
  **Путь:** ib_ui → «Пользователи и доступ» → \[пользователь\] → Доступ к данным → \[коллекция\] → Отозвать

  ----------------------------------------------------------------------------------------------------

**3. Проверить журнал PII Shield**

  ---------------------------------------------------------------------------------
  **Путь:** Настройки → PII Shield → Журнал маскирования → фильтр по пользователю

  ---------------------------------------------------------------------------------

Проверить, были ли в ответах обнаружены ПД и применено ли маскирование.

**4. Эскалировать**

Передать экспортированные журналы в службу ИБ. При подтверждении утечки ПД --- уведомить ответственного за ПД в организации согласно внутреннему регламенту и требованиям ФЗ-152 (уведомление Роскомнадзора в течение 24 часов).

### 8.3 Обнаружение попытки prompt injection

Признаки в журнале аудита: запросы, содержащие инструкции агенту («забудь предыдущие инструкции», «действуй как», «игнорируй ограничения»); нетипичные ответы агента; запросы системного промпта.

**1. Найти подозрительные запросы в аудите**

  -------------------------------------------------------------------------------------------------------------------
  **Путь:** Аудит → Журнал событий → Тип: DATA_ACCESS, Детали: содержит \'inject\' / \'ignore\' / \'system prompt\'

  -------------------------------------------------------------------------------------------------------------------

**2. Заблокировать пользователя при подтверждении**

**3. Передать запросы команде поддержки платформы для анализа обхода защит**

Передать: текст запросов (из журнала), ответы агентов, временны́е метки. Поставщик платформы анализирует и при необходимости усиливает платформенные рамки промпта.
