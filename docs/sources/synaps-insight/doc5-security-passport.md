## Архитектура безопасности

### 3.1 Периметр и сетевая изоляция

Платформа развёртывается исключительно в изолированном периметре клиента. Принципы сетевой изоляции:

-   Единственная точка входа: HTTPS (443) → Nginx → ib_ui. Все остальные порты компонентов закрыты для внешней сети

-   Межсервисное взаимодействие --- только внутри изолированной Docker-сети (synapse) или Kubernetes namespace

-   Платформа не инициирует исходящих соединений в интернет; поддерживается полностью изолированный air-gap режим

-   TEI-сервисы (эмбеддинг) могут быть вынесены на отдельный хост --- доступ строго по IP/DNS через ту же закрытую сеть

### 3.2 Аутентификация и авторизация

Многоуровневая модель авторизации:

  ------------------------------ ----------------------------------------------------------------------- ---------------------------
  **Уровень**                    **Механизм**                                                            **Компонент**

  Аутентификация пользователей   OAuth 2.0 / OIDC; JWT-токены с ограниченным TTL                         pii-shield

  Авторизация пользователей      RBAC: роли admin / analyst / viewer; назначение коллекций               ib_api, Синапс.Каталог

  Авторизация межсервисная       OPA (Open Policy Agent): декларативные политики                         OPA sidecar / standalone

  Авторизация к данным           Граница коллекции = граница ACL; Qdrant не фильтрует внутри коллекции   ib_api, Qdrant

  Сервисные токены               PII_TRUSTED_EGRESS_TOKEN для pii-shield ↔ agent-runtime                 pii-shield, agent-runtime
  ------------------------------ ----------------------------------------------------------------------- ---------------------------

### 3.4 Аудит и журналирование

Платформа ведёт многоуровневый журнал событий безопасности:

-   audit-service: полная трассировка операций с данными --- кто, когда, к каким данным обращался, что было возвращено

-   Все операции с ПД журналируются с указанием субъекта, категории данных, результата (включая маскирование PII Shield)

-   Прикладные логи сервисов собираются в OpenSearch (Зона 2) или Docker/K8s stdout

-   Метрики безопасности экспортируются в Prometheus: аномалии запросов, ошибки авторизации, нагрузка

-   Интеграция с SIEM клиента через syslog/webhook (опционально)

  -----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------
  **Примечание:** Логи аудита защищены от изменения: audit-service пишет в отдельную БД pii_audit с ролью, не имеющей прав UPDATE/DELETE. Целостность логов гарантируется на уровне PostgreSQL-ролей.

  -----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------

## Guard rails — контроли безопасности и режим применения

Раздел отвечает на частый вопрос заказчика: «какими механизмами платформа удерживает ИИ-агента и
пользователей в безопасных рамках и что из этого блокирует нарушение, а что — фиксирует его».

Контроли (guard rails) разделены по **режиму применения**:

-   **Enforcement (предотвращение)** — контроль **жёстко блокирует** нарушение до того, как оно
    произойдёт (запрос отклоняется, данные маскируются, действие не выполняется).
-   **Observability (наблюдение)** — контроль **фиксирует и сигнализирует** о событии для
    расследования и реагирования, не прерывая поток.

Многие контроли работают в обоих режимах (предотвращают и одновременно протоколируют).

| Контроль | Что удерживает / механизм | Режим | Компонент |
|---|---|---|---|
| Аутентификация | OAuth 2.0 Authorization Code + PKCE (S256), обязателен серверно | Enforcement | pii-shield |
| Защита от подбора пароля | Блокировка после N неудачных входов + rate-limit запросов (HTTP 429) | Enforcement | OpenMetadata / pii-shield |
| Разграничение доступа к данным | Построчная фильтрация (RLS) по бизнес-доменам пользователя; граница коллекции = граница доступа | Enforcement | OPA / оркестратор / Qdrant |
| Маскирование ПДн в ответах | Обнаружение → маскирование → восстановление на входе/выходе LLM; точечно по тегам каталога | Enforcement + Observability | pii-shield / dlp-secret |
| Контроль утечки в ответе модели | Повторный скан ответа LLM на ПДн после восстановления | Enforcement + Observability | pii-shield |
| Безопасный вывод наружу (egress) | В недоверенные внешние каналы токены не восстанавливаются — уходит только маскированное | Enforcement | pii-shield |
| Политика по доверию модели | Уровень маскировки зависит от класса модели (облачная строже, локальная мягче) | Enforcement | dlp-secret / pii-shield |
| Неизменяемая рамка промпта | Системные инструкции и правила инструментов защищены от правки; пользователь меняет только ролевой блок | Enforcement | agent-runtime |
| Карантин недоверенного контента | Внешний/RAG-контент подаётся модели в изолирующей рамке (защита от косвенных инъекций в документах) | Enforcement | agent-runtime |
| SQL «только чтение» | Отклонение любых изменяющих операций (DROP/INSERT/UPDATE/DELETE) на уровне валидатора запроса | Enforcement | оркестратор |
| Санитизация вывода агента | Удаление служебных артефактов/дампов из ответа перед выдачей | Enforcement | agent-runtime |
| Аудит LLM-сессий | Полная трассировка: вопрос, вызовы инструментов, факт и объём маскирования | Observability | audit-service (pii_audit) |
| Сигнал о попытке обхода | Пометка диалога `security_alert` при подозрительных паттернах | Observability | audit-service |
| Аудит SQL-запросов | Сгенерированные запросы, задействованные таблицы/колонки, длительность, результат | Observability | sql_audit |
| Аудит привилегированных действий | Операции администраторов и Data Steward со значениями «до/после» | Observability | admin_audit_log |
| Передача в SIEM | Потоковая выгрузка структурированных событий безопасности во внешнюю SIEM | Observability | pii-shield (SIEM-эмиттер) |
| Мониторинг и оповещения | Метрики безопасности + пороговые алерты | Observability | Prometheus / Grafana |
| Периметр | Единая точка входа, сетевая изоляция, поддержка air-gap; платформа не инициирует исходящих в интернет | Enforcement | Nginx / инфраструктура |

  ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------
  **Развитие контроля (roadmap).** Ряд усилений в плане развития: санитизация контента при
  индексировании (дополнение к карантинной рамке против косвенных инъекций); взаимный TLS
  для чувствительных межсервисных каналов; подпись образов в конвейере сборки; сценарные
  автоблокировки по правилам поверх сигналов `security_alert`. До внедрения эти меры не
  заявляются как реализованные.

## Обработка персональных данных (ФЗ-152)

### 4.1 Категории ПД, обрабатываемых платформой

Платформа обрабатывает ПД двух видов: служебные ПД пользователей платформы и ПД из подключённых источников данных клиента.

  -------------------------------------- -------------------------------------------------------------------------------------- -------------------------------------------------- -------------------------------------------------------------
  **Категория ПД**                       **Состав**                                                                             **Основание обработки**                            **Хранилище**

  Служебные ПД пользователей платформы   Имя, должность, email, история запросов, роль                                          Договор с клиентом; согласие субъекта              PostgreSQL (БД dlp)

  ПД из источников данных клиента        Определяется клиентом; платформа обрабатывает данные согласно настроенным коллекциям   Поручение на обработку от оператора ПД (клиента)   Только индексы в Qdrant; оригиналы --- в источниках клиента

  Биометрические ПД                      НЕ обрабатываются платформой                                                           ---                                                ---

  Специальные категории ПД               НЕ предназначены для обработки платформой без дополнительной конфигурации              ---                                                ---
  -------------------------------------- -------------------------------------------------------------------------------------- -------------------------------------------------- -------------------------------------------------------------

  ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------
  **⚠ Внимание:** Платформа является оператором ПД только в отношении служебных данных пользователей платформы. В отношении данных из источников клиента --- платформа действует как обработчик ПД по поручению клиента-оператора.

  ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------

### 4.2 Цели и правовые основания обработки

  ---------------------------------------------------------- ------------------------------------------------------ -----------------------------------------
  **Цель обработки**                                         **Правовое основание**                                 **Категория субъектов**

  Аутентификация и авторизация пользователей платформы       Договор с организацией-клиентом; согласие сотрудника   Сотрудники клиента

  Журналирование действий пользователей (аудит)              Законный интерес оператора; требования ИБ              Сотрудники клиента

  Обработка данных из источников по запросам пользователей   Поручение на обработку от клиента-оператора            Субъекты ПД по определению клиента

  Маскирование ПД в ответах агентов (PII Shield)             Законный интерес; выполнение требований ФЗ-152         Все субъекты ПД в обрабатываемых данных
  ---------------------------------------------------------- ------------------------------------------------------ -----------------------------------------

### 4.3 Меры защиты персональных данных

-   Минимизация данных: платформа не копирует оригинальные данные из источников --- только векторные эмбеддинги и метаданные

-   Разграничение доступа: пользователь получает доступ только к коллекциям, к которым назначен администратором

-   Автоматическое маскирование: PII Shield обнаруживает и маскирует ПД в ответах агентов перед выдачей пользователю

-   Аудит операций с ПД: все обращения к данным, содержащим ПД, фиксируются в audit-service с детализацией

-   Срок хранения сессионных данных: конфигурируется через TTL в Redis (по умолчанию --- согласно политике клиента)

-   Удаление данных: предусмотрена процедура удаления коллекций и связанных данных из Qdrant/MinIO/PostgreSQL

### 4.4 Обезличивание и маскирование --- PII Shield

PII Shield --- встроенный компонент защиты ПД, работающий на уровне ответов агентов. Архитектура защиты:

  ---------------------- ---------------------------------------------------------------------------------------------------------------------------------- --------------------------------------------------------------------------
  **Этап**               **Механизм**                                                                                                                       **Результат**

  Обнаружение ПД         ML-модели NER на базе bge-m3 эмбеддингов; настраиваемый порог detection rate (по умолчанию 40%)                                    Идентификация сущностей: ФИО, телефон, email, ИНН, СНИЛС, паспорт, карта

  Маскирование           Замена токенами: PERSON_1, PHONE_1, EMAIL_1 и т.д.; конфигурируемые стратегии (маскировать / псевдонимизировать / шифровать)       ПД не попадают в ответ пользователю в открытом виде

  Audit trail            Каждая операция маскирования записывается в audit-service с указанием типа ПД, пользователя, временной метки                       Полная трассировка для расследования инцидентов

  Column-aware masking   PII_COLUMN_AWARE_TABLE_MASKING=true: PII Shield учитывает теги ПД из Синапс.Каталога для точного маскирования на уровне столбцов   Точечное маскирование без потери контекста
  ---------------------- ---------------------------------------------------------------------------------------------------------------------------------- --------------------------------------------------------------------------

## Модель угроз и нарушителей

Модель угроз разработана в соответствии с Методикой оценки угроз безопасности информации ФСТЭК России (2021). Идентификаторы угроз соответствуют банку данных угроз БДУ ФСТЭК.

### 6.2 Актуальные и неактуальные угрозы

Актуальность угрозы определяется на основе оценки возможностей нарушителей и наличия/отсутствия защитных мер. Пять угроз признаны актуальными; три --- неактуальными в силу архитектурных решений или вынесены за периметр платформы.

  **УБИ.001**   НСД к данным через API                            **Актуальная**     Внешний (высокий), внутренний пользователь              Перехват или подбор JWT-токена; обход авторизации                                                     OAuth 2.0 + OPA; короткий TTL токенов; аудит-лог всех API-вызовов

  **УБИ.002**   Компрометация LLM-контекста (prompt injection)    **Актуальная**     Внутренний пользователь, привилегированный              Внедрение инструкций в запрос с целью обхода ограничений агента или извлечения системного промпта     Платформенные рамки промпта (immutable system frame); OPA-политики на вывод агентов; аудит запросов

  **УБИ.003**   Атака на цепочку поставок (образы, зависимости)   **Актуальная**     Внешний (высокий)                                       Компрометация базовых образов или зависимостей Python/npm с внедрением вредоносного кода              Использование только образов из реестра поставщика; air-gap режим; хэш-верификация образов; подпись образов

  **УБИ.004**   Утечка данных через RAG-индекс                    **Актуальная**     Внутренний пользователь                                 Формулировка запросов, извлекающих фрагменты данных других пользователей из векторного индекса        ACL на уровне коллекций Qdrant; пользователь видит только коллекции, к которым назначен; OPA-фильтрация

### 6.3 Специфические угрозы LLM-систем

Платформа Синапс.Инсайт использует LLM-компоненты, что порождает специфический класс угроз, отсутствующий в традиционных ИС:

  ---------------------------------- --------------------------------------------------------------------------------------------------------------------------- ----------------------------------------------------------------------------------------------
  **Угроза**                         **Описание**                                                                                                                **Контрмера в платформе**

  Prompt injection (прямой)          Пользователь внедряет инструкции в запрос с целью обхода системного промпта или извлечения конфиденциальных данных агента   Платформенные рамки промпта (immutable frame) в ib_ui; OPA-политики на допустимые инструкции

  Prompt injection (косвенный)       Вредоносные инструкции внедряются в индексируемые документы и срабатывают при RAG-запросе                                   Санитизация контента при индексировании; ограничение прав агента на действия

  Jailbreak системного промпта       Попытка извлечь содержимое системного промпта через многошаговые диалоги                                                    Системный промпт не передаётся пользователю; audit-лог подозрительных паттернов

  Data exfiltration через RAG        Формулировка запросов, последовательно извлекающих фрагменты данных из векторного индекса                                   ACL на уровне коллекций; rate limiting запросов; мониторинг аномального поведения

  Model inversion через embeddings   Попытка восстановить оригинальный текст из векторных представлений                                                          Qdrant не предоставляет прямого доступа к векторам без аутентификации; ACL на коллекции
  ---------------------------------- --------------------------------------------------------------------------------------------------------------------------- ----------------------------------------------------------------------------------------------

## Остаточные риски и разграничение ответственности

Ряд мер безопасности не входит в периметр платформы и является ответственностью клиента-оператора. Это не является уязвимостью платформы, но требует явного фиксирования в договорных и организационных документах.

  ----------------------------------------------------- --------------------- ---------------------------------------------------------------------------------------
  **Риск / область**                                    **Ответственность**   **Рекомендация клиенту**

  Шифрование данных на физических носителях (at rest)   Клиент                Шифрование томов LVM/LUKS или облачных PV; политика безопасного уничтожения носителей

  Физическая безопасность серверов                      Клиент                СКУД, видеонаблюдение, политика доступа в серверные помещения

  Защита от DoS/DDoS                                    Клиент                WAF, rate limiting на уровне сетевой инфраструктуры, Anti-DDoS сервис

  Антивирусная защита хостов                            Клиент                EDR/антивирус на хостах Docker/K8s; сканирование образов в реестре

  Управление уязвимостями (CVE)                         Совместно             Клиент: регулярное сканирование хостов; Поставщик: обновление образов платформы

  Регулярное сканирование образов                       Совместно             Trivy/Grype в CI/CD pipeline клиента; поставщик предоставляет SBOM

  Шифрование резервных копий                            Клиент                GPG-шифрование архивов резервных копий перед размещением на резервных носителях

  Обучение персонала (ИБ)                               Клиент                Инструктаж пользователей платформы по правилам работы с ПД и признакам атак

  Аккредитация / аттестация ИС                          Клиент                Получение аттестата соответствия в аккредитованной организации при необходимости
  ----------------------------------------------------- --------------------- ---------------------------------------------------------------------------------------

### 8.2 Источники данных для расследования

-   audit-service (БД pii_audit): полная трассировка операций с данными --- основной источник для расследования инцидентов с ПД

-   Логи pii-shield: все OAuth-события, ошибки аутентификации, операции маскирования

-   Логи ib_api: все API-запросы с идентификатором пользователя, endpoint, HTTP-статусом

-   Метрики Prometheus: исторические данные о нагрузке, ошибках, аномалиях

-   Логи Nginx: входящие запросы с IP-адресами, User-Agent, статусами

  --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------
  **Примечание:** Для получения логов конкретного периода использовать: docker compose logs \--since=\<ISO8601\> \--until=\<ISO8601\> \<service\>. Для долгосрочного хранения логов --- настроить интеграцию с SIEM клиента через syslog-драйвер Docker.
