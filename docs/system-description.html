О названии

В более ранних материалах системе присваивались разные рабочие названия («Синапс», «Синапс.Инсайт» — из презентаций и ТЗ). Прямой скриншот интерфейса показывает, что в самом продукте название пока не определено — сайдбар использует общую подпись «Платформа». Далее по всей базе используется это нейтральное обозначение; более ранние источники, где встречается конкретное имя, процитированы дословно и не изменены.

Приоритет источников

При расхождении фактов между материалами — вот кто побеждает.

  1. RFI-ответ разработчика наивысший приоритет — инженерная/архитектурная команда вендора, не продажи. При расхождении с чем угодно ещё в базе — верно то, что здесь. docs/rfi-responses/
  2. Пилотное ТЗ — юридическая сила для конкретного пилота, количественные критерии приёмки. case-03
  3. Живые встречи — дословная запись; достоверно как факт «что сказали», но сказано сейлзом/инженером на встрече, не проверено инженерной документацией. docs/accounts/
  4. Презентации — маркетинговый питч, самый низкий приоритет для фактической точности. docs/sales-enablement/

01Что это за система

Корпоративная платформа интеллектуальной аналитики, разворачиваемая целиком в изолированном контуре заказчика (on-premise, офлайн-поставка): каталог метаданных, конвейеры обработки данных, индексация и поиск по документам (RAG), ролевое разграничение доступа, обязательный компонент контроля обращений к языковым моделям (в клиентской терминологии — «AI Guard») и агентная подсистема.

Платформа не включает саму генеративную LLM — модель всегда внешний по отношению к платформе сервис, единственное жёсткое требование к ней — поддержка вызова инструментов (tool/function calling).

Продаётся не как единый монолит, а как портфель из пяти практик: сама платформа, AI Guard (позиционируется как отдельный продукт, технически неотделим), шлюз доступа к моделям (Veai Platform), сервис инженерного стаффинга («Внешний офис ИИ») и обучение.

02Архитектура

Самая точная часть всей базы знаний — источник наивысшего приоритета.

Поставка тремя слоями: версионируемое продуктовое ядро (не переписывается под заказчика) → настраиваемая конфигурация контура → проектная интеграционная обвязка (источники, роли, корпус документов). Вендор прямо признаёт: «коробочного» в строгом смысле решения этого класса не бывает — разграничение доступа по определению строится на структуре конкретной организации.

2.2Полный маршрут данных

  1. Аутентификация Учётные данные проверяются в каталоге организации, анонимный доступ отсутствует.
  2. Разграничение доступа До какой-либо обработки ПДн определяется, к каким источникам/объектам/строкам пользователь вправе обращаться.
  3. Обнаружение ПДн — три механизма одновременно Аннотации каталога метаданных (основной для структурированных данных); свыше 250 формальных правил для типизированных идентификаторов (телефон, email, ИНН, СНИЛС, паспорт, банковские реквизиты, ОГРН, IBAN, VIN, IP, госномера — с проверкой контрольных соотношений для 6 типов против ложных срабатываний); NER для свободного текста, раздельно для русского и английского.
  4. Применение политик Замещение типизированными метками ([PERSON_1], [PHONE_2]) с сохранением соответствия в пределах сессии, либо подавление строки целиком при превышении порога ПДн-полей (по умолчанию — три).
  5. Хранение таблицы соответствий Только внутри контура, привязана к сессии, TTL 60 минут по умолчанию, никогда не передаётся в модель; если хранилище недоступно при старте — компонент не запускается.
  6. Передача в модель Политика по поставщику: для локальной модели замещение может быть отключено, для внешней — принудительно; при недоступности механизмов контроля обращение блокируется.
  7. Обратное восстановление Подстановка по таблице соответствий той же сессии; пользователь видит в открытом виде только то, доступ к чему подтверждён на шаге 2.
  8. Журналирование Режим «только добавление»; сырые значения ПДн по умолчанию не пишутся; хранение 90 суток, настраивается.

Измеренная задержка — не точность

Обнаружение + замещение: не более 2 мс на 95-м перцентиле. Это цифра задержки, не точности. Единственный источник цифр точности во всей базе — пилотное ТЗ: ≥98% распознавания в документах, ≥95% анонимизации данных источников, ≥70% — согласуемый порог на «грязных» данных. Это целевые критерии приёмки, а не подтверждённый измеренный результат ни в одном известном отчёте.

2.3Ролевая модель

Трёхуровневая: предметные области → строки (по атрибутам вроде подразделения/региона) → поля (маскирование). Ключевой архитектурный принцип: разграничение доступа применяется до обезличивания — обезличенный ответ о записи, к которой у пользователя нет доступа, всё равно является нарушением, поскольку сам факт существования записи информативен. Маскирование не подменяет контроль доступа.

2.4Развёртывание и инфраструктура

Только on-premise, офлайн-поставка образов во внутренний реестр, без обращений к внешним репозиториям в рантайме — архитектурное ограничение, не настройка. Kubernetes — для промышленной эксплуатации; Docker Compose — для пилотов и малых инсталляций, без резервирования; функциональность идентична в обоих вариантах.

Инфраструктура платформы

8–16 vCPU

32–64 ГБ ОЗУ, 200 ГБ диска. GPU не требуется — векторизация (bge-m3/jina-code) на CPU.

Инфраструктура самой LLM

80–160 ГБ VRAM

2×NVIDIA A100-класс — только если заказчик самостоятельно хостит open-source модель.

Смешение этих двух цифр в одном коммерческом предложении — конкретный, уже зафиксированный риск.

03Бизнес-портфель

3.1Кто покупает и почему

Три признака квалифицированной сделки: ИИ нужен как постоянная, а не разовая часть работы; важна предсказуемость поведения/стоимости/соответствия политике; есть потребность в едином ИТ/ИБ-контроле. Платформа сама честно заявляет: для одной изолированной задачи она избыточна.

3.2Пять практик

Платформа (название не определено)

Ядро системы: AI Gateway, RAG с учётом прав доступа, ролевая модель, on-premise/гибрид.

AI Guard

Позиционируется как отдельный продукт, технически не лицензируется отдельно от платформы.

Veai Platform

Шлюз доступа к моделям и биллинг в рублях. Не поставщик DLP — это нативная функция платформы.

Внешний офис ИИ

Стаффинг/передача экспертизы, 11 ролей, 4 фазы, позиция «без вендор-локина».

Обучение и стратсессии

3 уровня зрелости, 7 форматов.

3.3Пилотная экономика — реконциляция

RFI-ответ (приоритет)

Единый пилот, 6 недель: 2 источника, 2 роли, 2 коллекции документов, одна модель по выбору. Цена «по запросу». Явно исключены: инфраструктура и оплата обращений к внешней модели.

Презентация 2026

Два отдельных пилота: AI Guard — 1 млн ₽ / 4–6 нед.; «Платформа» — 1,5 млн ₽ / 6–8 нед.

Не обязательно взаимоисключающие предложения, но одному заказчику нужно показывать одну рамку, а не обе.

3.4Что реально волнует покупателей

Единственная живая встреча в базе — discovery-звонок с mz-arsenal. Распределение содержательного времени разговора:

Маскирование / доверие — ~38%
Инфраструктура / GPU — ~24%
Остальное — ~38%
Доверие к маскированию — доминирующая тема Инфраструктура/GPU — вторая тема Конкретные бизнес-кейсы — наименьшая доля

Заказчик трижды не смог сформулировать, чем будут заниматься 100 планируемых пользователей. Закрывающий сигнал — некритичная сдержанность («много вопросов остаётся»), не отказ. Подготовленный лист возражений совпал с реальным разговором слабо — лист рассчитан на презентацию, а встреча оказалась чистым discovery.

3.5Разрыв доказательной базы кейсов

Все ~10 именованных клиентов во всех версиях презентации — инструменты для разработчиков и инженерных команд (код-ревью, генерация тестов, контроль зависимостей). Ни один не демонстрирует питчуемые бизнес-персоны (ассистент руководителя, HR-рекрутер, тендерный специалист, поддержка клиентов). Рост числа кейсов в 2026 году не изменил их профиля — разрыв нерешённый.

3.6Рекомендация по упаковке

Вести продажи единой 6-недельной рамкой пилота, не двумя разнесёнными прайсами презентации; открывать сделку через AI Guard/маскирование как основной крючок, а не через бизнес-агентов. До демо, а не на нём — фиксировать конкретный список сценариев по отделам, иметь честную формулировку по метрике точности маскирования, проактивно проговаривать исключение инфраструктуры/API из цены пилота.

  • закрыто

4.2Не решено даже с учётом нового документа

  • открыто
    Точность/полнота маскирования.

    Есть только задержка. Единственные цифры accuracy — целевые критерии приёмки (≥98%/≥95%/≥70%), не измеренный результат. Закрывается только фактическим отчётом.

  • открыто
    Разрыв кейс-стади vs питчуемые сценарии.

    Документ разработчика вообще не касается именованных клиентов.

  • открыто
    Селектор моделей — «работает» ≠ «показан».

    По всем собранным скриншотам видна ровно одна опция.

  • открыто
    Граф доступа для реальной персоны.

    Архитектура реализована в коде; настроены ли маски хоть для одной реальной персоны — не подтверждено.

  • сверить

  • сверить
    Номер реестра отечественного ПО №33199 — нужна сверка с реестром.
  • сверить
    Любые оставшиеся гиперточные версии сторонних моделей, если всплывут заново.

Методологическое правило для всей базы

Ревьюер уже однажды самонадеянно заявил, что конкретная версия модели — фактическая ошибка, и был вынужден откатить это после контрпримера. Правило: помечать как непроверенное, никогда не утверждать «неверно» без независимого подтверждения.

4.4Один вопрос, который вскроет реальный пробел

«Покажите фактически измеренный процент точности/полноты обнаружения ПДн по результатам реального прогона, а не целевой порог из ТЗ.»

Даже самый строгий документ базы отвечает на это только цифрой задержки, оставляя главный вопрос безопасности без единого подтверждённого числа во всей базе знаний.

05Готовность продукта

Не отдельный синтез агентов — прямой вывод по итогам всей работы над этой базой.

Общий вердикт

Не сырой продукт и не vaporware, но неравномерно созревшая система: инфраструктурный слой (безопасность, доступ, развёртывание) заметно зрелее, чем слой доказательств бизнес-ценности (кейсы, метрики, живая демонстрация).

Что реально готово

  • Архитектура маскирования и доступа продумана на уровне инженерных решений: fail-closed, доступ проверяется до маскирования, отказ от избыточных заявлений — признаки зрелой инженерной культуры.
  • Реальная эксплуатационная история — Мосбиржа, МКБ, ВТБ и другие не выдуманные логотипы, а содержательные внедрения.
  • Готовность к организационной самокоррекции — две ревизии презентации точечно исправили именно то, что было раскритиковано.

Где готовности не хватает

  • Ключевая метрика — точность обнаружения ПДн — нигде не подтверждена числом, только задержка.
  • Бизнес-сценарии существуют только на слайдах — ни один именованный клиент не подтверждает питчуемые персоны.
  • Разрыв между «закодировано» и «продемонстрировано» — мультимодельность, реальные маски Графа доступа.
  • Коммерческая упаковка ещё не устаканилась — два разных пилотных предложения одновременно.

Итог одной фразой

Фундамент — уровня production-ready корпоративного вендора. Надстройка (доказанная бизнес-ценность конкретных сценариев, подтверждённые метрики точности) — всё ещё «архитектурно готово, эмпирически не подтверждено». Для закрытого контура и compliance-чувствительного покупателя это рабочее сочетание для старта пилота — но не повод пропускать пилот и переходить сразу в прод.

06Возможности развития

Не абстрактный roadmap-брейншторм — каждый пункт выведен из конкретного пробела в этой базе, приоритет — по тому, насколько он мешает продавать и внедрять уже сейчас.

приоритет 1закрывает главный открытый вопрос всей базы

Опубликовать реально измеренную точность маскирования

Во всём корпусе есть только задержка (RFI-ответ, ≤2 мс) и целевые критерии приёмки (case-03: ≥98%/≥95%/≥70%) — ни одного фактически измеренного результата. Это вопрос, который гарантированно вскроет подготовленный ИБ-покупатель. Действие: довести пилот до отчёта с реальными процентами по протоколу case-03 и включить цифру в стандартный пакет продаж.

Мультимодальность / OCR для регламентных документов

OCR не поддерживается (RFI-ответ) — сканы без текстового слоя помечаются необработанными. Единственный бизнес-кейс, который заказчик (mz-arsenal) сформулировал сам, без подсказки, — проверка соответствия ГОСТу по чертежу. Чертежи почти всегда растровые. Действие: без OCR/мультимодального входа именно эта, самостоятельно придуманная заказчиком задача — не решается.

приоритет 2закрывает разрыв между архитектурой и доказательствами

Кейс под питчуемую бизнес-персону

Все ~10 именованных клиентов — dev-tooling и данные; ни один не подтверждает ассистента руководителя, HR-рекрутера, тендерного специалиста, поддержку клиентов. Действие: довести до продакшена пилот именно в этом профиле — retail-кейс «ТоргЛайн» (docs/demo-retail/) уже готовый кандидат для превращения из демо в реальный референс.

Демонстрируемость вместо архитектурного описания

Селектор моделей (на всех скриншотах — одна опция) и Граф доступа с реальными row/field-масками для живой персоны реализованы в коде, но никогда не наблюдались работающими. Действие: на ближайшем демо-стенде — реально настроить и показать оба.

Унификация пилотной рамки

RFI-ответ описывает единый 6-недельный пилот; презентация — два отдельных, по-разному оценённых. Действие: выбрать одну рамку для GTM (рекомендация — из RFI-ответа, как более новую) и синхронизировать документы.

приоритет 3расширяет периметр применимости

Верифицированное расширение каталога моделей

Подтверждены только GigaChat, Qwen, OpenAI, Anthropic, YandexGPT. Каталог в презентации (Gemini, Z.AI, Kimi и т. д.) — аспирация без подтверждения. Действие: пройти тем же циклом верификации и обновлять таблицу по факту.

Нативный DLP — от функции внутри AI Guard к отдельному аргументу

Автономный механизм контроля передачи ограниченных сведений, не завязанный на сторонние DLP-системы, — реальное преимущество, почти не выделенное в продающих материалах отдельно. Действие: вынести как самостоятельный аргумент для заказчиков с DLP-требованиями без бюджета на интеграцию стороннего продукта.

Формализация отложенных направлений

Заказчик сам поднял компьютерное зрение и генерацию УП для станков как более широкие амбиции; партнёрский CV-кейс (Газпромнефть) уже есть. Действие: не педалировать в пилоте, но иметь заранее честно обозначенный как партнёрский ответ — вопрос предсказуемо всплывает у промышленных заказчиков.

тех. долгуже назначенные сроки — просто исполнить

Криптографическое подтверждение неизменности журнала аудита (4 кв. 2026); аутентифицирующий прокси-сервер (4 кв. 2026); интеграция с HashiCorp Vault (1 кв. 2027). Ни один не блокирует продажи сегодня, но все три всплывут в чек-листе более зрелого покупателя, чем mz-arsenal.
