# Описание системы: корпоративная платформа + компонент контроля обращений («AI Guard»)

Итоговый синтез по всей базе знаний — архитектура, бизнес-портфель и честный список нерешённого, собранные тремя ролями (архитектор, аналитик, критик) и сверенные по установленной иерархии приоритета источников (см. [корневой README](../README.md#приоритет-источников-при-расхождении-фактов-между-материалами)). Главное правило синтеза: там, где материалы расходятся, побеждает формальный документ разработчика (`docs/rfi-responses/`), а не презентация или живая встреча.

**О названии.** В более ранних материалах системе присваивались разные рабочие названия («Синапс», «Синапс.Инсайт» — из презентаций и ТЗ). Прямой скриншот интерфейса показывает, что в самом продукте название пока не определено — сайдбар использует общую подпись «Платформа». Далее по всей базе используется это нейтральное обозначение; более ранние источники, где встречается конкретное имя, процитированы дословно и не изменены.

---

## 1. Что это за система, в двух словах

Корпоративная платформа интеллектуальной аналитики, разворачиваемая целиком в изолированном контуре заказчика (on-premise, офлайн-поставка): каталог метаданных, конвейеры обработки данных, индексация и поиск по документам (RAG), ролевое разграничение доступа, обязательный компонент контроля обращений к языковым моделям (в клиентской терминологии — «AI Guard») и агентная подсистема. Платформа **не включает саму генеративную LLM** — модель всегда внешний по отношению к платформе сервис, единственное жёсткое требование к ней — поддержка вызова инструментов (tool/function calling).

Продаётся не как единый монолит, а как **портфель из пяти практик**: сама платформа, AI Guard (позиционируется как отдельный продукт, технически неотделим), шлюз доступа к моделям (Veai Platform), сервис инженерного стаффинга («Внешний офис ИИ») и обучение.

## 2. Архитектура

### 2.1 Компоненты продуктового ядра

| Компонент | Что делает |
|---|---|
| Компонент контроля обращений (AI Guard) | Обязательная часть ядра; пропускает через себя все обращения к моделям из всех каналов |
| Каталог метаданных | Аннотации полей источников (что — ПДн, какая политика) — основной механизм обезличивания структурированных данных |
| Оркестрация конвейеров данных | Подключение и обновление источников |
| Индексация и поиск по документам | Гибридный (векторный + лексический) поиск, RAG-генерация с указанием источников |
| Агентная подсистема | Сценарии на базе tool calling |
| UI | Диалоговый интерфейс, «Управление данными» / «Граф доступа», конвейер модерации «Задачи» |
| API | REST платформы; интерфейсы, совместимые с OpenAI Chat Completions и Anthropic Messages; MCP; Python-библиотека; интеграция с LangChain — все каналы проходят те же проверки, что и UI |

Поставка тремя слоями: версионируемое продуктовое ядро (не переписывается под заказчика) → настраиваемая конфигурация контура → проектная интеграционная обвязка (источники, роли, корпус документов). Вендор прямо признаёт: «коробочного» в строгом смысле решения этого класса не бывает — разграничение доступа по определению строится на структуре конкретной организации.

### 2.2 Полный маршрут данных (самая точная часть всей базы знаний)

1. **Аутентификация** — учётные данные проверяются в каталоге организации, анонимный доступ отсутствует.
2. **Разграничение доступа** — до какой-либо обработки ПДн определяется, к каким источникам/объектам/строкам пользователь вправе обращаться.
3. **Обнаружение ПДн — три механизма одновременно**: аннотации каталога метаданных (основной для структурированных данных); свыше 250 формальных правил для типизированных идентификаторов (телефон, email, ИНН, СНИЛС, паспорт, банковские реквизиты, ОГРН, IBAN, VIN, IP, госномера — с проверкой контрольных соотношений для 6 типов против ложных срабатываний); NER для свободного текста, раздельно для русского и английского.
4. **Применение политик** — замещение типизированными метками (`[PERSON_1]`, `[PHONE_2]`) с сохранением соответствия в пределах сессии, либо подавление строки целиком при превышении порога ПДн-полей (по умолчанию — три).
5. **Хранение таблицы соответствий** — только внутри контура, привязана к сессии, TTL 60 минут по умолчанию, никогда не передаётся в модель; если хранилище недоступно при старте — компонент **не запускается** (без тихого отката в менее защищённый режим).
6. **Передача в модель** — политика по поставщику: для локальной модели замещение может быть отключено, для внешней — принудительно; по умолчанию при недоступности механизмов контроля обращение блокируется.
7. **Обратное восстановление** — подстановка по таблице соответствий той же сессии; пользователь видит в открытом виде только то, доступ к чему подтверждён на шаге 2.
8. **Журналирование** — режим «только добавление»; сырые значения ПДн по умолчанию не пишутся, отдельный шифрованный режим — явное включение; хранение 90 суток, настраивается.

Измеренная задержка обнаружения+замещения — не более 2 мс на 95-м перцентиле. **Важная оговорка**: это цифра **задержки**, не точности. Единственный источник цифр точности во всей базе — пилотное ТЗ (`case-03`): ≥98% распознавания в документах, ≥95% анонимизации данных источников, ≥70% — согласуемый порог на «грязных» данных. Это целевые критерии приёмки, а не подтверждённый измеренный результат ни в одном известном отчёте.

### 2.3 Ролевая модель

Трёхуровневая: предметные области → строки (по атрибутам вроде подразделения/региона) → поля (маскирование). Ключевой архитектурный принцип: **разграничение доступа применяется до обезличивания** — обезличенный ответ о записи, к которой у пользователя нет доступа, всё равно является нарушением, поскольку сам факт существования записи информативен. Маскирование не подменяет контроль доступа.

### 2.4 Развёртывание

Только on-premise, офлайн-поставка образов во внутренний реестр, без обращений к внешним репозиториям в рантайме — архитектурное ограничение, не настройка. Kubernetes — для промышленной эксплуатации; Docker Compose — для пилотов и малых инсталляций, без резервирования; функциональность идентична в обоих вариантах.

**Критическое разделение сайзинга** (ключевая находка синтеза): сайзинг платформы (8–16 vCPU, 32–64 ГБ ОЗУ, 200 ГБ диска, **GPU не требуется** — векторизация на CPU) — это отдельная линия от инфраструктуры под саму генеративную LLM, если заказчик хостит её самостоятельно (2×A100-класс, 80–160 ГБ VRAM — цифра из презентации и живой встречи с mz-arsenal). Смешение этих двух цифр в одном коммерческом предложении — конкретный, уже зафиксированный риск.

### 2.5 Подключаемость моделей

Подтверждено работоспособными: **GigaChat, Qwen (локально), OpenAI, Anthropic, YandexGPT**. DeepSeek и прочие — через OpenAI-совместимый интерфейс, без специализированной реализации, проверяется на пилоте. Гиперконкретный каталог версий из презентации ITQ («Claude Sonnet 4.6», «GPT-5.5» и т.п.) — маркетинговая аспирация, а не подтверждённый факт; ревизия 2 презентации сама признала риск, свернув список до уровня брендов без номеров версий.

### 2.6 Явно не поддерживается

OCR (документы-сканы без мультимодальной модели помечаются необработанными); интеграция со сторонними DLP-системами (вместо неё — собственный автономный механизм контроля передачи сведений ограниченного распространения); Kerberos/SPNEGO; контроль обхода периметра в обход платформы — прямо назван не функцией компонента («мы считаем некорректным заявлять контроль обхода периметра как функцию прикладного решения») с явной передачей задачи сетевой команде заказчика.

### 2.7 Дорожная карта (с датами из документа разработчика)

Криптографическое подтверждение неизменности журнала аудита — 4 кв. 2026; работа через аутентифицирующий прокси — 4 кв. 2026; интеграция с HashiCorp Vault — 1 кв. 2027.

## 3. Бизнес-портфель

### 3.1 Кто покупает и почему

Три признака квалифицированной сделки: (1) ИИ нужен как постоянная, а не разовая часть работы; (2) важна предсказуемость поведения/стоимости/соответствия политике; (3) есть потребность в едином ИТ/ИБ-контроле. Платформа сама честно заявляет: для одной изолированной задачи она избыточна.

### 3.2 Пять практик

- **Платформа** (название пока не определено) — ядро системы: AI Gateway, RAG с учётом прав доступа, ролевая модель, on-premise/гибридное развёртывание.
- **AI Guard** — компонент контроля обращений; позиционируется в презентации как отдельный продукт, но технически **не лицензируется отдельно от платформы** — маскирование опирается на аннотации каталога метаданных самой платформы.
- **Veai Platform** — шлюз доступа к моделям и биллинг в рублях (партнёр, не сама ITQ). **Не поставщик DLP** — это нативная функция платформы; ревизия 2 презентации и независимо документ разработчика подтверждают это разделение.
- **Внешний офис ИИ** — стаффинг/передача экспертизы, 11 ролей, 4 фазы, позиция «без вендор-локина».
- **Обучение и стратсессии** — 3 уровня зрелости, 7 форматов.

### 3.3 Пилотная экономика — реконциляция

Наиболее приоритетный источник (документ разработчика) описывает **единый пилот на 6 недель**: 2 источника данных, 2 роли, 2 коллекции документов, одна модель по выбору заказчика, цена «по запросу», единой суммой. Явно исключены: промышленная эксплуатация, нагрузочное тестирование, доработки сверх объёма, **стоимость инфраструктуры и оплата обращений к внешней модели**. Презентация 2026 года описывает иную структуру — два отдельных пилота с конкретными ценами (AI Guard — 1 млн ₽/4–6 недель, «Платформа» — 1,5 млн ₽/6–8 недель). Не обязательно взаимоисключающие предложения, но одному заказчику нужно показывать одну рамку, а не обе.

### 3.4 Что реально волнует покупателей (единственная живая встреча — mz-arsenal)

Из ~40 содержательных минут discovery-звонка около 15 занял один сюжет — доверие к маскированию (может ли сотрудник доверять ответу ИИ, если часть договора вырезана). Инфраструктура/GPU — вторая тема. Конкретные бизнес-кейсы — наименьшая: заказчик трижды не смог сформулировать, чем будут заниматься 100 планируемых пользователей. Закрывающий сигнал — некритичная сдержанность («много вопросов остаётся»), не отказ. Подготовленный лист возражений совпал с реальным разговором слабо — лист рассчитан на презентацию, а встреча оказалась чистым discovery.

### 3.5 Разрыв доказательной базы кейсов

Все ~10 именованных клиентов во всех версиях презентации — инструменты для разработчиков и инженерных команд (код-ревью, генерация тестов, контроль зависимостей). Ни один не демонстрирует питчуемые бизнес-персоны (ассистент руководителя, HR-рекрутер, тендерный специалист, поддержка клиентов). Рост числа кейсов в 2026 году не изменил их профиля — разрыв нерешённый.

### 3.6 Рекомендация по упаковке

Вести продажи единой 6-недельной рамкой пилота (из документа разработчика), не двумя разнесёнными прайсами презентации; открывать сделку через **AI Guard/маскирование как основной крючок**, а не через бизнес-агентов — живые данные показывают, что именно вопрос доверия к маскированным ответам квалифицированный покупатель разбирает въедливо и самостоятельно. До демо, а не на нём — фиксировать конкретный список сценариев по отделам, иметь честную формулировку по метрике точности маскирования, проактивно проговаривать исключение инфраструктуры/API из цены пилота.

## 4. Что до сих пор не решено

### 4.1 Реально закрыто документом разработчика

- DLP — функция самой платформы, не Veai.
- Инфраструктура/GPU/API явно исключены из цены пилота — в самом документе, не как открытие постфактум.
- Разделены два сайзинга: платформа (8–16 vCPU, без GPU) и LLM (80–160 ГБ VRAM, если хостится локально).
- Контроль обхода периметра прямо назван не-функцией компонента — самокритичный отказ от избыточного заявления.

### 4.2 Не решено даже с учётом нового документа

- **Точность/полнота маскирования.** Есть только задержка (медиана 0,05–1,08 мс, p95 ≤2 мс). Единственные цифры accuracy — целевые критерии приёмки из `case-03` (≥98%/≥95%/≥70%), не подтверждённый измеренный результат. Ни в одном клиентском материале эти цифры не встречаются. Закрывается только фактическим отчётом с реальными измеренными процентами по итогам прогона тестовых сценариев.
- **Разрыв кейс-стади vs питчуемые сценарии.** Документ разработчика вообще не касается именованных клиентов (раздел о внедрениях оставлен как незаполненный шаблон) — разрыв не тронут новым источником.
- **Селектор моделей — «работает» ≠ «показан».** Документ подтверждает работоспособность моделей как возможность, не как наблюдаемый факт. По всем собранным скриншотам интерфейса видна ровно одна опция в селекторе — вопрос остаётся открытым.
- **Граф доступа — row/field-маски для реальной персоны.** Архитектура описана и реализована в смысле кода, но остаётся нерешённым, критичным для комплаенса вопросом: настроены ли такие маски хоть для одной реальной персоны, или это по-прежнему пустая, никогда не проверенная конфигурация. Закрывается только реальным снимком заполненной админ-панели, не архитектурным описанием.

### 4.3 Непроверенные конкретные утверждения — сверить перед использованием с клиентом

- Штрафы по ст. 13.11 КоАП РФ (3–15 млн ₽, до 3% выручки повторно) — нужна юридическая сверка.
- Номер реестра отечественного ПО №33199 — нужна сверка с реестром.
- Любые оставшиеся гиперточные версии сторонних моделей, если всплывут заново.

**Методологическое правило для всей базы**: в разборе презентаций ревьюер уже однажды самонадеянно заявил, что конкретная версия модели («Claude Sonnet 4.6») — фактическая ошибка, и был вынужден откатить это после контрпримера пользователя. Правило на будущее: помечать подобные утверждения как непроверенные, никогда не утверждать «неверно» без независимого подтверждения.

### 4.4 Один вопрос, который вскроет реальный пробел

Если подготовленный технический/ИБ-покупатель сядет со всем массивом материалов сразу, самый вероятный вопрос: **«Покажите фактически измеренный процент точности/полноты обнаружения ПДн по результатам реального прогона, а не целевой порог из ТЗ»** — даже самый строгий документ базы отвечает на это только цифрой задержки, оставляя главный вопрос безопасности без единого подтверждённого числа во всей базе знаний.

## 5. Оценка готовности продукта

Не отдельный синтез агентов — прямой вывод по итогам всей работы над этой базой.

**Общий вердикт.** Не сырой продукт и не vaporware, но **неравномерно созревшая система**: инфраструктурный слой (безопасность, доступ, развёртывание) заметно зрелее, чем слой доказательств бизнес-ценности (кейсы, метрики, живая демонстрация).

**Что реально готово.**
- Архитектура маскирования и доступа продумана на уровне инженерных решений, а не только слайдов: fail-closed при недоступности хранилища соответствий, доступ проверяется до маскирования (а не вместо него), явный отказ признавать контроль обхода периметра функцией продукта — признаки зрелой инженерной культуры, а не маркетинга.
- Реальная эксплуатационная история есть — Мосбиржа, МКБ, ВТБ и другие не выдуманные логотипы, а содержательные внедрения (миграция данных, DevSecOps, RAG-поиск).
- Готовность к организационной самокоррекции — презентация прошла две ревизии и за несколько дней исправила именно то, что было раскритиковано (формулировка RBAC, противоречие Veai/DLP) — сильный сигнал зрелости процесса.

**Где готовности не хватает.**
- Ключевая метрика продукта — точность обнаружения ПДн — нигде не подтверждена числом, только задержка. Для продукта, который продаётся именно на безопасности, это дыра в доказательной базе, а не деталь.
- Бизнес-сценарии существуют только на слайдах — ни один из ~10 именованных клиентов не подтверждает ни одну из шести питчуемых бизнес-персон.
- Разрыв между «закодировано» и «продемонстрировано» — мультимодельность в интерфейсе, реально настроенные row/field-маски в Графе доступа для живой персоны существуют как возможность платформы, но не как то, что кто-то видел работающим на реальном стенде.
- Коммерческая упаковка ещё не устаканилась — два разных пилотных предложения в разных документах одновременно.

**Итог одной фразой.** Фундамент (безопасность, доступ, развёртывание) — уровня production-ready корпоративного вендора. Надстройка (доказанная бизнес-ценность конкретных агентных сценариев, подтверждённые метрики точности) — всё ещё на стадии «архитектурно готово, эмпирически не подтверждено». Для закрытого контура и compliance-чувствительного покупателя это рабочее сочетание для старта пилота — но не повод пропускать пилот и переходить сразу в прод.

## 6. Возможности развития

Не абстрактный roadmap-брейншторм — каждый пункт выведен из конкретного пробела, найденного в этой базе, с приоритетом по тому, насколько он мешает продавать и внедрять уже сейчас.

### Приоритет 1 — закрывает главный открытый вопрос всей базы

**Опубликовать реально измеренную точность маскирования.** Во всём корпусе есть только два числа: задержка (RFI-ответ, ≤2 мс) и целевые критерии приёмки пилота (`case-03`: ≥98% / ≥95% / ≥70%) — но ни одного фактически измеренного результата прогона. Это единственный вопрос, который, по независимой оценке критика (раздел 4.4), гарантированно вскроет подготовленный ИБ-покупатель. Развитие: довести хотя бы один пилот до отчёта с реальными процентами по протоколу `case-03` и сделать эту цифру частью стандартного пакета продаж — не как маркетинговый тезис, а как воспроизводимый тестовый отчёт.

**Мультимодальность / OCR для регламентных документов.** RFI-ответ прямо говорит: OCR не поддерживается, документы-сканы без текстового слоя помечаются необработанными. При этом единственный содержательный бизнес-кейс, который реальный заказчик (mz-arsenal) сформулировал сам, без подсказки — «проверка соответствия ГОСТу по чертежу» (`meeting-01-analysis.md`, ~23:25–24:16). Чертежи в промышленности и оборонке почти всегда растровые/сканированные. Без OCR/мультимодального входа именно та задача, которую заказчик придумал сам, а не которую ему предложили, — не решается платформой в её нынешнем виде. Это самый конкретный, документально подтверждённый пробел между тем, что просят, и тем, что умеет система.

### Приоритет 2 — закрывает разрыв между архитектурой и доказательствами

**Кейс под питчуемую бизнес-персону.** Все ~10 именованных клиентов во всех версиях презентации — dev-tooling и инфраструктура данных; ни один не подтверждает ассистента руководителя, HR-рекрутера, тендерного специалиста или поддержку клиентов (`case-04`, `case-05`) — притом что именно эти персоны продаются на слайде 8/10. Развитие: довести до продакшена хотя бы один пилот именно в этом профиле (retail-кейс «ТоргЛайн», уже собранный в `docs/demo-retail/`, — готовый кандидат для превращения из демо в реальный референс) и получить право его назвать.

**Демонстрируемость вместо архитектурного описания.** Два конкретных места, где возможность реализована в коде, но никогда не наблюдалась работающей: селектор моделей (по всем собранным скриншотам — одна опция, `docs/platform/otkrytye-voprosy.md`) и Граф доступа с реально настроенными row/field-масками хотя бы для одной живой персоны. Развитие: на ближайшем демо-стенде — реально настроить и показать оба, а не полагаться на архитектурное «реализовано».

**Унификация пилотной рамки.** Документ разработчика описывает единый 6-недельный пилот; презентация — два отдельных, по-разному оценённых. Развитие: выбрать одну рамку для GTM (рекомендация аналитика — рамка из RFI-ответа как более новая и приоритетная) и синхронизировать оба документа, а не показывать заказчику расхождение.

### Приоритет 3 — расширяет периметр применимости

**Верифицированное расширение каталога моделей.** Подтверждены («Реализовано») только GigaChat, Qwen, OpenAI, Anthropic, YandexGPT; каталог в презентации (Gemini, Z.AI, Kimi и т. д.) — маркетинговая аспирация без подтверждения. Развитие: пройти по каждой заявленной модели тем же циклом верификации, что уже применён к первым пяти, и обновлять таблицу по факту, а не заранее.

**Собственный DLP-механизм — от «встроенной функции» к самостоятельному конкурентному аргументу.** RFI-ответ описывает автономный, не завязанный на сторонние системы механизм контроля передачи сведений ограниченного распространения (документ 2, §5.3) — это реальное архитектурное преимущество (не нужно интегрировать стороннюю DLP), которое почти не фигурирует в продающих материалах отдельно от общей темы AI Guard. Развитие: вынести как самостоятельный аргумент для заказчиков, у которых уже есть требования по DLP, но нет бюджета/времени на интеграцию стороннего продукта.

**Формализация направлений, упомянутых заказчиками, но отложенных.** На единственной живой встрече заказчик сам поднял компьютерное зрение и генерацию управляющих программ для станков как более широкие амбиции (`meeting-01-analysis.md`, ~06:31) — ITQ уже имеет непрофильный кейс в этой области (Газпромнефть, видеоаналитика, `case-05`) через партнёров. Развитие: не педалировать это в пилоте (текущая рекомендация верна), но иметь заранее подготовленный, честно обозначенный как партнёрский, ответ на этот вопрос — он предсказуемо всплывает у промышленных заказчиков этого профиля.

### Технический долг с уже назначенными сроками

Из дорожной карты RFI-ответа — просто довести до исполнения: криптографическое подтверждение неизменности журнала аудита (4 кв. 2026), аутентифицирующий прокси-сервер (4 кв. 2026), интеграция с HashiCorp Vault (1 кв. 2027). Ни один не блокирует продажи сегодня, но все три обязательно всплывут в комплаенс-чек-листе более зрелого покупателя, чем mz-arsenal.
